# 地图缩放 (ScaleBar)

代码：`src/GUI/ScaleBar.cpp` (+ `FullMap.cpp` 里"视口改成 A*scale"那几行,
`MOExperience.cpp` 里四个裸钩的 Entry)。配置：`[ScaleBar]`。
本文件是 2026-10 重写后的**实证**记录; 旧版本里关于"引擎做不到缩小"的结论是错的
(引擎没缩放路径 ≠ 不能把画好的像素缩小), 下面按新的做法重写。

---

## 0. 一句话

引擎只会 1:1 逐格画地图, 所以"缩放"= **把视口 R 改成 A 的 scale 倍, 引擎照旧
1:1 画, 呈现时在 A 与 R 之间做一次最近邻重采样**。放大 (scale<1) 视口变小,
引擎画得少; 缩小 (scale>1) 视口变大, 引擎画得多 —— 画到**我们自己的一张整图
大小的面**上, 再降采样进 Composite 的视图区。

## 2. 两个矩形与不变量

```
A = 满视图区 (侧栏模式决定宽, 高 = winH-32), FullMap 每循环写死
R = 引擎实际视口 = A * scale, 恒有 ViewBounds.X = ViewBounds.Y = 0
```

★ **ViewBounds.xy 缩放时必须恒为 0**:
- 渲染落点是 `ViewBounds.xy + (mapPos - T)`, 所以 R 永远落在渲染面的 (0,0);
  放大档就是 Composite 左上角那块, 呈现时放大铺回 A; 缩小档是大面里
  `(T, R)` 那一块, 呈现时降采样进 A。视觉结果与"居中放"完全一样。
- 引擎自己的两条查格路 (`CoordsToCell` / `ClientToCoords`) 只在 X=0 时一致,
  非 0 会让下单击与 hover 差 2·X ⇒ 缩放下绝不能靠 ViewBounds 偏移来做居中。

## 3. 档位表 (运行时生成, 不是写死三档)

```
0.25 (=4 倍放大) / 0.5 / 1 / 2 / 4 ... / 顶上一档 = 正好看到全图
全图缩放 full = max(整图宽 / A.w, 整图高 / A.h)   ← 图比视图区大 ⇒ full > 1
整图宽高 = Clamp_Center 探出来的整图包围盒 (每格 60x30)
```

- 每缩小一档 scale ×2 ⇒ 每档视野面积 ×4 ("4 倍的视野")。
- 预算: `[ScaleBar] MaxViewPx` (视口像素上限, 默认 40000000) 与
  `[ScaleBar] MaxScale` (0 = 自动到全图)。超预算就按 0.92 往回收档, 并打日志。
- `Level` ini 是**档位序号**, 不是倍率; 换分辨率/换图重建表时按 scale 找最近的一档,
  所以原来的档不会跑掉。
- 档位文字: scale≤1 打放大倍数 (`4x`/`2x`/`1x`), scale>1 打分数 (`1/2x`/`1/4x`),
  顶上一档打 `MAP`。实测 7800x4035 图 + A=1752x1048 ⇒
  `full=4.45`, 档位 `4x 2x 1x 1/2x 1/4x MAP`。

## 4. 缩小档的自建大面

- 尺寸 = 整图包围盒 + 两侧 64px 余量, **一张就够** (R 只在它里面滑动, 地图/分辨率
  变了才重建)。建面用引擎自己的 `DSurfaceClass::Create` 0x4BA5A0
  (`new(0x24)` 走引擎 operator new 0x7C8E17, 参数 (w,h,**1=系统内存**,0)),
  释放走虚表 0 号 (flag=1)。它内部把 w/h 写进 0x6C 字节的 SURFACE_DESC, 按
  `sysMem` 置 `DDSCAPS_SYSTEMMEMORY=0x800`, 再调包装类的 vtable+0x18 建面。
- ⚠ **尺寸上限**: 7800x4035 的图要 7928x4163 = **66MB** 的一张面, 实测会在
  **ddraw.dll 内部炸掉** (阶段 `swap-surface`, 栈上是 `DSurfaceClass::Create`
  的返回地址, 读野指针; 引擎自己只碰过 7M 像素的 ZBuffer/ABuffer)。所以卡一道
  `[ScaleBar] MaxSurfPx` (默认 12000000): 超过就不建, **缩小档整个关掉**, 档位表
  也把 >1 的档去掉 (`SB_CanZoomOut`) —— 否则 ViewBounds 比视图区大而没人降采样,
  屏幕上只剩左上角一小块。要更大的视野就得先确认 ddraw 吃得下 (试调大 ini,
  崩了就调回)。真要看全图得换成"自己 malloc 的马赛克 + 分条渲染"那套 (见文末)。
- 大面 (0,0) 对应的地图像素坐标 = 整图左上 - 余量; 视口在大面里的位置 =
  `TacticalPos - 大面原点`。
- **ZBuffer/ABuffer 也会跟着视口重建** (每像素 2 字节, "看到全图"那档就是几十 MB)。
  它们每帧还要 memset 清零 (十几毫秒), 所以缩小档且视口 > 4M 像素时钩掉
  `ZBuffer::Fill` 0x7BCF50 与 `ABuffer::Fill` 0x4112D0 (纯渲染缓冲; 代价是
  深度/alpha 不归零, 光束/子弹/粒子的混合在缩小档下可能略有偏差)。

## 5. 时序 (钩点与理由)

```
prepare 0x4F42F0 (每循环)  → SB_Poll   : 探整图 / 建档位表 / 摆条 / 点选滚轮换档
                              FM_Poll → Fm_ApplyViewWidth → SB_GetViewRect → 写 ViewBounds
render  0x6D3D10 (入口, 6B) → SB_RenderSurface : 缩小档把渲染面换成大面 (参数在 [esp+4])
         0x4F451B (5B)      → SB_PostMapRender : 把大面里的 R 降采样进 Composite 的 A
                              ★ 必须在 MessageList::Draw 之前 ⇒ 引擎 UI 与我们的 *_Draw
                                全都照旧画在 Composite 上, 天然 1:1 不受缩放影响
                                (战役框/提示框/超武列表/聊天框/橡皮线/光标都不用管)
呈现    0x4F4780 (DoBlit) 之后 → SB_PostPresent  : 放大档把 Composite 的 R 放大铺到 Primary 的 A,
                                                  然后在 Primary 上重画一遍 UI 层
                                                  (MOE_DrawUILayers; 光标不重画, 见 §8)
鼠标    WWMouse 虚表 +0x34     → MOE_MousePos : 物理鼠标点 → 视口点 (源头折算, 见 §7)
标脏    0x6D2790           → SB_NoteDirty : 目的区脏矩形 (静止时不必每帧扫整张大面)
```

**呈现后处理挂在哪**: 帧尾 0x7776F1 起有两条路径 —— A: `[0xA8ED5C]==1`(世界已载入,
0x683E75 置 1 / 0x6856A5 清 0) → `UpdatePrimarySurface` 0x777717 + `BlitSidebar`
0x777723 + flip 0x77772A; B: 否则(载入中/简报) → 别的 blit + flip, **没有
BlitSidebar**。正常对局只走 A, 所以后处理就挂在 `BlitSidebar` 的**入口钩**里
(前置跳板, pushal/pushfl 平衡, 栈逐字节不变), 日志 `sbar: post x120 tick=… d=…`
可核对调用率 (d≈2000 = 每帧)。

⚠ **试过但撤回的三种挂法** (都实测崩过, 别再走):
- `UpdatePrimarySurface` (0x4F4780) 的调用点: 它入口 `mov eax,[esp+0x60]` 直接从
  **调用者的栈**上读参数 ⇒ 任何多压一层返回地址的包装 (`__fastcall` 也一样) 都让
  入参错位 (崩在 0x4F48F9 `mov ebp,[ecx]`, ecx=0x31); 而且我们已经有它的入口
  前置钩, 再挂调用点等于双重跳转 (崩在 0x4F480B, edx=NULL)。那个函数的调用点
  **没法安全挂**。
- 帧尾翻页调用点 (0x77772A/0x777745/0x777776, `call [0x7E1478]`) + "换返回地址 +
  尾跳": 翻页是 **stdcall (`ret 8`)**, callee 自己把返回地址弹掉了, after 里再
  `ret` 就把调用者栈数据当返回地址跳飞 (实测 `EIP=0x15`)。
- 同样的翻页调用点 + "原样 call 再做后处理": 栈没问题, 但仍在启动阶段崩
  (`eip=15`, 栈里没有我们 DLL 的地址 ⇒ 崩在引擎里), 原因未定, 更危险, 撤回。

**教训**: 改"调用点"钩子之前先确认四件事 —— callee 的参数清理 (`ret N` 还是 `ret`)、
callee 是否从**调用者栈**上取参、同一函数是否已经有别的钩、以及被调方是不是每帧
必经。定位崩溃时"崩溃点栈里有没有本 DLL 的地址"能立刻区分是我们自己的 bug 还是
我们搞坏了别人的栈。

**放大档 UI 为什么要"跳过一次再补画"**: R 在渲染面 (0,0), 而 Composite 的 Composite
UI (小地图/超武面板/战役框/橡皮线) 也画在 R 那块屏幕上 —— 不跳过就会被一起放大
(小地图跟着变糊), 事后补画也盖不干净 (半透明底板)。所以 `MOE_DrawUILayers`
在 `SB_In()` (放大档) 时整条跳过, 只由 `SB_PostPresent` 在 Primary 上画一次
(1:1, 位置不变)。缩小档不需要这一步: 降采样发生在 `MessageList::Draw` 之前,
UI 照旧 1:1 画进 Composite。

⚠ 早先版本还做过"把 A\R 四条带从 Composite 拷回 Primary"。**这是错的**, 现在删了:
ViewBounds.xy 恒为 0 ⇒ R 在左上角, A\R 是一整块 L 形而不是四条带, 而 Composite
那一块除了 UI 还留着**缩放前的旧地图像素** (引擎只画 ViewBounds 那一块) ⇒ 拷回来
就是"地图缩在左上角 + 其余是旧图", 而且旧图每帧在变 = 持续闪烁。同理不能在放大档
往 Composite 上补画 UI。

四个裸钩的落点/首字节 (装在 `VecText_Install`, 与既有钩同一套 BuildTrampAt/PatchAt;
`PatchAt` 至少要 5 字节, 所以偷的字节数按跳板指令长度取):

| 钩 | 地址 | 首字节 | 跳回 |
|---|---|---|---|
| TacticalClass::Render | 0x6D3D10 | `81 EC F4 00 00 00` (6B) | 0x6D3D16 |
| 三趟之后降采样 | 0x4F451B | `A0 19 B5 B0 00` (5B) | 0x4F4520 |
| RegisterDirtyArea | 0x6D2790 | `83 EC 58` + `8B 0D 88 CE B0 00` (9B) | 0x6D2799 |
| ZBuffer::Fill | 0x7BCF50 | `83 EC 10` + `8B 51 2C` (7B) | 0x7BCF57 |
| ABuffer::Fill | 0x4112D0 | `83 EC 10` + `8B 51 2C` (7B) | 0x4112D7 |

**⚠ 查格钩 (ClientToCoords 0x6D2280 / CoordsToCell 0x6D6590) 已全部拆掉 (0.2.207)**
—— 改在鼠标**源头**折算, 见 §7。留下的只是这段历史, 别再照着它装回去。

<summary>为什么以前那套"按调用点白名单折算"必然漏 (已退役)</summary>

下单击那条路确实走 `CoordsToCell` (`ProcessClickCoords` 0x69238E), 只钩
ClientToCoords 的话点选会落在错的格子上 —— 这条结论本身没错, 错的是"折算点 =
查格函数的调用点"这个选点方式:

- `ClientToCoords` 4 个调用点 / `CoordsToCell` **12** 个, 其中绝大多数传的是
  引擎自己的地图像素 (0x6DA4E1 就在 `TacticalClass::Render` 里), 折算等于替
  引擎改它自己的数据 (实测开钩后启动即崩, eip=堆地址)。
- 于是只能按调用点白名单挑, 结果只折了 3 个点, 剩下的 8 个消费者全漏 ——
  其中就包括框选橡皮线 (0x6D5030) 和点选那条 (0x692F5E), 症状就是
  **"点选/框选错位, 但下令落点是对的"**。
- 白名单本身还错了一个: 0x4FB425 的注释写"入参是从某个对象读出来的点 =
  引擎自己的地图像素 ⇒ 不折", 实际 0x4FB3F8 是
  `mov ecx,[0x887640]; call [edx+0x34]`, 拿的就是鼠标。

**教训: 坐标折算要挑"数据源", 不要挑"消费者"。** 同一个物理量在一堆函数里
流过时, 在**唯一的数据源**上折一次, 比在 N 个消费者上各折一次更难漏。
</details>

## 6. 缩放在 Composite 上的两条不变量

1. **Composite 一个字节都不许在"呈现阶段"动它**。它是引擎增量维护的持久画布
   (每帧只重画脏格, 地面层靠 Tile 面 + 每趟 CopyFromPart 刷新)。在呈现阶段
   做任何重采样/拷回, 下一次增量更新就建立在改过的像素上 ⇒ 糊成一片或闪烁。
   所以放大只在 **Primary** 上做 (R→A), 缩小只在 **大面 → Composite 的
   `MessageList::Draw` 之前那次写入**里做。
2. 缩小档的降采样只写**脏矩形** (由 RegisterDirtyArea 汇总, 外加每
   `[ScaleBar] FullRefresh` 帧一次全量校正); 视野挪动 (T 变了) 时整块重采样并催
   引擎把 R 重画一遍 (拖影防护)。

## 7. 鼠标

**折算在源头做 (0.2.207 起)**: 换掉 `WWMouseClass` 虚表 **+0x34**
(`GetMousePosition`), 由我们自己的入口读实例里的原始物理坐标
(`[0x887640]+0x1C/+0x20`, 与 `GtMouseGameXY` 同源) 再折成视口点:

```
v = (p - A.xy) * R.size / A.size      (p 在 A 内才折)
```

`WWMouseClass` 虚表 +0x34 的调用点**全集是 11 个** (全二进制扫
`mov ecx,[0x887640]` 附近 `call [reg+0x34]` 得到的, 逐一核过语义):

| 调用点 | 消费者 | 坐标系 |
|---|---|---|
| 0x4A56CE | 单位矩形命中 (距离+角度打包) | 视口 |
| 0x4A91EF / 0x4A9232 / 0x4A9284 | `DisplayClass::Scroll_Map` 边缘卷屏 | 视口 |
| 0x4AAC6D | `ClientToCoords` → `ProcessClickCoords` | 视口 |
| 0x4AE538 | 框选 (`<900px`) → `ProcessClickCoords` | 视口 |
| 0x4B8FAA | 地图像素区判定 (÷60 换格) | 视口 |
| 0x4FB405 | `ClientToCoords` → `ProcessClickCoords` | 视口 |
| 0x692F5E | 点选下单击 | 视口 |
| 0x6D0ABA | 地形判定 | 视口 |
| 0x6D5068 | **框选橡皮线** (0x6D5030, `TacticalClass::Render` 第三趟调用) | 视口 |

11 个全是**视口空间**消费者 —— 它们的判据一边 (`ViewBounds` 右/下界、格号、
橡皮线矩形、单位/地块的屏幕矩形) 本来就是视口坐标, 而鼠标是物理屏幕点,
1x 下两者重合, 放大档下差一个 `A/R` 倍。**这就是"点选/框选错位但下令落点
是对的"的根因**: 下令那条恰好是唯一被白名单折到的 (`CoordsToCell`
0x69238E), 点选 (0x692F5E) 与橡皮线 (0x6D5068) 都在白名单外。

为什么这样安全:
- gadget 命中链 (`GadgetClass::Input` 0x4E1640) 用的是虚表 **+0x2C/+0x30**
  (X/Y 取值), 不是 +0x34 ⇒ 侧栏/工具栏/小地图的命中一点不变; 视口 gadget
  的矩形本来就被 `FM_TrimViewGadget` 改成按 **A** 算的, 配物理鼠标正好。
- 光标绘制走 +0x3C/+0x40 (`DrawMouseTo`), 读实例里的原始坐标 ⇒ 光标仍停在
  物理位置 (与 §8 "放大档光标看不见" 一致)。
- **1x 时 A == R, 折算恒等** ⇒ 非放大档零行为变化。
- 只读实例内存 + 只算坐标, 不碰任何模拟状态, 联机安全。

**A 之外的点原样放行, 不推成 R 之外。** 引擎自己会拒: `ClientToCoords` 只比
`ViewBounds` 的宽高 (0xB0CE30/34, 由 `TacticalClass::Set_View_Dimensions`
0x6D5F60 从 `ViewBounds` 抄来), 橡皮线与 `Scroll_Map` 是同一套边界判定。
以前那句"推到 R 之外"是在只挂两条查格路、其余调用点都还拿物理点的前提下按需要
加的; 改在源头折算之后再推, 等于替引擎改它自己的数据。

本项目里自己走 `DisplayClass::ProcessClickCoords` (0x692300) 的三处
(`OrderUtil::OU_MouseCellPx` / `OU_MouseCellTarget` / `DeployPreview::DP_MouseCellZ`)
必须在喂点之前自己调一次 `SB_MapPoint` —— 那个函数按视口空间判格, 而它们拿的是
`GtMouseGameXY` 的物理点。按引擎投影画图元的三处照旧: `DeployPreview` 走
`SB_ViewToScreen`, `SmartArea`/`FuzzyAttack` 的路径预览走 `SB_MapDeltaToScreen`。
橡皮线由引擎自己画 (0x6D5030), 不用管。

## 7.5 超武列表在放大档下会漏出来 (0.2.207 修)

原版超武列表由 `PowerBarClass::Draw` (**0x6DA9D0**, `TacticalClass::Render`
第三趟 0x4F4515 调, 画进 Composite 0x887314) 画, VecText 在 `Simple_` 入口
收表并整体隐藏。实测那批行的 **x 是 `ViewBounds.Width - 30` (名) / `-3` (计时器)**
(0x6DAF57 `add eax,[0x886FA4]`, 同一函数 0x6DB005 还把 `&ViewBounds` 当裁剪
矩形传给 `Simple_Text_Print`); 1x 下视口右缘 1752 ⇒ 名 1722 / 计时器 1749,
侧栏隐藏后右缘 1920 ⇒ ~1890。

`ViewBounds` 就是缩放用的视口 R (`R = A*scale`)。放大档下这批行跟着视口缩到
**视口右缘** (2x 下 846/873, 落在 R 里面), 随后被 `SB_CompositeMagnify` 那步
原样放大两倍 —— 于是原版列表又大又偏, 正好压在自定义面板上 (图 2/图 3 的症状)。
以前 `inband` 的横向带写死下界 1300, 846/873 被整批踢出 ⇒ 既不收表也不拦截,
`return g_OrigSimple` 放行, 原版列表照画。

**⇒ 横向带必须跟着 `ViewBounds` 走** (`VecText.cpp` 的 `VecSWBand`):
`[ViewBounds.X+Width-160, +16]`。同理 `Print` 层的计时器兜底 (`VecSWCapture`)
用同一条带。ViewBounds 还没写好时退回老口径 1300..画布宽。

**教训: 只要把 `ViewBounds` 改小, 任何"按 ViewBounds 定位"的引擎代码都会跟着
挪位置** —— 除了地图光栅化, 还有超武列表、卷屏边界、橡皮线。缩放是"改引擎
一个全局矩形", 凡是拿它当布局基准的地方都要重新核一遍。

## 8. 已知限制 / 待实测

- **放大档下光标看不见**: 我们把 Primary 的 A 整块重采样盖掉了引擎画上去的光标。
  ⚠ 别去调 0x4F4583 那两个虚表槽: `MouseClass` +0x3C 是 `RemoveMouse(surface,flag)`
  (两个栈参数), `DisplayClass` +0x44 的参数还压在栈上语义不明 —— 试过按"取光标
  索引"调 +0x3C, 实际是"抹光标", 没压参数 ⇒ 崩 (实测 `addr=8108965`,
  `call [eax+0x78]`, `ecx`=WWMouseClass 0x7B8640)。要恢复光标得走"从 Composite
  里按光标矩形把那一小块拷到 Primary"的路子, 需要先确认光标矩形来源。
- 视口大于窗口时, 引擎有几处按窗口尺寸建的临时面 (Tile 面 1920x1080 等) 会拿到
  超界 blit。DDraw 会裁剪, 不会写坏内存, 但缩小档下**局部可能糊/缺块** —— 需要
  实机看图确认, 有问题就调低 `[ScaleBar] MaxViewPx` 或 `MaxScale`。
- `VisibleCells[800]` 有硬上限 (0x6DA93E `cmp eax,0x31F`): 缩小档下若同一帧超过
  799 个"有对象的格子"要重画, 后面的单位可能不画。战场单位密度大时才会碰到。
- 缩放档下"卷动速度"仍按地图像素走 (边缘卷动看起来比 1x 快/慢 scale 倍)。
  边缘卷屏的**触发区域**已经跟着修好了 (`Scroll_Map` 那条判据就是 `ViewBounds`,
  鼠标在源头折成视口点 ⇒ 判的就是 A 的边缘, 见 §7), 但卷动步长本身没折。
- ZBuffer/ABuffer 跳过清零的副作用见 §4。

## 10. 两个把游戏打崩的真 bug (0.2.203 修)

**① 跳板偷的字节数没落在指令边界上 (主因)**

`CoordsToCell` 入口 `0x6D6590`:

```
0x6D6590  83 EC 6C        sub esp, 0x6C      3 字节
0x6D6593  53              push ebx           1 字节
0x6D6594  8B 5C 24 78     mov ebx,[esp+0x78] 4 字节  → 下一条在 0x6D6598
```

原来跳板偷 **6** 字节后跳回 **0x6D6596**, 正落在 `mov ebx,[esp+0x78]` 的正中间。
于是从 `24 78`(`and al,0x78`)开始当指令执行, 后面整段是垃圾执行 —— 它能写任意
内存(把我们 DLL 的 `g_CallC2Cell` 函数指针写成堆地址), 能跳去任何地方。症状:
**每次调用 CoordsToCell 必崩, 栈形每次一样但 eip 每次不同、都在堆上**, 看着跟
缩放毫无关系。改成偷 8 字节、跳回 `0x6D6598`, `BytesSame` 也校验完整 8 字节
(原来只校验 3 字节, 等于后面 5 字节根本没验)。

**教训: 任何"偷 N 字节 + 跳回原处+N"的跳板, N 必须是完整指令的长度。**

**② prepare 路径上的几处越界写**

- `BuildQueue.cpp` 内联汇编 `call *%1` 只声明破坏 `ecx/edx/cc/memory`, **漏了
  `ebx/esi/edi/ebp`**。引擎那个回调是真函数、会动 callee-saved 寄存器, 编译器
  却以为不会 ⇒ 紧接着用它写引擎的事件账本 `OutList_Next/OutList_Count`, 写进去的是
  垃圾值, 引擎同帧按这份坏账本派发事件就跳进堆。孪生代码 `OrderUtil.cpp` 早就修过,
  两边没同步。
- 同一处 `next` 读出来直接当数组下标用 (`next * EVT_SIZE`), 只在**写回**时 mask,
  脏值就是一次任意地址写。读出来就该 mask。
- `SWSBar.cpp` `char cur[512]`, 守卫只查 `q+1 < 512` 但一轮最多追加 21 字节 ⇒
  侧栏条目一多就写溢出、砸掉本函数栈帧(每次 poll 都发生)。
- `SWSBar.cpp` 去重删除按引擎给的 `cnt` 原地搬 0x34 字节的条目, 但没夹到权威上限
  (`SwsStripCameoCount()`), 读的那条 `SwsEngineCleanList` 有夹、写的这条漏了。
- 往 DirectDraw 面写入的几处 (`SB_CompositeMagnify` / `PowerDisplay_DrawSb`) 没查
  `pitch >= 2*width`。不是 16bpp 的面就会每行越过行尾、最后几行冲出缓冲。

**教训: 写引擎内存的每个循环都要同时按"目标对象的实际尺寸"夹, 不能只夹调用方
给的矩形。**
