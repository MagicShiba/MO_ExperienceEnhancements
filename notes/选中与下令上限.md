# 选中与下令的两道硬上限（500 / 128）

> 全部结论来自 `gamemd.exe` 反汇编 + vtable 扫描。YRpp / Ares / Phobos 三份参考里**都没有**
> 任何一处声明、修改或注释过这两个上限 —— 它们是 YR 自己的 `static` 定长数组和环形队列容量。
> 下面凡标「实证」的都附了地址；标「推断」的地方写明了依据不足。

## 0. 一句话

- **500** 限的是**框选的候选池**（`Unsorted::TacticalSelectables`），不是选中集合本身；
  选中集合 `ObjectClass::CurrentObjects` 是动态向量，**没有上限**。
- **128** 限的是**每逻辑帧能抛出的联机事件条数**（`EventClass::OutList`）。一个单位一条令
  = 一条事件，所以一次框 500 个单位右键移动，第 129 条起事件被丢弃 → **只有前 128 个单位会动**。

两道限制互相独立，各修各的。

## 1. 限制一：框选候选池 500

### 1.1 数据结构

| 项 | 地址 | 说明 |
|---|---|---|
| 数组 | **`0xB0CEC8`** | 500 项 × 12 字节 = `{Object* Obj; int X; int Y;}`（对齐 YRpp `TacticalClass.h:13`）|
| 计数器 | **`0x8880D4`** | 实例 `0x887324` + `0xDB0`（`[ecx+0xDB0]`），每帧重建 |
| 实例 | `0x887324` | 登记/消费两边的 `ecx` 都是它 |

> YRpp `Unsorted.h:652` 只声明了数组 `DEFINE_ARRAY_REFERENCE(TacticalSelectableStruct, [500], TacticalSelectables, 0xB0CEC8)`，
> 计数器偏移 `0xDB0` 是从二进制里读出来的。

### 1.2 两个写死 0x1F4 的执行点（实证）

```
; TacticalClass::AddSelectable(Techno*, x, y)   @ 0x6D9EF0   (ret 0xC)
6d9ef0: mov eax,[ecx+0xdb0]      ; SelectableCount
6d9ef7: cmp eax,0x1f4            ; == 500 ?
6d9efd: je  0x6d9f74             ; -> return false，这条静默丢掉
6d9eff: ... 写 0xB0CEC8[i*12] ...
6d9f69: mov [ecx+0xdb0],eax      ; SelectableCount++

; 另一处同款追加 (函数 0x6D9CE0, ret 0x10, 调用点 0x6D461A)
6d9e54: mov eax,[esi+0xdb0]
6d9e5c: cmp eax,0x1f4
6d9e61: je  0x6d9eca             ; 同样丢
```

### 1.3 谁往里填、谁从里面读

- **填**（每帧，屏内可见的可选对象自己登记）：`0x73CF6B`、`0x5192E6`、`0x519609`、
  `0x4148CC`、`0x74D558`（都是 `call 0x6D9EF0`）。
- **读**：`Tactical_MakeFilteredSelection` @ **`0x6D9FF0`**（Phobos 在
  `Misc/Selection.cpp` 用 `DEFINE_FUNCTION_JUMP`/`DEFINE_FUNCTION_JUMP(CALL, 0x4ABCEB, …)`
  整函数换掉了），遍历 `[0, SelectableCount)`；框选命中测试 @ `0x6DA080`（调用点
  `0x4ABCCB`）同样遍历该区间；`0x4AAE90`（MouseClass 主处理，含框选状态机）。

### 1.4 为什么「选中集合」本身没有 500

`ObjectClass::CurrentObjects` @ **`0xA8ECB8`** 是 `DynamicVectorClass<ObjectClass*>`，
`ObjectClass::Select` @ `0x5F45FD` 会经虚表 `+0x8` 扩容：

```
5f462d: mov eax,[0xa8ecc8]        ; Count
5f4632: mov ecx,[0xa8ecc0]        ; Capacity
5f4638: cmp eax,ecx
5f463a: jl  0x5f467a              ; 还有空位
5f4665: mov ecx,0xa8ecb8
5f466a: call [edx+0x8]            ; Resize
```

**所以：全选（P）、类型选择（T）、`Shift` 加选都不受 500 约束，只有「拖框选」受。**
框 600 个单位时，进候选池的只有先登记的那 500 个 → 表现为「最多选中 500」。

### 1.5 为什么没去动它

`0xB0CEC8` 后面紧邻别的全局，**没有原地扩容的空间**；要改就得整张表换基址/搬移，连带
`AddSelectable` / `MakeSelection` / `0x6DA080` / 所有调用点一起改。属于高风险低收益。
`MindSelect.cpp` 也是绕开 `SelectableCount`、直接扫 500 项原始数组的。

## 2. 限制二：每帧 128 条联机事件

### 2.1 队列结构

`EventClass::OutList` = `QueueClass<EventClass, MAX_EVENTS>`，`MAX_EVENTS = 128`
（YRpp `EventClass.h:14,16`），布局按 `QueueClass<T,N>`：

| 偏移 | 地址 | 内容 |
|---|---|---|
| +0 | **`0xA802C8`** | `Count` |
| +4 | `0xA802CC` | `Head` |
| +8 | **`0xA802D0`** | `Tail`（`& 0x7F`）|
| +12 | **`0xA802D4`** | `Array[128]`，每项 `sizeof(EventClass) = 111` |
| +12+128×111 | **`0xA83A54`** | `Timings[128]`（`timeGetTime()` 记账）|

`Add` 的语义（YRpp `QueueClass.h:80-92`）：`Count < size` 时写 `Array[Tail]`、
`Tail = (Tail+1) & (size-1)`、`++Count`，返回 true；否则**返回 false**。

后继队列（同一套 `QueueClass`，容量逐级放大）：

| 队列 | 地址 | 容量 |
|---|---|---|
| `EventClass::OutList` | `0xA802C8` | **128** |
| `EventClass::MegaMissionList` | `0xA83ED0` | 256 |
| `EventClass::DoList` | `0x8B41F8` | 16384 |

组包侧同量级上限：`MegaMissionTargets[8][8][128]` @ **`0xAFA468`**
（`MegaMissionTargetNum[64]` @ `0xAC50FC`），组包器 `0x64BFxx` 一次最多往一个包里塞
128 个 `Whom`。

### 2.2 关键粒度：**一个单位一条事件**

- 下令循环 `0x4AE750` 遍历 `ObjectClass::CurrentObjects`，**每个单位各调一次**派发；
- 每次派发最终落到 `TechnoClass::ClickedMission` @ **`0x6FFBE0`**（虚表槽 **0x378**）
  的末尾 `call 0x646E90`；
- `0x646E90` 构造一条 `EventClass` 并 `OutList.Add` —— **一次一条**；
- 事件体是 `MEGAMISSION { TargetClass Whom; Mission; Target; Destination; Follow; }`，
  `Whom` 就是「这条令给哪个单位」。

所以 **500 个单位 = 500 条事件，OutList 只装 128 条**。不存在「发一条让 500 个各自模拟」
这种批量语义 —— 同一层含义在组包侧也成立：`MegaMissionTargets` 的上界也是 128 个 `Whom`。

### 2.3 抛事件的位置（都带 `cmp …,0x80 / jge`）

```
; 抛 MEGAMISSION（单位令）—— OrderThrottle 钩的就是它的上游
646ef0: call 0x4c6860                                  ; 构造事件
646ef5: cmp DWORD PTR ds:0xa802c8,0x80
646eff: jge 0x646f58                                   ; 满 -> 丢
646f4e: mov al,0x1                                     ; Add 成功
646f58: xor al,al                                      ; Add 失败 -> 返回 false
```

## 4. 超限之后各条路径分别怎么处理

**三条路径行为不一样**：

### (a) 右键 / 自定义热键 → 逐单位派发：**完全静默**

`0x4AE750`（调用点 `0x4ABFA9`，属于 `0x4AAE90` 这个 MouseClass 主处理）：

```
4ae844: call DWORD PTR [edx+0x144]    ; 派发 (ClickedMission 分派器)
4ae84a: mov eax,[0xa8ecc8]
4ae851: inc esi
4ae858: cmp esi,eax
4ae85a: jl  0x4ae824                  ; 照旧扫完整个选区, 返回值被丢掉
```

返回值**完全不看**。超限的单位既没有语音也没有任何提示，就是不动。

### (b) 组命令逐单位循环：中途失败即停（原版语义）

```
; GuardCommandClass::Execute @ 0x730D60 (Ares 挂在 0x730DB0)
730deb: call DWORD PTR [edi+0x378]    ; ClickedMission (G 传 mission 0xB)
730df1: mov  bl,al
730df3: test bl,bl
730df5: je   0x730e8f                 ; -> 直接走函数尾巴, 剩下的人全都不管

; StopCommandClass::Execute @ 0x730EA0 (Ares 挂在 0x730EE5)
730eeb: call DWORD PTR [edx+0x374]    ; 槽 0x374 = 0x6FFE00 (S 传 6=Sticky)
730ef1: mov  bl,al
730ef3: test bl,bl
730ef5: je   0x730f1c                 ; 同上
; 第三个组命令 @ 0x730FE0 (传 7=Enter) 同样 call *0x374 (0x73101D)
```

`bl` 是「到目前为止全部成功」的标志。Guard 走槽 `0x378`，一旦有单位因队列满
失败，剩下的人全都不管；Stop（S）与第三个组命令走槽 `0x374`（`0x6FFE00`，
单 int 参，体内直塞 OutList、满静默丢但恒返 1），所以 S 循环总能扫完选区，
超限单位静默没停。OrderThrottle 对两处都加了钩（见 §6.1）。

### (c) 一处会明确拒绝 + 播语音的 128 检查

```
0x639130: mov al,[0xac4cf4]           ; 条件标志, 语义未查清 (见 §7)
639138: je  0x639203                  ; 标志为 0 -> 直接放行
639143: mov ecx,[eax+0x30]            ; 当前玩家序号
63914a: cmp ecx,0x18                  ; 0..23
63915f: mov ebp,[ecx*4+0xac4b84]      ; 该玩家的计数
        <遍历 CurrentObjects, 统计同类选中数 -> edi>
6391a3: add  ebp,edi
6391a7: cmp  ebp,0x80                 ; >128 ?
6391af: jle  0x639203                 ; 否则播一句警告语音, 让调用方放弃下单
```

调用点 `0x4ABF7F`（在 `0x4AAE90` 里），前置 `0x639040` 先判「选中的是不是同一类单位」。

### (d) 其它抛点

`QueueClass::Add` 返回 `false`，调用方多数直接忽略（和 (a) 一样静默丢）。

## 5. 联机影响：没有影响

**分帧与补发都不破坏同步**，理由是结构性的：

1. **本机生成的出站事件只归本机一家。** 别的玩家的操作是**收**进来的，本机不替他们生成
   `PRODUCE`/`PLACE`。所以「要不要延迟」只取决于本机输入 + 本机队列水位，不存在同一件事
   两端算出不同结果。
2. **补发出去的仍是原版那条事件**，带原版帧号，走同一条 `OutList → DoList` 通道。各端收到的
   还是同一串事件、同一个执行序；「晚几帧发」与「网络延迟晚几帧到」等价。帧 CRC
   （`LatestFramesCRC[256]` @ `0xB04474`、`CurrentFrameCRC` @ `0xAC51FC`）算的是这串字节，
   字节相同就不会报不同步。
3. **一条被挤掉的事件是「所有端一起缺」。** 它根本没进 OutList → 根本没上网 → 谁也没收到。
   这是「偶发丢一个开工/丢一个单位」的玩法 bug（YR 原版就带着这个 bug），不是不同步。
4. **每帧峰值没有超过原版。** 原版一帧就是 128 条 × 111B ≈ 14KB；本模块补发时每帧同样最多
   128 条 = 同样 14KB，只是把原来丢掉的那部分摊到后续帧。

因此 `[Features] OrderThrottle=2` 纯粹保守，挡的是 §3.3 那个没验证的下一层缓冲，不是同步。
单机（`GameMode` 0=战役 / 5=遭遇战）直开。`GameMode` @ `0xA8B238`：
`Campaign=0 / LAN=3 / Internet=4 / Skirmish=5`。

## 6. 已实施：`OrderThrottle`

### 6.1 钩点（三路，共用 Decide/队列/Poll/配置）

`.text` 直接补丁（不进 `.inj`）：`0x6FFBE0: 81 EC 88 00 00 00 53 55 56 57`
（`sub esp,0x88` + 四个 push，偷 10B 且不含任何直接相对跳转，跳板重放安全；回跳 `0x6FFBEA`，
尾声 `ret 0x10`，返回值只保证 AL）。入口栈形 `[esp+4]=Mission, +8=pTarget,
+0xC=TargetCell, +0x10=NearestCell`，`ECX=this`。冲突核对：Phobos 只钩 `0x6FFD4C`
（体内 +0x16C 的 VoiceSpecialAttack），Ares 只钩 `0x6FF860`/`0x6FFEC0`/`0x6FFF9E`，无
`0x6FFBE0`，不重叠。

第二钩 `0x6FFE00`（槽 `0x374`）：`83 EC 78 56 57`（`sub esp,0x78` + push esi +
push edi），偷 5B，跳板回跳 `0x6FFE05`，尾声 `ret 0x4`，入口栈形 `[esp+4]=int 参数`。

### 6.2 判定与补发

判定（**原版能发的发，原版会丢的不丢**，无额外阈值）：

```c
if (s_QCount <= 0 && *(unsigned*)ADDR_OUT_COUNT < EVT_CAP) return 0;  /* 放行 */
... 否则入队 (返回 1) ...
if (s_QCount >= OT_QCAP) return 2;  /* 队列满: 与原版同形地失败 */
```

补发（挂 `PowerDrawBoth` 每逻辑帧）：`cnt=OutList 现有数; cnt>=128 return;`
`while (队非空 && cnt<128)` 校验后调**跳板**（非补丁入口，不递归），`cnt++`
（一条令恰推进 1）。`cnt` 是上界：原版中途拒收只会令其高估，高估 = 少发方向，本帧必不溢出，
无需预留。补发还原入队瞬间 `MoveFeedback`（`0x822CF2`），语音不变。

第三路 kind=2（中键托管 raw 事件）：补发 = `OU_Enqueue` 原样入队，
`OU_Enqueue` 回 0（OutList 真满）则 `break` 留下轮、不 pop；kind=0/1 保持原语义
（跳板原函数满丢也认 `cnt++`）。

### 6.3 中键收编（七家中键模块）

SmartOrder/SmartArea/FuzzyAttack/PatrolCircle/TreeChop/AttackMove/DeployPreview
不调 `ClickedMission`（写本地状态，联机不安全）。各家 `Fire*` 先调 `OT_SubmitRaw`，
回 1 即托管成功，回 0 才 `OU_Enqueue` 走自家 drip：

- 单机 + `OrderThrottle≠0`：超限事件进 OT 队列（1024），与右键/S 同水位分帧补发；
  统计行 `q2=` 即中托管累计。
- 联机（默认 mode=1）或 `OrderThrottle=0` 或 OT 队满（1024）：`OT_SubmitRaw` 回 0，
  各家保持原 drip 行走为，不影响联机。
- 快照/待发上限提到 1024（`SO/SA/FA/TC/AM_*_CAP`，`PC_CLOSE_CAP`；
  `PC_PEND_CAP`=16×1024+1024=17408），目标类上限（`SA_TGT_CAP`/`FA_ENEMY_CAP`/
  `TC_TREE_CAP`，定"打谁"不定条数）保持 256；`PC_FireCommit`（单条 house 事件）
  不托管，直发。
- kind=2 校验：`OU_PtrAlive`（Fetch_ID 二分）验 Whom + 入队瞬间 house 指针比对。

### 6.4 兜底

换图/读档（`ScenarioClass::Instance` @ `0xA8B230` 变）整队丢弃；单条等超 600 帧（~10s）丢弃；
补发前校验（`IsPlausiblePtr` + 虚表落 exe 映像 + `IsAlive`(+0x90) 且非 `InLimbo`(+0x81)，
cell 只验指针）；装钩幂等 + 目标点被占则 `OFF` 不覆盖。

### 6.5 配置

```ini
[Features]
OrderThrottle=1 ; 0=禁用 (完全旁路, 与原版逐位相同); 1=仅单机 (默认); 2=联机也启用, 见 §5
```

## 7. 没查清（别当结论用）

- `0xAC4CF4` 标志语义，§4(c) 那条 128 拒绝何时真正生效。
- `WinsockInterfaceClass` 三个 128 缓冲在满命令量下溢出是丢包还是阻塞。
- `MegaMissionTargets` 的 128 是「每组 128 目标」还是别的含义（仅从 `0x64BFxx` 偏移算术推断）。
- §3.1 表中未标抛出处的行只确认了名字与编号，未逐个定位调用点。
