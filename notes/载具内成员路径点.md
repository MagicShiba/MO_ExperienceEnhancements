# 载具/驻军建筑内成员的路径点

目标：载具（或驻军建筑）里的某个成员，**还在容器内**时就能给它规划路径点，出舱后按路径走。

## 结论

- 引擎侧**没有"载具内单位不能规划"的检查**：建节点的整条路径只看命令类型、目标和该单位
  计划链的最后一环，不看 `InLimbo`/`Transporter`。事件里的 Whom 指向那个成员，节点就挂得上。
- 真正的两堵墙：
  1. **UI**：limbo 单位不在图上，原版选不到它，永远发不出这种事件。我们自己发事件，
     不需要选中表，`Whom` 直接给成员 ID。
  2. **Enter 是终止节点**：计划链最后一环的 mission 是 `Enter(7)`/`Capture(8)`/`Eaten(9)`
     时，再加点会被拒收并播 `MSG:PostTerminatingCommand`。用路径点进舱的单位，计划正好
     以 Enter 收尾，于是"进舱后再补点"这条路被引擎主动关掉了。
- 只发标准事件（MegaMission `IsPlanningEvent=1` + 引擎自己的 PlanCommit），各端跑同一份
  原版代码 → **联机天然一致**。唯一例外是绕过第 2 条时（那是事件处理器里的共同判断，
  只有本端放宽就会分叉）。

## 规划系统（PlanMgr）

事件驱动的共享结构，因此"谁加的节点"不影响一致性：

| 事 | 地址 | 作用 |
|---|---|---|
| PlanConnect | `0x2A`（ctor `0x4C6780`） | 把单位挂到已有节点（合环/并线） |
| PlanCommit | `0x2B` | 松开 Z：定稿并让带 token 的单位开始执行 |
| PlanNodeDelete | `0x2C` | 删节点 |
| 处理器 | `0x4C6CDE` → `0x637E00(event)` | 上面三种都进这里，按 `event->Type` 分支 |
| 建节点/挂单位 | `0x638120(unit, event)` | token 空则新建（`0x635F20`，0x9C）并挂上 |
| 加点校验 | `0x638CE0(unit, event)` | 返回 `-1`=没计划可续（正常建点）、`0=命令类型非法`、`1=会终止现有路线` |
| 计划推进 | `0x6385C0 TryNextPlanningTokenNode` | 上一段任务收尾时取下一节点 |
| 路径渲染 | `0x6393A0` 每帧扫 token 数组画折线 | 只要有 token 就画，与单位在哪无关 |

- token 挂点：`TechnoClass+0x514`（`0x705D20` 取 / `0x705D10` 设），
  `Items@+0x08`、节点数 `@+0x14`、`ClosedLoopNodeCount@+0x90`；
  全局数组 `0xAC4C78`（Items `0xAC4C7C` / Count `0xAC4C88`）。
- 每个节点里存一份**完整的 111 字节命令事件拷贝**（`0x638D5D` 起 `rep movsd`），
  所以"最后一环是什么命令"是直接读节点里的 mission 字节（`+0xC`）。

### 拒收判定 `0x638CE0`

1. 事件类型 ∈ {Deploy 9, Idle 6, Scatter 7}？→ `0`（后续播 NoDeploy / NoStop / NoScatter）。
2. mission == `Area_Guard(11)` 且目标就是自己脚下 → `0`（`MSG:PlanningModeNoGuardArea`，判定在 `0x638B70`）。
3. 取该单位 token 的**最后一个节点**，读它的 mission：
   - ∈ {`Enter(7)`, `Capture(8)`, `Eaten(9)`} → **`1`**：`0x6382AA` 播
     `MSG:PostTerminatingCommand`（`0x836BB8`，只播一次，`0xAC4C08` 压标志），本次不加点。
   - ∈ {`Attack(1)`, `Place(0xB)`} 且新命令同类 → `2`（另一条反馈）。
   - 其它 → `-1`：正常建点（`0x638325`）。

新建节点分支（`0x638325`）里对**新命令**是 Enter/Capture/Eaten 反而放行（不报错），
所以 `[移动, 移动, Enter]` 是合法计划；被禁的只有 `[Enter, …]` 这种"进舱之后还想续"。

## 联机红线

第 3 条（Enter 终止）是**事件处理器里的共同判断**：只要有一个端放宽，同一串
PlanConnect 在两端落成不同的节点表 → 计划执行分叉。要放宽就只能在单机放宽
（`OU_IsMP()` 判定），联机保持原版拒收，和 `SingleUnload` 同一套处理。

## 实现（手势 = 按住 Z 点载员格）

配置 `[Features] PaxWaypoint`（默认 1）。代码全在 `src/misc/SingleUnload.cpp`，
面板侧只有两处接线（`src/gui/UnitPanel.cpp`）。

| 步骤 | 位置 | 做什么 |
|---|---|---|
| 认人 | `SU_ClickPassenger` → `SU_PlanArm` | Z 按住时点面板载员格 = 只认这一个（**重建集合**，可切回单人） |
| 认人（全部） | `UP_Click` → `SU_PlanArmAll` | Z 按住时点第 0/1 格（本车/本建筑自己）= 认下车里全部载员 |
| 认人（多选） | `UP_Click` → `SU_PlanArmList` | shift 点载员格挂名单（2px 黄框），按住 shift + Z 再点其中一个 = 只给名单里这几个 |
| 认人（名单自动） | `UP_Poll` → `SU_PlanAutoArm` | 名单非空 + **按住 shift** + 按住 Z 就自动认下 —— 不必先回面板点一次 |
| 吞点击 | `UP_ClickGate` → `SU_PlanClick` | Z 按住 + 左键按下沿：吞掉这次地图点击（否则选中的载具也加点），置待决 |
| 发令 | `UP_Poll` → `SU_PlanPoll` → `SU_PlanAdd` | `OU_MouseCellTarget` 取格 + 点中对象，判出 Mission，**当场发** `IsPlanningEvent=1` 的 MegaMission |
| 垫点 | `SU_PlanArm` → `SU_PlanPadOne` | **只有容器里仅 1 个载员时**，认人时立刻补一个移动节点（落点=自己所在格），专门给引擎的提交吃掉 |
| 结束 | `SU_PlanPoll` | Z 松开 / 载员没了 / **容器被取消选中** → `SU_PlanDisarm`；提交由引擎自己发（`0x637A10`） |

### shift 多选载员

面板自己维护一份「多选名单」（`s_Pick[]` / `s_PickHost`，最多 12 个），**shift + 点载员格**
加入/移出，与游戏的选择集无关（载员在车内不可被引擎选中，所以不能用 `CurrentObjects`）。

**shift 是"多选模式"的显式开关**：名单只在按住 shift 时参与决策，松开回到"只给这一个"的
默认语义。用到名单的地方都要过这道门（`UP_Click` 里取一次 `sh`，`UP_Poll` 里现取一次
`GetAsyncKeyState(VK_SHIFT)`）。

**不按 shift 点载员格会 `Up_PickClear()`**：这是明确的单人语义，同时收掉名单，避免下一次
按住 shift 按 Z 又把旧名单整组认下来。

**单人路径必须重建集合**（`SU_ClickPassenger` → `SU_PlanArm`），不能往现有集合里补；补人
只能走 shift 分支的 `SU_PlanResync`。

| 操作 | 结果 |
|---|---|
| shift + 点载员格 | 加入/移出名单，**2px 黄框**标记（不卸载、不开始规划） |
| 按住 shift + 按 Z（名单非空） | 自动认下名单，之后的地图左键就是这些人的路径点 |
| 按住 shift + 按 Z（规划中）+ 点载员格 | 只把这个新载员补进集合（`SU_PlanResync`，只增不减） |
| 按住 shift + Z + 点第 0/1 格（本车/本建筑） | 有名单 → 只给名单里的；没名单 → 车内全部 |
| **不按 shift，Z + 点载员格** | **只给这一个**（重建集合），可从多选切回单人 |
| 不按 shift，Z + 点第 0/1 格 | 车内全部 |
| 普通点载员格（不按 Z） | 单卸 |

名单的生命周期：归属容器变了（换选中目标、取消选中）就整组清掉，`UP_Poll` 每帧
`Up_PickPrune` 查一次 `s_List[0].obj == s_PickHost`；载员指针会被引擎复用，不能只
存指针不留归属。名单在翻页、多页版式下都按指针身份匹配，不受页码影响。

**名单用完必须清**：一次规划真的下过点（`SU_PlanFiredCount() > 0`）且规划结束时
`Up_PickClear()`。不清的话下一次按 Z 又被它接管，想给载具本身下点就下不成；反过来
只按一下 Z 又松开（误触）`s_PlanFired` 为 0 就跳过。

**规划已开始之后名单变化要跟着同步**（`SU_PlanResync`，shift 点完名单立刻调）：认人只
发生在面板点击那一帧，不同步的话"先 Z+点一个人开规划、再 shift 补选两个"只有第一个人执行。

`SU_PlanResync` 是**只增不减**的：只把新出现的载员加进 `s_PlanPax[]`，不移除。节点是
"点击即发"的，已经发出去的收不回来（单机没有可用的删节点事件），把一个人移出集合只会
留下挂在他 token 上的孤儿节点。所以 shift 取消选中对已在规划中的那个人不起作用 ——
要重来就松 Z 重新认人。

黄框 2px（`Up_CellFrame` 内部两圈循环：外 1px 贴格边、内 1px 紧贴它，255/205/60），画在
cameo 之后。条件：

```
SU_PlanHasPax(e->obj) || (sh && Up_PickHas(e->obj))
```

- `SU_PlanHasPax` = 正在参与本次规划的载员，**一直画**。单人规划也画（那是"选中了这个人"
  的反馈），也包括"Z+点载员格"直接认下的那个（他不在 shift 名单里）。
- `Up_PickHas` = shift 名单，**只在按住 shift 时画**，松手回到单人视图。
- 两个条件缺一不可：只留前者，松 shift 后名单仍在画框；只留后者，单人点选没有框。

排除容器自己那一格用**对象比较** `e->obj != s_List[0].obj`，不要用 `i >= 2`：
分页版式下第 0/1 格也是载员（信息格 `count == 0` 已被上面挡掉）。

### 一次给全部载员下令

单选版式第 0 格是本车/本建筑的图标、第 1 格是它的信息格，第 2 格起才是载员。
Z 按住时点**第 0 或第 1 格** = 认下车里所有载员（载具走 `0x118` 链，建筑走
`Occupants` 向量），之后每个地图点会给**每个载员各发一条**，`s_PlanPax[]` 最多 10 个。

- 不对容器本身下令：建筑驻军时它本来不能动，载具不靠面板也能直接在地图上点。
- 每个载员的 Mission **各自判定**（同一格对工程师是占领、对步兵是移动），
  不能共用一次 `OU_NativeMission`。
- 日志 `plan node m=.. n=.. k=<发出数>/<认下数>`：`k=5/5` 表示全员都收到了。

### 取消选中 = 结束本次规划

`SU_PlanStillInside` 同时要求**容器还在 `CurrentObjects` 里**（`SU_HostSelected`，扫
`0xA8ECB8` 的 items/count）。否则右键取消选中之后，地图左键仍会被点击门吞掉去给车里的
人加点。

### 为什么开头要垫一个节点

松开 Z 时引擎**无条件**发 PlanCommit（`0x637A10`，处理器扫**全族 Techno**，limbo
成员也在内）。提交对每个有 token 的单位做的事是：把 token 里的**第一个节点当场
转成一条真令**派下去（`0x6385C0` 把节点事件的 `+0x1D` 置 2 再入队）。载员还在舱里，
这条令跑不起来 → 这个节点就废了。

所以 `SU_PlanArm`（认人那一刻）先发一个**移动节点，落点取该载员自己所在格**
（`OU_GetCoords` → `/256`，失败退到容器），专门去挨这一下。

**只在容器里恰好一个载员时垫**（`SU_HostPaxCount(host, bld) == 1`）：多载员载具提交
从不吞路径点，节点原样留在 token 上，再垫一个就是白白多走一段。判据取"容器总载员数"，
不是"本次认下几个" —— 从三人车里单挑一个，提交同样不吃节点。不垫时写日志
`plan nopad pc=<载员数>`。

**必须在认人时发、不能等到第一次点击**：单机事件是直写 DoList，由主循环下一拍才派发；
而提交是在松开 Z 的**同一帧**立刻跑。点击与松手挨得近时，事件还没进 token，提交就在
空 token 上跑完了。认人比松手早几帧到几秒，这个时间差足够稳。

落点选自己那格还有两个好处：提交把它转成真令后等于"走到原地"，出舱瞬间完成，不影响
后续；也不会和第一个真节点同格同形被引擎合并。

判据是"该载员 token 当前 0 个节点 = 新计划"：已有计划就不垫（往队尾垫只会多走一段）。
同一计划只垫一次；等 token 先挂上节点、之后又清空（计划跑完了）才重置，所以同一个兵
第二次进车再规划还会重新垫。表 `SU_PAD_MAX=10`，键是单位指针 + 单位 ID，指针复用即丢。

```
日志对法:  plan arm → plan pad x= y= → (点击) plan node m=.. n=1,2..
           su: plan nopad pc=<N>  多人容器, 本次不垫 (N=容器总载员数)
```

### 约束一：取格函数自己也被点击门钩着

`SU_PlanPoll` 取格用的 `OU_MouseCellTarget` 内部就调 `ProcessClickCoords`，而那个
函数正是被 `UP_ClickGate` 钩住的 —— 门在自家这次调用里又跑一遍 `SU_PlanClick`，看到
"左键还按着 + `s_PlanLb` 已置"就返回 1 把这次坐标计算也吞了，`ProcessClickCoords`
失败 → 恒回 0 → 节点一次都没发出去。
解法是 `s_PlanQuery` 自锁：取格前后置 1/0，`SU_PlanClick` 见到它直接回 0。
**凡是"取格函数自身被门钩着"的模块都要这样自锁。**

### 约束二：任务类型必须与裸左键同判

路径点上的命令不是"MOVE 到那格"，而是"这个单位对那个目标按左键会下什么"。
所以取格时同时取点中对象（`OU_MouseCellTarget`），再问
`OU_NativeMission(pax, tgt)`（vtbl+0x74 光标 → 类内重映射 → `0x4D74E0` 表）：

| 判定结果 | 事件形状（与 `SmartArea`/`SmartOrder` 同源） |
|---|---|
| `Attack(1)` | `Target=目标对象` |
| `Enter(7)` / `Capture(8)` / `Sabotage(17)` | `Destination=目标对象`，Follow 空 |
| 其余（含 -1） | `Destination=格`，`Follow=格`（移动） |

于是工程师的路径点"占领建筑"、"进入载具"、"攻击敌兵"都与手点一致。
点中**自己所在的容器或自己**时强制落回移动（Enter 回本车没有意义）。

### 已知限制

- 同一条计划**分两次画**（松 Z 再按 Z 续点）时，第二次的提交还会再吃一个真节点，
  因为垫点只能加在队尾。要避免就这么用：一次按住 Z 把点画完。
- 计划链最后一环是 `Enter/Capture/Eaten` 时补点会被引擎按原版拒收并提示，见上文。

日志（每次规划/点击各一行，不是每帧）：`plan arm` / `plan pad x= y=`（垫点已发）/
`plan node m=<mission> x= y= n=<本计划第几个> k=<发出数>/<认下数>` / `plan nopad pc=`
（多人容器不垫）/ `plan end z|gone`（松 Z / 载员不在了）/ 失败路径 `plan cell fail|bad`、
`plan uid fail`、`plan fire fail`、`plan pad drop`。

排查"发了令但没执行"看 `plan node` 的 `k=`：`k=<认下数>` 表示每个载员都收到了事件；
`k` 偏小就是某个载员的事件被引擎丢了，问题在发令侧，否则在引擎执行侧。
