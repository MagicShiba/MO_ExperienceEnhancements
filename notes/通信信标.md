# 通信信标 (B 键放置) 单机启用

原版只在联机可用。单机被**四处** `GameMode==0 || GameMode==5` 早退挡住,
全部共享同一段字节 `a1 38 b2 a8 00 85 c0`（`mov eax,[0xA8B238]` + `test eax,eax`）：

| 地址 | 函数 | 早退落点 | 早退之后还剩什么 | 单机要补吗 |
|---|---|---|---|---|
| `0x5370A0` | `BeaconPlacementCommandClass::Execute` | `0x5370B3` (ret 4) | 全部（就是整个动作） | **要** |
| `0x430CD4` | `BeaconManagerClass::PlaceBeacon` 尾 | `0x430F20` | EVA + 两条操作提示 + 组包广播 | **要**（只要 UI 那半段） |
| `0x4314F1` | `EditBeaconMessage` | `0x4316EA` | 只剩发包 + 非本家 EVA | 不要 |
| `0x431331` | `DeleteBeacon` | `0x4313F8` | 只剩发包 | 不要 |

关键结论：**信标本体（建对象/写槽/绘制/雷达点/点选/文字读写）全都不查 GameMode**，
四处早退都挡在“动作入口”或“动作收尾”。单机需要开放前两处、跳过组包并补齐美术，
信标文字输入另依赖 ChatBoxSP，不能只改 B 键入口就认为整套功能可用。

联机保持每玩家 3 个共享槽；单机可将现有 24 槽池化，见第十四节。

本文的地址、寻址和广播可达性结论来自当前 `gamemd.exe` 的静态反汇编及 YRpp/Phobos 参考。
美术参数和单机 24 槽轮换另有已有日志支持；点选、删改、跨场景清理及原版对端兼容性
不能由轮换日志推出。本轮未做双客户端、抓包或丢包实测，不把静态路径核验写成联机实测通过。

## 一、键位 → 布署模式

```
BeaconPlacementCommandClass::Execute   0x5370A0   (vtable 0x7EBBDC)
  a1 38 b2 a8 00   mov  eax,[0xA8B238]      ; GameMode
  85 c0            test eax,eax
  74 0a            je   0x5370B3             ; Campaign(0) → ret 4, 什么都不做
  83 f8 05         cmp  eax,5
  74 05            je   0x5370B3             ; Skirmish(5) → 同上
0x5370AE: e8 7d a9 1f 00   call 0x731A30
0x5370B3: c2 04 00         ret  4
```

`0x731A30`（信标布署开关壳）：
```
mov eax,[0xA8B538]      ; Unsorted::MuteSWLaunches
test eax,eax
jne 0x731A45 (ret)      ; 非 0 直接不响应
push -1                 ; -1 = 切换
mov ecx,0x87F7E8        ; DisplayClass::Instance
call 0x4AC960           ; SetPlaceBeaconMode
ret
```

`0x4AC960 SetPlaceBeaconMode(int mode)`（`ret 4`，mode：-1 切换 / 0 关 / 1 开）：
- 与 `[0x87F7E8+0x11B4]` 比较，相同就什么都不做；
- `[0x87F7E8+0x11A8]`（CurrentBuilding）非 0 就拒（正在放建筑）；
- 打开时用 `[0xA83D4C]+0x30` 调 `CanPlaceBeacon 0x430F30`，**满 3 个就静默拒绝**
  （`0x4AC9B6 xor bl,bl`，无提示、无音效）；
- 成功：`[+0x11B4]=1`（`0x4AC9E3`）然后 `call 0x48DC90 UnselectAll()`。
  `UnselectAll` 是必需的：`DisplayClass::DecideAction 0x692610` 在有选中物体时
  会先走别的分支，选着单位按 B 会拿不到 `action=0x3C`。
- 关闭路径顺带清 `[+0x11B0/11B1/11B2/11B3]` 四个布署模式字节。

**`0x88099C` 就是 `[0x87F7E8+0x11B4]`**（0x87F7E8 + 0x11B4 = 0x88099C），
所以“单例基址+字段”与“全局绝对地址”两种写法指的是同一个字节。它的全部引用只有 5 处：
`0x4FB8A2` / `0x6AAF8B` / `0x6DEDD0` / `0x6E26A6` 写 0（关各类布署模式）、
`0x6929AF` 读（`mov al,[0x88099C]; test; je; mov [esp+0x10],0x3C`）。
邻座 `0x880999/99A/99B` = `+0x11B1/11B2/11B3`，是另外三种布署模式。

## 二、放置提交（不查 GameMode）

`0x4AC033`（`DisplayClass` 左键提交内）：
```
cmp eax,0x3C                 ; Action::PlaceBeacon
jne ...
mov eax,[0xA8B538]           ; MuteSWLaunches
test eax,eax
jne 0x4AC0A2                 ; 非 0 只关模式不放置
call 0x5657A0                ; 取格 (esi = CellStruct*)
; Coord = (cell.X*256+0x80, cell.Y*256+0x80, [cell+0x11B]*[0x8A0740])
push -1                      ; houseBeaconId = -1 (自动选空槽)
call 0x430BA0                ; PlaceBeacon(Coord, houseId=[0xA83D4C]+0x30, -1)
0x4AC0A2: SetPlaceBeaconMode(0)   ; 放完自动退出布署模式
```

`0x430BA0 PlaceBeacon`（`ret 0x14`，5 参数：Coord 3 个 dword + houseId + id）：
- `0x430BC6..0x430BD2` 扫本家 3 个槽；满了且 `id==-1` → `0x430F20` 早退；
- `0x114` 字节分配（`0x7C8E17`），拷 `0x89C430/434/438` 上次坐标模板，
  `and al,0xFC`（`0x430C16`），清 0x40 个 dword 的 `Text[128]`；
- 写槽 `0x430C72`；`HouseID`（`0x430CBE`）、`Bitfield |= 1`（`0x430CC4`）、
  `AllocatedCount++`（`0x430CD0`）—— **这三步在早退之前，单机照跑**；
- `0x430CD4` 早退（单机到此为止：信标已存在、已在画、能点选、文字能存）；
- `id != -1`（指定槽，原生收包使用此路径）分支 `0x430E5D`：若旧槽非空则释放旧信标并
  `AllocatedCount--`，写入新对象后 `jmp 0x430C76`。它只跳过自动选槽/写槽段，
  **仍执行公共坐标初始化、HouseID、可见位、AllocatedCount++ 和 0x430CD4 尾段**。
  因此覆盖已占槽时计数净变化为 0，写入空槽时为 +1。

## 三、收尾段（EVA / 提示 / 广播）

从 `0x430CEA` 开始（单机补的就是这里）：
```
0x430CEA  mov ecx,[0xA83D4C]
0x430CF0  cmp ebx,[ecx+0x30]        ; ebx = houseId, 是本家吗
0x430CF3  jne 0x430E87              ; 非本家 → 侦察提示分支
; ---- 本家 ----
0x430D18  格式串 0x818AC4 "TXT_BEACON_HELP1"  (+ 玩家名 [CurrentPlayer+0x16054])
0x430D2C  call 0x5D3BA0             ; MessageListClass::AddMessage
0x430D55  格式串 0x818AB0 "TXT_BEACON_HELP2"
0x430D69  call 0x5D3BA0
0x430D78  VoxClass::Play("EVA_BeaconPlaced")             ; 0x752700
0x430D94  VocClass::PlayGlobal(idx, 0x2000, 1.0f)       ; 0x750920
0x430D99  mov ecx,[0xA8DA78]        ; ★ 从这里开始组 IPX 包
0x430DA7  mov ecx,[ecx]             ; 玩家表首元素 → 名字转换 0x7350C0
0x430D9F  [esp+0x18] = 0x20         ; 包类型 0x20 = 放置
...
0x430E02  [esp+0x54] = bl           ; houseId
0x430E06  cmp eax,esi / jle 0x430F20  ; eax=[0xA8DA84] 玩家数; ≤1 直接退
0x430E0C..0x430E4E  逐玩家 0x5410F0 Send_Global_Message(buf, 0x3D, 1, addr, 0, 0)
0x430E50  pop edi/esi/ebp/ebx; add esp,0x1D0; ret 0x14
; ---- 非本家（只在本机收到别人放的包时走）----
0x430E87  Bitfield&1 → IsAlliedWith(0x4F9A10) → 0x4F9A50 → [house+0x1F5] 迷雾
0x430F03  0x65FA70(0xB, cell)       ; RadarEvent
0x430F16  VoxClass::Play("EVA_BeaconDetected")
```

单机补 `0x430CD4` 后若一路跑下去会进 `0x430D99` 那段组包：
`[0xA8DA78]` 是 `NodeNameType::Array`（`DynamicVectorClass` @ `0xA8DA74`）的 Items 指针，
`0x430DA7` 再解引用它的首元素。单人局玩家表可能为空 → Items 为 NULL → 崩。
所以单机在 `0x430D99` 再拦一刀，直接跳到共享收尾 `0x430E50`：
EVA 和提示照拿，组包与广播整段不跑（单机本来也没有对端）。

## 四、删除 / 改文字（单机无需补）

`DeleteBeacon 0x4311C0`（`ret 8`，houseId, houseBeaconId）：`(-1,-1)` = 删本地选中的那个
（`0x4311F4..0x431219` 扫 8×3 找 `Bitfield&2`）；释放、清槽、`AllocatedCount--`（`0x43132E`）
和删除特效（`0x4312B0..0x4312E6`）全在早退之前，`0x431331` 之后只剩发包（类型 `0x21`）。

`EditBeaconMessage 0x431450`（`ret 0x10`）：删/改文字的落盘（清 128 wchar + 拷新文字
`0x4314D6..0x4314EE`）也在早退之前，之后只剩发包（类型 `0x22`）与非本家的 EVA。

`DeleteAllBeacons 0x431410`（`ret 4`）按 `house*3` 删一家 3 槽，不查 GameMode。
"删除信标"命令 `0x537F90` = `call 0x731A10; ret 4`：有选中对象就转给对象，否则
`DeleteBeacon(-1,-1)`。原版没有删除热键（KeyboardMD.ini 只有 `PlaceBeacon=66`），删除靠选中
信标后按 Del —— `0x55E77B` 分支 → `0x431170` 找选中信标 → `0x431450` 传空文字清讯息，
真正的删除走 `0x537F90`。

## 七、数据布局

`BeaconManagerClass` @ `0x89C3B0`（`sizeof 0x80`）：
```
BeaconClass* Beacons[8][3]   +0x00   (共 0x60 字节, 索引 = house*3 + id)
int          AllocatedCount  +0x60
Point2D      BeaconSize      +0x64
int          BeaconFrameCount +0x6C
Point2D      RadarBeaconSize +0x70
int          RadarBeaconFrameCount +0x78
int          RadarBeaconAnimPeriod +0x7C
```
`0x89C410` 是上述对象的 `+0x60 AllocatedCount`，不是美术已载标记。
对象范围为 `0x89C3B0..0x89C42F`；对象之外的旁挂全局包括上次坐标模板
`0x89C430/434/438`、`BeaconArt` `0x89C474` 和 `RadarBeaconArt` `0x89C478`。
绝对地址相邻不代表它们属于同一个 `0x80` 字节对象。

`BeaconClass`（`sizeof 0x114`）：
```
CoordStruct Coord   +0x00
byte        Bitfield +0x0C   1=已放置(可见)  2=本地选中
wchar_t     Text[128] +0x0E
int         HouseID  +0x110
```

生命周期：
- 构造 `0x430190`：清 `0x18` 个 dword（`0x60` 字节）并注册 `0x4301C0` 清理；
- `Reset 0x430980`（`0x5349A0` 调）：释放 8×3 并清 `+0x60` —— **换场景即清空**；
- 已核对的离场/战败调用 `0x4FC1C6` → `DeleteAllBeacons` 前有
  `CurrentPlayer == 当前处理的House` 门控，不能据此推断任意 AI 战败都会调用此清理；
- 存档：Phobos `src/Ext/House/Body.cpp` 的序列化注释为
  `beacon is not saved, so this follows it.`，说明其按原生信标不保存来处理序号表。
  这不是“只有扩容部分不保存”；本轮未另做存读档实测，不承诺读档保留任何信标；
- 美术 `LoadArt 0x4309D0`（`__thiscall(self=0x89C3B0)`）：唯一调用点在 `0x687BB2`，
  属**联机开局流程**（`0x686B20` 一族），单机不走 ⇒ 单机美术与动画周期都停在
  静态构造留下的 0。单机要用信标必须自己补调一次，见第十节。
  资源本身在：`PBEACON.SHP` 66×?、20 帧，`RDRBEACN.SHP`，补调后
  `period=32 / w=66 / f=20`（实测日志）。

## 八、联机为什么保持 3 槽

- 原生上限由 `Beacons[8][3]`、判满循环和 `house*3+id` 寻址共同决定，
  不是一个可单独调大的容量变量。`CanPlaceBeacon 0x430F30` 扫本家 3 槽
  （`0x430F45 cmp,3`）；`AllocatedCount` 是数量/绘制闸门，不决定数组步长。
- 数组位于固定全局 `0x89C3B0`，后面紧跟 `+0x60` 的计数与尺寸字段，
  **原地不能直接加长**。扩容必须同时处理所有寻址、遍历、删改和生命周期路径；
  混合 `house` 与 `slot` 的 `lea` 不能一律替换为清零。
- 已核对的信标复制路径使用独立 IPX 全局包
  （`IPXManagerClass 0xA8E9C0` 的 `Send_Global_Message 0x5410F0`），
  而非单位命令的 `EventClass` OutList/DoList。不能仅以未进入帧 CRC 路径推导联机安全。
- 包里的 `houseBeaconId` 是一个字节，收端以 `movsx` 解码，但**字节宽度不是上限为 3 的原因**。
  原版收端没有槽号边界校验，仍按 `house*3+id` 访问固定数组：
  单侧发送 `id=3` 会写进下一家的 0 号槽，`house==7` 时则踩到
  `0x89C410 AllocatedCount`，造成串槽或内存破坏。
- 因此，**要兼容未修改的对端，就不能把共享信标直接扩成每家 4 槽以上**。
  全部客户端统一修改布局/协议并非技术上不可能，但不属于单侧兼容增强；
  额外的纯本地自绘标记也不等于增加队友可见的共享容量。
- 联机复用 `0..2` 槽满后轮换，不改变包格式和槽号范围；单机池化可以独立处理，
  见第十三、十四节。轮换仍需记录顺序和正确的装钩依赖，并非只改两处判满就完整。

## 九、包格式（顺带订正）

`push 0x3D` 是**包长 61 字节**，不是包类型；类型是缓冲区首 dword：

| 动作 | 首 dword | 包长 | 发送点 |
|---|---|---|---|
| 放置 | `0x20` | `0x3D` | `0x430D9F` / `0x430E41` |
| 删除 | `0x21` | `0x3D` | `0x431367` / `0x4313E9` |
| 改文字 | `0x22` | `0x1C7` | `0x43153F` / `0x431632` |

接收端派发 `0x48D1E0`：`type` @ `[0xA8D638]`，`lea eax,[ecx-0xA]; cmp eax,0x25; ja default`
→ 字节表 `0x48DB44` → 13 项 dword 表 `0x48DB10`：
`0x20→idx6→0x48D798`（坐标 `[0xA8D667/66B/66F]`，
`id=[0xA8D673]`、`house=[0xA8D674]`，两者按有符号字节扩展后传给 `PlaceBeacon`）、
`0x21→idx7→0x48D7D5`（`DeleteBeacon`）、`0x22→idx8→0x48D7F4`（`EditBeaconMessage`）。

## 十、实现（BeaconSP.cpp）

每轮实时读取 GameMode：仅 Campaign(0)/Skirmish(5) 请求单机功能，
`OU_IsMP()` 的 LAN(3)/Internet(4) 用于联机替换路径；不把其他模式笼统当作单机。
按组懒装/卸钩，分三组（`BS_SCOPE_*`）：

| 站点 | 长度 | 原字节 | 落点 | 作用 | 组 |
|---|---|---|---|---|---|
| `0x5370A0` | 5 | `a1 38 b2 a8 00` | `0x5370AE` | B 键布署开关 | SP |
| `0x430D99` | 6 | `8b 0d 78 da a8 00` | `0x430E50` | 跳过组包/广播，直接收尾 | SP |
| `0x430CD4` | 5 | `a1 38 b2 a8 00` | `0x430CEA` | EVA + 两条操作提示（顺带记槽号） | NOTE |
| `0x430F4A` | 5 | `32 c0 c2 04 00` | 直接 `ret 4` | 满 3 也让 `CanPlaceBeacon` 返回 1 | SWAP |
| `0x430BD4` | 8 | `83 bc 24 f4 01 00 00 ff` | `0x430BE2` / `0x430F20` | 满了顶掉最旧（写回槽号让引擎自己覆盖） | SWAP |

- **SP**：只在单机装，`BeaconInSP=1` + 美术齐才请求启用，包含 hotkey/sendbuild 两处；
  再加 NOTE 的尾段才组成“单机也能放信标”所需的三处站点。
- **NOTE**：单机整套开 或 联机开着替换时装。`0x430CD4` 在单机同时负责跳过
  GameMode 早退（拿 EVA/提示），在联机只用来记槽序号。
- **SWAP**：`BeaconAutoReplace=1` 时装，单机还要求 SP 那组可用；两个站点必须成对。

五处覆盖的原指令均无相对地址操作数。尾壳会调用序号记录函数，替换壳会调用挑槽函数，
所以不能说“不碰寄存器”；其正确性依赖被覆盖指令重放及后继活跃值分析。
已核对的编译产物中，辅助函数保存 callee-saved 寄存器，`eax/ecx/edx` 等易失寄存器
在后继路径中被重定义，未发现明确的活跃寄存器破坏。

失败时必须区分“壳的开关关闭、执行原版语义”与“站点字节已恢复”。
`BS_Group` 任一站点失败时会调用 `BS_Uninstall` 撤下本组仍由本模块持有的钩子；
已放弃（state=2）的组不反复安装。字节恢复仍以站点所有权及内存保护操作成功为前提，
不能无条件承诺恢复完成。跨组按实际成功结果联锁，不能只依据配置意愿放行。

配置 `[Features] BeaconInSP` / `BeaconAutoReplace`（缺失=1，改后重启）。

信标讯息的输入依赖 `[MsgText] ChatBoxSP=1`（默认开）：`0x55E477` 那道 session
检查是 `ChatBoxSP` 在管，关掉它单人连回车都进不了信标讯息分支。
放信标本身、EVA、两条操作提示不依赖它。

### 美术 / 动画周期闸门

`+0x64/68/6C` = BeaconSize(X,Y) + 帧数，`+0x70/74/78/7C` = RadarBeaconSize(X,Y) + 帧数 + 周期，
全部由 `LoadArt 0x4309D0` 从 SHP 头部 `[+2]/[+4]/[+6]` 填。它的唯一调用点 `0x687BB2` 属
**联机开局流程**，单机不走 ⇒ 两个 SHP 指针和 `+0x7C` 都停在静态构造的 0。

三处 `idiv` 全在 `AllocatedCount != 0` 之后，原版单机永远走不到，一能放信标就立刻除零
（`0xC0000094`，`eip=0x4318B6`，现场 `AllocatedCount=1`）：

| 指令 | 地址 | 前置 |
|---|---|---|
| `idiv [ecx+0x7C]` | `0x431718` | `0x431700 DrawRadar`，`[ecx+0x60] != 0` |
| `idiv [ecx+0x7C]` | `0x4318B6` | `0x431800`，`[ecx+0x60] != 0` |
| `idiv [0x89C42C]` | `0x430659` | `0x430650` 单信标绘制 |

所以启用前先过闸门：仅 Campaign/Skirmish 且 `BeaconInSP=1` 时允许补调；
单机两个指针都空时补调一次 `LoadArt`（只一次，它不释放旧缓冲），
然后要求 `PBEACON` 指针、`RDRBEACN` 指针、`+0x7C` 三者都非 0，否则**拒绝启用**并记一行日志 ——
空 SHP 指针进 `0x430250` 一样会崩。补调后 `period=32 / w=66 / f=20`。
联机不补调（引擎开局会自己读，重复调用会漏一份缓冲），只查。

### 装钩顺序

`PowerDrawBoth` 先调用 `BeaconCap_Poll`、再调用 `BeaconSP_Poll`，
让同一轮序号管理读取到已更新的池化状态。

SP 轮询先将 `g_BsSpOn / g_BsNoteOn / g_BsSwapOn` 全部置 0，再处理安装/卸载；
其间现存壳执行原版语义。SP 实际成功后才请求单机 NOTE，NOTE 失败则卸下单机 SP；
SWAP 还要求 NOTE 成功且 `(mp || sp)` 成立，最后才发布各运行门控。
这些门控不是字节恢复完成标记，失败时仍按前述站点所有权/保护条件处理。

替换停用、槽数语义改变或帧号回退（场景重开）时清空序号表，
避免把上一局或原布局的序号套到当前槽位。

## 十三、满了自动替换最旧（BeaconAutoReplace）

目标：达到容量后再确认放置，自动顶掉最旧那个，不必先手动删。
联机容量仍是 3；单机容量取第十四节的池化配置。
功能用于单机和联机，联机不额外发删除包：它复用原生指定槽覆盖及放置广播路径。
“本地和远端经过同一段引擎代码”只是路径证据，不单独构成联机安全证明。

### 两处判满

```
CanPlaceBeacon 0x430F30              ; 唯一调用方 SetPlaceBeaconMode 0x4AC9AD
  0x430F45  cmp eax,3 / jl 循环
  0x430F4A  32 c0            xor al,al     ← 满: 返回 0
  0x430F4C  c2 04 00         ret 4
  0x430F4F  b0 01            mov al,1      ← 有空槽: 返回 1
```
满时 `SetPlaceBeaconMode` 只是 `xor bl,bl`（`0x4AC9B6`），无提示无音效 ——
所以原版满 3 个按 B 是“毫无反应”。改 `0x430F4A` 那 5 字节为返回 1 即可进布署模式。

```
PlaceBeacon 0x430BA0
  0x430BBE  xor ecx,ecx                  ; 扫槽入口（ecx=槽号, eax=槽指针, edi=本家槽首）
  0x430BC6  循环找空槽, 满则往下
  0x430BD4  83 bc 24 f4 01 00 00 ff  cmp [esp+0x1F4],-1   ; 8 字节, [esp+0x1F4]=id 参数
  0x430BDC  0f 84 3e 03 00 00        je  0x430F20         ; id==-1 → 放弃
  0x430BE2  分配 0x114 …
  0x430C2C  mov eax,[esp+0x1F4]
  0x430C33  cmp eax,-1
  0x430C36  0f 85 21 02 00 00        jne 0x430E5D         ; id!=-1 → “按 id 覆盖指定槽”
```
注：`0x430BDC` 是那条 `je` 本身，越过它的落点是 **`0x430BE2`**（分配对象）。

### 关键：0x430E5D 那段就是“覆盖”

```
0x430E5D  lea eax,[eax+ebx*2]            ; eax=id+house*2
0x430E60  mov ecx,ebx
0x430E62  add ecx,eax                   ; ecx=house*3+id
0x430E64  old = Beacons[ecx]
0x430E6E  old==NULL ? 跳到0x430E80
0x430E70..0x430E7D  operator delete(old), AllocatedCount--
0x430E80  Beacons[ecx对应的槽] = 新对象
0x430E82  jmp 0x430C76                  ; 公共尾：坐标/HouseID/可见位/Count++/CD4
; CEA按是否本家分流：本家进入EVA/组包，非本家进入侦察提示；并非远端再次广播
```

这段原本只有**收到远端放置包**时才走（`id` 来自包里的 `houseBeaconId` 字节）。
所以只要让 id 不再是 -1，就能复用整条“释放旧对象 + 装新的 + 广播这个 id”的流程。

### 壳的行为（只挂 0x430BD4 一处）

| 条件 | 去向 |
|---|---|
| 功能关 | 重放 `cmp` 语义：id==-1 → `0x430F20`，否则 `0x430BE2` |
| 功能开 + id≠-1（远端包） | `0x430BE2`（原版路径，绝不改 id） |
| 功能开 + id==-1 + 挑到槽 | **把槽号写回 `[esp+0x1F4]`** → `0x430BE2` |
| 功能开 + id==-1 + 无槽可挑 | `0x430F20`（原版放弃，理论上不会） |

写回后 `0x430C2C` 读到的 id 已是那个槽号，`0x430C36` 自然跳到 `0x430E5D`：
释放该槽旧信标、装新的；本家放置随后进入 `0x430D99`，广播中的 `houseBeaconId` 也是这一槽。
对端收到后可走原生同槽覆盖。这里修改的是信标/UI 状态，并复用独立的原生 IPX 消息，
不是单位模拟命令，也不是 Mega/Connect/Commit 事件。
**不得把这条 UI 路径当成其他模拟变更绕过标准事件广播的先例**；
同段引擎代码、未见 CRC 更新均不单独证明联机安全。

### 为什么不用 DeleteBeacon

`DeleteBeacon 0x4311C0`（thiscall / `ret 8`）区分指定槽删除与删除本地选中项：
`(-1,-1)` 表示后者，**不是删全部**。明确传入 `(house,slot)` 的路径不会发出原生删除广播，
所以不能在联机仅本地调用它来腾槽。

也存在可用的广播删除方案：Phobos `src/Ext/House/Hooks.cpp` 的
`MouseClass_ToggleBeaconMode_AllUsed` 先 `UnselectAll()`、给目标信标置选中位，
再调 `DeleteBeacon(-1,-1)`，以触发原生 IPX 删除消息。
本实现选同槽覆盖，是为了到落点确认时才替换，并且不额外发送删除包；
不是因为原生删除入口完全不能用于广播。Phobos 方案在进入布署模式时已删除，取消布署也不会恢复旧信标。

被顶掉的信标不保留任何东西：`Text[128]` 一起没了，这点无法回避。

### “最旧”怎么定

槽里没有时间戳，自己记：`0x430CD4` 那一刻 `ebx` 仍是 houseId、
`[esp+0x1F4]` 仍是刚写入的槽号，在已有的尾壳里顺手记 `ts[slot] = ++seq`（只记本家）。
挑序号最小的槽；`ts==0`（补丁装上之前放的）一律当最旧。槽删空后 ts 不清 ——
空槽不参与比较，再放进来会被重新记一次，所以“手动删 A 再放 D”之后不会把 D 当成最旧。

`0x430CD4` 这个壳联机也需要挂：自己放置和远端指定槽覆盖都会经过它，
但 `Bc_NoteSlot` 只记录 house 等于当前玩家的放置。没有记录钩子时，时间戳保持为 0，
挑槽会反复选第一个占用槽，而非可靠地选择最旧项；因此替换门控必须依赖记录钩子实际就绪。

### 联机的边界

- 静态兼容性依据：在槽号保持 `0..2` 时，未修改对端已有 `0x430E5D` 同槽覆盖分支，
  无需新增包类型即可处理替换消息。这支持原版对端兼容的设计，但本轮未做混合客户端实测。
- 从覆盖逻辑可推导：若一条放置消息未送达，对端可能保留旧槽内容；
  后续同槽放置若成功送达，可再次覆盖该槽。这不是丢包/重排/重传行为的实测结论，
  不能据此承诺网络异常只影响一个信标或与原版可靠性完全相同。
- 观战时把开关按回原版（钩子留着不装卸，避免抖动）：否则观战者满 3 再点一下
  就会顶掉被观战玩家的信标，并按人家的名义广播。
- `AllocatedCount` 守恒：释放（-1）与公共尾的 `++` 在同一次调用里配平。

### 日志

```
beaconsp: BeaconInSP=1 BeaconAutoReplace=1   启动时读到的配置
beaconsp: state sp=1 swap=1 sp               生效状态（变化时才记；mp 表示联机）
beaconsp: canfull hook ON                    两处站点各自装钩
beaconsp: swapfull hook ON
beaconsp: swap h=0 slot=1 seq=7              每次替换（house / 挑中的槽 / 它的序号）
```

### 配置

`[Features] BeaconAutoReplace`（缺失=1，改后重启）。单机还要求 `BeaconInSP=1` 且美术齐；
联机仍要求美术和记录钩子就绪。两处判满站点必须成对：只装 canfull 会“B 键进得去却点不下去”，
只装 swapfull 则满 3 时根本进不了布署模式。失败回滚和跨组门控见第十节；
恢复字节是否完成还取决于站点仍由本模块持有及内存保护操作成功，不能只凭配置意愿断言。

## 十四、单机数量上限（BeaconLimit）

联机保持每玩家 3 个（原版收端固定 `house*3+id` 寻址，单侧加格会串槽或越界）；
单机把 8 个玩家的槽**合并成一个池子**，总量可到 24（整个数组）。

### 为什么不是 128

`Beacons[8][3]` 位于 `0x89C3B0` 起 **96 字节**，紧跟 `+0x60 AllocatedCount`
和 `+0x64..+0x7C` 的尺寸/动画字段；管理器对象到 `+0x80` 即结束。
更后的坐标模板、美术指针等是已被使用的旁挂全局，不是可随意覆盖的空地，也不能据此
把对象大小解释为 `0x1B8`。所以扩到 128 不能只增加循环常量或继续占用相邻地址。

现有数组访问以 `this` 为基址，混合 `house*3+slot` 寻址，涉及分配、选择、查询、
编辑、删除、绘制和清理。要搬到自建数组或接管入口，仍须逐条审计所有访问及生命周期，
不能保证“一处重定向”就能完成。24 是复用当前指针数组、不增加存储容量的池化上限，
不是引擎在任何改造方案下都不可突破的理论上限。

### 池化怎么做

物理索引从 `house*3+slot` 改为全局 `slot`，但对象 `HouseID` 保留真实归属。
`BeaconCap.cpp` 共 **29 个事务站点**：28 处原地寻址/常量改写，另有 1 处 DeleteAll 入口 E9 包装。

| 组 | 处数 | 作用 |
|---|---|---|
| `Z1..Z6/Z9/Z10/Z11/Z13/Z14` | 11 | 去掉定址中的 house 分段，保留 slot 和真实 owner |
| `L1..L3` | 3 | 放置扫槽及判满界改为 `BeaconLimit` |
| `L4..L8/L10..L12` | 8 | 有 house 语义的查询/删改等遍历扫描 24 槽 |
| `H4/H6..H9/H11` | 6 | 配套 house 外循环只跑一段 |
| `DeleteAll` | 1 | `0x431410` 入口 6 字节跳转，按对象 HouseID 删除指定玩家的信标 |

关键寻址不能机械清零：
- `Z2/Z3`、`Z4/Z5` 配套保留槽号、移除 house 偏移；
- `Z9/Z13` 清 `eax` 中的 house，保留 `ecx/edx` 中的 slot；
- `Z11` 将 `0x43131B` 起的 `lea/mov/add` 共 7 字节改为 `mov edx,ebx` 加 NOP，
  直接以 `ebx=slot` 清槽，并保留 `ecx=owner`；不能释放 slot N 后误清 owner 对应的槽。

析构、Reset、取消选择、普通绘制、雷达绘制本来就按连续指针扫描完整 `8×3=24` 格，
池化仍用同一数组，因此保留这五对原生 M/H 循环，不必改成 `1×24`。
点选/坐标查询的外层 house 被限制为 0 后，其原生 `slot+house*3` 已等于 slot，
对应 `Z7/Z8` 也无需修改。共删除这 12 项冗余补丁；DeleteAll 另以一个入口包装替代两处 Z12/L9 改写。

`DeleteAll` 包装仅在池化有效时接管，遍历 24 格并检查对象 `HouseID==house`，
再调用已池化的 `DeleteBeacon(house,slot)`；不递归调用 DeleteAll，也不把共享池全部删掉。
停用时入口壳重放原序言，返回原函数。

**不改的**：`0x430CB6 cmp ebx,8` 是 house 合法性判断，不是循环界。
缩小它会使非 0 玩家信标漏写 `HouseID`；真实归属是颜色、可见性和按家删除的依据。

### 与"替换最旧"的交互

池化后所有玩家的信标同在一个池子，`Bc_PickOldest` 不能再按 `house*3+i` 取，
改为扫 `slot 0..BeaconLimit-1` 并**按对象里的 HouseID（+0x110）过滤出本家的**，
否则会顶掉别人的信标。槽数由 `BeaconCap_SlotCount()` 给出（池化生效=BeaconLimit，
否则=3）；槽数一变就清空序号表，否则联机会拿着单机池的旧序号去挑本家那 3 格。

### 配置与日志

`[Features] BeaconLimit` 默认 24，范围 **3..24**，越界钳制到此范围。
3 保留原版每玩家 3 槽；4..24 是单机共享池总量，改后重启；联机共享容量恒为每家 3。
池化仅在 Campaign/Skirmish、`BeaconInSP=1`、帧数达到门槛且原 24 格指针全空时首次安装，
不能把已有原版 house 分段布局直接重新解释为池化布局。

```
beaconcap: BeaconLimit=24 (sp only)
beaconcap: ON limit=24 (pooled, sp)
beaconcap: install failed - OFF (vanilla limit)
beaconcap: protection restore failed - retrying
beaconcap: restore failed - pooled state retained, retrying
beaconcap: restored (vanilla 3/house)
beaconsp: slots 3 -> 24
```

### 字节事务与布局切换

安装/恢复都先校验全部站点的预期状态、再全部解锁，全部成功后才改写字节；
校验或解锁失败不留下半套寻址补丁。包含 DeleteAll E9 在内的 29 处属于同一事务。
同页多次解锁会记录到中间 RWX 状态，因此页保护按**逆序**恢复；
恢复失败保留原保护记录到后续轮询重试，保护事务未完成时不开始新字节事务。

退出池化布局前，若仍有信标，先调用原生线性 `Reset` 清空本地信标 UI，再恢复原字节，
避免全局 slot 被原版重新当作其他玩家的 3 格分段。正常跨局已经空池时不重复 Reset。
此清理不操作单位模拟、不发信标广播；不应推广为联机本地修改模拟状态的许可。
若恢复事务失败则保留池化状态并重试，不谎报已经回到原版布局。

### 证据与限制

- 各玩家若产生信标，会占用同一单机池；总量不是每家各有 `BeaconLimit` 个。
- 原生信标不保存的依据见第七节 Phobos 注释；不是只有扩容部分不保存，本轮未另做存读档实测。
- 单机 h0 放置并轮换 slot 0..23 的已有日志，只支持该路径曾运行；修正后的点选、删改、
  按 HouseID 清理及模式切换仍须针对性实际验证，不能由日志自动认定全部通过。
- 池化不在联机新装；正常恢复成功后，29 处池化站点回到校验的原字节。
  BeaconSP 的联机替换钩子仍可能启用，因此不能宣称整个信标模块联机“字节零改动”。
