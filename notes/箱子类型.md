# 箱子类型调查与显示方案

（所有地址均来自 gamemd.exe 反汇编实证）

## 0. 结论速览

1. 箱子内容 = **一个字节**：`CellClass + 0x11E`（YRpp 里叫 `OverlayData`，注释就是
   "The crate type on this cell"）。取值 0~18 = 固定类型，**≥19（运行时放的都是 0xFF）=
   没定，拾取那一瞬间才按权重 roll**。
2. 所以**联机/单机随机刷出来的箱子，在拾取前根本没有"类型"这个东西**，读不到。
   想显示确定内容，必须先让它有类型 = 改变随机流程（见 §5 方案 B）。
3. 能只读显示的只有两类：地图里预置的箱子（OverlayData 来自地图 OverlayDataPack），
   以及被我们自己定了型的箱子。剩下的只能显示"概率表"。
4. 类型共 19 种，但真正有代码处理的 16 种；`Invulnerability(13)` / `IonStorm(15)` /
   `Pod(18)` 引擎里只有动画没有效果。

## 1. 类型存在哪 / 谁读它

`CellClass::CollectCrate(FootClass*)` = `0x481A00`（YRpp 同名）。顺序：

```
0x481A1C  overlayIdx = cell->OverlayTypeIndex        (+0x44)
0x481A31  if (!OverlayTypes[overlayIdx]->Crate) return false   (+0x2AA = Crate 标记)
0x481AC8  idx = cell->OverlayData                    (+0x11E)
0x481ACE  if (idx >= 0x13)  → 按权重 roll（消耗共享 RNG）
0x481B2B  if (GameMode == 0 && cell->OverlayData == 0) → 按箱子图像类覆盖
0x481D52  if (cell->LandType == 2 /*Water*/ && !enabled[idx]) → idx = 0
0x481DB8  if (idx == 6) idx = 0                       /* Squad 实际算资金 */
0x481DDC  switch (idx) 跳 0x4833C4 表（0~17）
```

- 权重表 `0x81DA8C[19]`(int)，动画表 `0x81DAD8[19]`(AnimType 索引, -1=无)，
  参数表 `0x89EC28[19]`(double，钱数 / 倍率 / 伤害)，开关表 `0x89ECC0[19]`(byte，
  **含义是"允许出现在水上"**，水上格且为 0 时强制成 0=资金)。
  这四张表是全局变量（不是 RulesClass 成员），随存档一起序列化（`0x67F940` 起）。
- 名称→索引的权威表：`0x7E523C[19]`（`[Powerups]` 解析器 `0x673EA2` 按这个顺序循环）。
- 权重 roll：`0x481AF0` `Random::RandomRanged(1, 总权重)` 后累加比对
  （`0x65C7E0`，RNG 在 `0xA8B230 + 0x218`）。**这一步消耗全局共享 RNG。**

## 3. 运行时放箱子 = 一定"未定"

`CellClass::PlaceOverlay`（`0x5FD060` 起）：

```
0x5FD0B2  cell->OverlayTypeIndex = idx
0x5FD0CC  cell->OverlayData = 0            (普通 overlay)
...
0x5FD105  mov byte [ebp+0x11E], 0xFF       (OverlayTypes[idx]->Crate != 0 时)
```

即：**只要是箱子，运行时放下去一律 0xFF**。`MapClass::PlaceRandomCrate`（`0x56BD40`）
→ 256 槽箱子表（`MapClass+0x158`，每槽 0x10 字节：+0 生成帧、+8 寿命、+0xC 格坐标）
→ 放 overlay → 0xFF。只有地图文件里的 `OverlayDataPack` 能带预设值。

## 4. 战役里的图像类覆盖（只在 GameMode==0 且字节==0 时）

```
if (overlayType == Rules.CrateImg      /*+0xFC*/) idx = Rules.SilverCrate /*+0x1464*/
else if (overlayType == Rules.WoodCrateImg /*+0xF8*/) idx = Rules.WoodCrate /*+0x1468*/
else if (overlayType == Rules.WaterCrateImg /*+0x100*/) idx = Rules.WaterCrate /*+0x146C*/
```

MO 的 `WoodCrateImg=CRATE` 与 `CrateImg=CRATE` 是**同一个 overlay**，
比较顺序里 `CrateImg` 在前 ⇒ 战役地图上普通的 CRATE 走 **SilverCrate=HealBase（维修）**，
`WoodCrate=Money` 实际到不了。显示端要照抄这段逻辑，否则战役里会显示错。

## 5. 显示方案

### 方案 A（只读，零风险，建议先做）

- 触发：鼠标所在格（`OU_MouseCell`）是箱子 → 在格上方画一行标签。
- 内容分两种：
  - 字节 < 19（地图预置 / 我们定过型）：显示确定类型（含 §4 图像类补正、§1 水上补正）。
  - 字节 ≥ 19：显示 `?` + 全表概率（`0x81DA8C` 权重 + `0x89ECC0` 水上开关，实时算，
    地图换了 `[Powerups]` 也自动跟着变）。
- 成本：一格一次读内存 + 一行矢量文本，可忽略。
- 缺点：随机箱子看不到确定内容（物理上不可能，见 §0）。

### 方案 B（让箱子先有类型，才谈得上"显示箱子类型"）

在 `0x5FD105`（7 字节 `C6 85 1E 01 00 00 FF`）挂钩，把 0xFF 换成我们自己按权重选的
索引，返回 `0x5FD112`。写进 `CellClass+0x11E` 之后：

- 引擎自己就当"固定类型"用，拾取处不需要再挂钩；
- 存档/读档自动带上（OverlayData 属于 CellClass，随地图存）；
- 不需要自建表、不需要额外同步事件。

选型两种：

- **B1 用共享 RNG**（和引擎同表同算法）：所有客户端结果一致，但会改变全局随机数流
  （AI/动画/其它系统全部跟着错位）——对"体验优化"类 mod 影响面过大。
- **B2 自算 hash**（`hash(格坐标, 生成帧)` 再按权重取档）：**完全不碰共享 RNG**，
  各端独立算出同一个结果，对原版随机性零影响。推荐。

联机：按项目铁律，先只对 `GameMode 0/5`（战役、单机遭遇战）启用；`3/4`（LAN/Internet）
不挂钩。若将来要放开，前提是确认"箱子生成在每一端都执行同一路径"，且各端 DLL 一致。

### 方案 C（纯提示，不做 B）

悬停只显示概率表。适合"不想动任何玩法"的场合。

### 绘制落点

- 取格 → 屏：`CoordsToClient`(0x5B1A00 一类) + `SB_ViewToScreen`，Z 用
  `OU_CellFloorZ` / `CellClass::GetFloorHeight`；写法照抄 `gui/GridView.cpp:GV_ProjCorner`。
- 文本走 `VecText`（同 `preview/*`、`gui/GridView`）；图标可选：`[Powerups]` 第 2 字段
  的 AnimType 图像（要先确认这些 SHP 是单帧图标，见 §7）。
- 常显 vs 悬停：常显要遍历视口内所有格子（`OverlayTypeIndex != -1` 且
  `OverlayTypes[i]->Crate`），`CrateMaximum` 最大 255，屏上几十个时矢量文本会吃不消，
  建议常显只画图标、文字只在悬停时画。

### 真正的来源：触发动作 108 CreateCrate（61 张图 / 549 次）

编辑器数据 `G:\地图编辑器\FA2SP_HDM_Edition_1.5.0_MentalOmega\FAData_TriggerAndScript.ini`：
`108=Create Goodie Crate at...,0,31,...`（第 2 个参数类型 31 = `Crate type`，枚举就是 `[Chinese-CrateTypes]` 的 0~17）。
对照 `17=Reveal around Waypoint...,0,30,...`：这类动作的第 2 参数才是主参数（地图里动作 17 的路点确实写在**第 2 位**）。

引擎侧一致：
- 动作分派 `0x6DD8E7 jmp [edx*4+0x6DFDEC]`，**索引 = 动作号-1**（别再用 0x6DFDEC+108*4）。
- 动作 108 的处理在 `0x6DF69B`：`[esi+0x44]` 当路点、`[esi+0x90]` 当内容，调 `MapClass::PlacePowerupCrate`（`0x56BEC0`）。
  `0x56BFF9 mov [eax+0x11E], dl` 把内容写进格子；内容 == `0x14` 时**不写**（留给 0xFF = 随机）。
- 动作 17 的工作函数 `0x6E0FE0` 读的也是 `[ecx+0x90]` 当路点 → 第 2 参数 ↔ `+0x90`。

全库 549 个动作 108 的内容分布（第 1 参数路点全是 0，即玩家起始路点）：

| 类型 | 内容 | 次数 | 地图数 |
|---|---|---|---|
| 6 | 金钱(随机) | 260 | 40（其中 22 张 Challenge 用同一份 8 连模板） |
| 2 | 医疗 | 88 | 16 |
| 14 | 升级 | 63 | 19 |
| 9 | 防御力强化 | 40 | 16 |
| 0 | 大量金钱(固定值) | 37 | 7 |
| 11 | 火力强化 | 29 | 14 |
| 10 | 速度强化 | 25 | 14 |
| 12 | 一次核弹 | 4 | 2 |
| 7 | 重置黑幕 | 1 | 1 |
| 8 | 显示全图 | 1 | 1 |

没被用到的：1 随机单位、3 隐形、4 爆炸、5 大型爆炸、13 空、16 毒气、17 一片矿。

### 预设字节为什么会留在格子里

读图函数（`0x5FD3F6` 起）跑两遍：
1. 第一遍按 OverlayPack 建 OverlayClass，`PlaceOverlay` 在 `0x5FD105` 先写 `0xFF`（桥 0x18/0x19/0xED/0xEE 除外，保留旧值）。
2. 第二遍（`0x5FD5FB`~`0x5FD640`）再读 OverlayDataPack，`0x5FD640 mov [eax+0x11E], dl` **逐格无条件**覆盖。

所以预设箱子的类型字节是地图说了算，`CollectCrate` 直接拿它当类型（`0x481ACE cmp bl,0x13`）。

### 两个只影响"字节 0 / 字节 6"的坑

- **字节 6 恒等于 0**：`0x481DB8` 有 `cmp ebx,6 / jne / xor ebx,ebx`，类型 6 在分派前就被改成 0。
  想让地图作者写 6 得到"随机金额"是无效的。
- **GM 0 且字节 0 时还要过图像映射**（`0x481B58`~`0x481B94`，顺序 CrateImg → WoodCrateImg → WaterCrateImg，后者覆盖前者）：
  MO 的 `CrateImg=CRATE → SilverCrate=HealBase`、`WoodCrateImg=CRATE → WoodCrate=Money` 同时命中 CRATE，
  最终取 **WoodCrate=Money**；`WCRATE → WaterCrate=Money`。
  也就是说 MO 里字节 0 永远是金钱箱，不会变成旧结论里的 HealBase。字节 1~18 不过这道映射，直接生效。

### 不在"预设格子"里的另一类

61 张图的触发器动作 108（CreateCrate，`549` 次）会在开局往 waypoint 放箱子，参数第 1 位全是 0。
那是运行时创建，落格后同样写 `+0x11E`，但不算预设；战役图在 mix 里，未统计。

### 判读要点

- `[Triggers]` 格式 `ID=国家,关联触发,名称,是否禁用,简单,中等,困难,重复类型`，**第 4 字段 1 = 开局禁用**。
  验证依据：coop_asarin 里所有第 4 字段为 1 的触发器，正好是被动作 53（Enable Trigger，写法 `53,2,<触发ID>`）点名的那些。
  f_skymountain 的两条箱子触发器都是 1，且全图没有任何 53/54/22 动作 → 永远不会触发。
- 时间类事件（13）**不需要把标签挂到具体对象上**也会跑：c_aberration 等 22 张挑战图的 `[Start] Crates` 标签
  （01000176）同样只出现在 `[Tags]` 里，实测开局照出 8 个箱子。所以"标签孤儿"只对对象事件（7/48）致命。
- 事件 7 = 被任意**所属方**摧毁（友伤/附带伤害不算），事件 48 = 被任意方式摧毁。想拿核弹必须自己动手炸掉地标建筑。
- 两张图的地标都叫得出名字：Smithsonian Castle / Movie Theater / Alcatraz Lighthouse，`Strength=1000`，不设防，一炮就碎。
- f_skymountain 那两条大概是作者做完又关掉的遗留（名字还是 `_Small objects_1/2` 这种占位名）。

| 15 IonStorm | IonStorm | DEMTEXPC | **DEMTEXP.SHP** | `Image=DEMTEXP`，毒气爆炸 |

**11 种有现成图像，8 种没有。** 所有 artmo 段都只有 `Rate=400 / UseNormalLight=yes`，没有 `LoopCount`，
artmo 的注释也自带 `; crate armor / crate money / crate heal base / crate toxic bomb / crate iron curtain` 等，
确认它们就是箱子拾取动画。

### 引擎侧对照（`CellClass::CollectCrate`）

- 分派表 `0x4833C4` 按类型取 handler，`0x4832F5` 是**只播动画**的分支，类型 **6 / 13 / 15** 直接指向它。
- 该分支：`cmp dword [ecx*4+0x81DAD8], -1 / je 跳过` → 取 `0x8B4154[idx]`（AnimTypeClass*）
  → `operator new(0x1C8)` + `0x421EA0`（AnimClass ctor）→ 在格子中心 `((x<<8)+0x80, (y<<8)+0x80, z+0xC8)` 建动画。
- **`0x81DAD8` 是"类型 → 动画索引"数组**（`-1` = 无动画 = ini 里的 `<none>`）。exe 里初值全 -1，rules 载入时填入。
  `0x81DA8C` 是权重数组（exe 初值是原版权重，会被 MO 的 `[Powerups]` 覆盖）。
- 结论：**13 的"无敌"效果其实来自动画自带武器** —— `[IRNCR]` 有 `Weapon=IronCrate / Damage=1 / DamageRadius=10 / Damage.Delay=3`，
  不是 CollectCrate 的 handler（handler 是空的）。`[DEMTEXPC]` 只有 `SpawnsParticle=VirusCloud1 / Report=MolebombDie`，纯视觉。

### 做 UI 时的取舍

- 有现成图的 11 种可以直接借 SHP；没图的 8 种要么自绘图标，要么统一用"问号/木箱"占位。
- 这些 SHP 都是原版素材，MO 没有覆盖（游戏目录散装只有 `shroud.shp` 一个，其余在 mix 内，未解包）。

## 11. 图标实现（src/gui/CrateIcon.cpp）

数据链只有两跳，和 `CellClass::CollectCrate` 读的是同一份：

```
CellClass +0x44 OverlayTypeIndex  →  OverlayTypes[Items 0xA83D84, Count 0xA83D90]
                                  →  OverlayTypeClass +0x2AA Crate (bool)
CellClass +0x11E OverlayData      →  类型字节 0~18 (0xFF = 未定型)
```

**不要用 `OverlayClass::Array` 反推箱子位置。** 覆盖物对象没有可靠的格子坐标：
构造 `0x5FC380` 里 `0x5FC4A5 test eax,eax / jne 跳过` —— 只有当 `0x47C550(cell)`
回 0 时才 `0x5F4EC0` 设 Location，否则 Location 停在 (0,0,0)。按对象坐标
`OU_GetCoords` 再 `>>8` 会把所有箱子塌到 (0,0)，读到那里的数据字节后全部被过滤，
列表恒为空（首版就是这么失效的，日志里连 `n=` 都打不出来）。

因此扫描改成**只扫视图区覆盖的格子**：`GV_ViewCellRect()`（GridView 新增导出，
四角反投影 + 2 格余量）→ 逐格 `OU_CellPtr` → 上面两跳。视野约 40×30 格，
200ms 重建一次，开销可忽略；拉远到超过 20000 格直接跳过（那时图标也看不清）。

判定规则：

- 类型字节 `>= 19`（即 0xFF）→ 不显示（随机箱子拾取时才 roll，本来就没有类型）。
- 16 / 17 / 18 → 没有图标；6 → 复用金钱图标（引擎 `0x481DB8` 把 6 改写成 0）。
- 图标贴图 `icon_crate_type.pcx`，216×50，9 列 2 行，单格 24×25，键色 `0xF81F`。

日志只有一行 `crateicon: on`（功能启用的标志，开关打开时也打）。

微调（实测）：投影点 `OU_ProjWorld` 不是木箱的视觉中心，图标需再左移 2px、上移 4px 才与木箱居中对齐
→ 常量 `CI_OFF_X=-2` / `CI_OFF_Y=-4`（`src/gui/CrateIcon.cpp`），改观感只动这两个。

### 画在哪一层

图标画在 **Composite**（`MsgDrawBody` 里、天气之后、`MOE_DrawUILayers` 之前），
`GtLock`/`GtUnlock` 成对取像素，每帧重画（Composite 每帧被引擎重铺）。

**不要往引擎的地图缓冲 `[0x87E8A4]` 里写。** 它是环形缓冲（滚图只改 `+0x10` 偏移），
而取址函数 `0x4114B0` 内部 `Lock(x,y)` 之后**立刻 `Unlock()`**，只在调用方已持锁时
返回的指针才有效。在自己的钩子里调它，拿到的是失效指针：

- 写不进去（屏幕上零像素）；
- 写坏堆，几百毫秒后崩在 `phase=blitsidebar`（`CRASH eip=exe+0x9810C`，`mov dx,[ecx+edx*2]` 读越界）。

### 黑幕下怎么画

散文件 `shroud.shp` 是否存在就是判据（原版黑幕打包在 mix 里，只有替换成半透明
黑幕的玩法才会在游戏根目录放这个文件；`PvpNotice.cpp` 也用它判"开了透明迷雾"）：

| 目录有 `shroud.shp` | 该格在黑幕下 | 画法 |
|---|---|---|
| 有 | 是 | 照画，RGB565 每通道右移一位（≈ 50% 亮度） |
| 有 | 否 | 照画，原色 |
| 无 | 是 | 不画（不透明黑幕整块盖死，画了也是零像素，还泄露位置） |
| 无 | 否 | 照画，原色 |

判定是否在黑幕下读 `CellClass+0x12C` 的 bit3（`CELL_SHROUD_REVEALED`）：未置 = 还在
黑幕下。`CellClass::Unshroud 0x4876F6 or al,0x18` 置位、`MapClass::Reshroud
0x577B48 and ecx,0xFFFFFFE7` 清位。这个结果在 `Ci_Init` 里只算一次并存日志
（`crateicon: on (half shroud)`），中途换文件需重开游戏。

### 黑幕与迷雾的状态位

| 状态 | 字段 | 判定 |
|---|---|---|
| 未探索（黑幕） | `CellClass+0x12C` bit3 | 未置 = 还在黑幕下（置位 = 已揭示） |
| 有雾（已探索、视线外） | `CellClass+0x140` bit1 | 未置 = 不在本方视野（本功能不看） |

- `CellClass::Unshroud` `0x4876F6 or al,0x18` 置 `+0x12C` 的 bit3|bit4；
  `MapClass::Reshroud` `0x577B48 and ecx,0xFFFFFFE7` 清 bit3|bit4，
  同一处 `0x577B4B and edx,0xFFFFFFFC` 清 `+0x140` 的 bit0|bit1。
- `ShroudClass::GetLevel 0x6D8700(coords*, layer)` 是引擎自己的判定：
  layer 0 走 `0x6D88F4 test byte [cell+0x12C],0x18` 再 `test al,8`（bit3 必须置）；
  layer 1 走 `0x6D8724 test byte [cell+0x140],3` 再 `test al,2`（bit1 必须置）。
  返回 `-1` = 不遮挡、`-2` = 全黑、其它 = 邻格未揭示方向的掩码（用来选 SHP 边角帧）。
- **不要调 `CellClass::IsShrouded 0x487950` / `MapClass::IsLocationShrouded 0x586360`**：
  内含 `idiv [0xABDE88]`（LevelHeight，镜像初值 0），载入期调用会除零。
