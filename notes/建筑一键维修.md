# 建筑一键维修（RepairAll）

原版修建筑 = 点维修图标（或按维修快捷键）进维修光标，再逐个点带血的建筑。
`[RepairAll] Mode` 三档：

| Mode | 行为 |
|---|---|
| 0 | 保持原样（本模块完全不介入） |
| 1 | 半自动，手动触发 |
| 2 | 自动修，定时扫，掉了血且还没在修的建筑自动进维修流程 |

**手动触发**（Mode=1/2 都行，`DoubleClick=0` 可只留 Ctrl 那两条）：

- Ctrl + 点维修图标 / Ctrl + 维修快捷键
- 双击维修图标 / 连按两下维修快捷键

四种都是"一键全修"，不新增键位。维修快捷键的 VK 从 `KeyboardMD.ini` 的
`[Hotkey] ToggleRepair` 读（默认 75 = `K`），玩家改键自动跟随。

> **Ctrl+维修快捷键必须自己轮询**：`Game::KeyboardProcess`（`0x55DEE0`）遇到修饰键
> 只按**精确组合键**查命令表（`0x55DF89` 起），而 `KeyboardMD.ini` 把
> `ToggleRepair` 只绑在裸 `K` 上；`ToggleRepariModeCommandClass::
> PreventCombinationOverride`（`0x535BD0`）恒 false，不会退回裸 K 命令。
> 于是 `0x536FA0` 的 Execute 根本不会被调用。现在由 `RepairAll_Poll` 每循环轮询
> `Ctrl && ToggleRepair` 的边沿补上（只读键态，触发后仍只发标准 Repair 事件），
> 并加了"聊天输入中不响应"与"游戏在前台"两道门。

## 触发点（`dist/MOExperience.dll.inj`）

| 地址 | 是什么 | 偷 | 吞掉时落点 |
|---|---|---|---|
| `0x536FA0` | `ToggleRepariModeCommandClass::Execute`（维修快捷键） | 7 | `0x536FAC`（`ret 4`）|
| `0x6A78D9` | 侧栏维修图标分支（只有 `eax==0x8065` 才走到） | 6 | `0x6A78FF`（`jmp 0x6A7A82` 公共尾）|

按钮音之后才是 `0x6A78F6 push -1 / mov ecx,esi / call 0x4AC8C0`，即
`MapClass::SetRepairMode`（`[0x87F7E8]+0x11B0` = RepairMode）。热键那边同形，
只是 `mov ecx,0x87F7E8` 写死。Phobos 的 PlayerAutoRepair 钩同两个点、返回同两个
落点；`Ares.dll` 与 `AutoLoad_nolog.dll` 都没有这两个点。

## 双击为什么只吞第二下

第一下必须放行（走原版，切维修光标），第二下才吞。反过来"其实是单击"时就没法补
维修光标状态了——补它得直调 `MapClass::SetRepairMode`，那是改模式状态，撞铁律。

所以**双击/连按的净效果 = 单击的维修光标切换（第一下）+ 一键全修**，单击行为不变。
Ctrl+点击则两下都吞（否则会进维修光标又马上退掉，还白 `UnselectAll` 一次）。

判定用**墙钟毫秒**（`GetTickCount`），间隔上限 `DblMs`（默认 400）：

- **不能用引擎帧号 `0xA8ED84`**：逻辑帧就是游戏速度，高帧率时 12 帧只有几十毫秒，
  而手动双击的两下间隔是 15~17 个逻辑帧，按帧判会全部落空。
- **图标**再比点位（`GtMouseGameXY`，侧栏区域同样有效），两点位移各 ≤ 12 游戏像素，
  顺带挡掉"维修→卖→维修"这种快速三连的误判。
- **快捷键**靠"两下之间松开过"排除按住不放的 OS 自动重复。
- 图标与快捷键**各存一份状态**（`s_RaDblBtn` / `s_RaDblKey`）：共用一份时快捷键那边
  不比点位，会与图标互相串成"多修一次/少修一次"。

## 联机（AGENTS.md 铁律）

唯一的模拟变更 = 往 OutList 塞标准事件 `EventType::Repair`（0x15），**照抄引擎自己
手点维修的那一段**（`0x4AC0BE`：`WhatAmI()==6` → `TargetClass 0x6E6AB0` →
`EventClass(house,0x15,id,rtti) 0x4C65E0` → OutList，house 取 `[0xA83D4C]+0x30`）。
真去改血的是各端自己的 `BuildingClass::Update`。钱照扣，与手点一致。

事件布局：`Type@0 / HouseIndex@2 / Frame@3 / Target@7（ID@7 + RTTI@11）`，共 111
字节。对象 RTTI=52(0x34)，但**不硬编码**，直接取 `TargetClass` 构造器产物。

### 事件是个"强制"原语

`IsBeingRepaired` 在全 exe **只有一处**写入：`ObjectClass::SetRepairState`
（`0x446FF0`，`BuildingClass` 虚表槽 `0x19C`，`-1`=翻转 / `0`=关 / `1`=开）。
三个调用点：`0x449C41` 拆除时关、`0x450708` 在 `0x450630` 那道门里（= "设置 IQ
自动维修"）、`0x4C6F01` Repair 事件处理。

事件处理（`0x4C6EFD`）只查 `IsAlive` 然后 `SetRepairState(-1)`——**没有资格判定、
没有扣钱**。所以事件一发引擎不再复查，直接开修；原版不让你修不可修的东西，靠的是
光标阶段根本不生成事件。由此三条硬约束：

- 资格必须自己判（见下"判定链"）；
- `SetRepairState(-1)` 是**翻转**，同一栋楼别发两条事件（`RA_Push` 按对象指针去重）；
- **发一次就够**：满血时引擎自己清 `+0x6E8`（`0x4508D0`），钱不够付下一步时也清
  （`0x4509B4`）。配套"已在修就不排队"，平时几乎不耗事件。

### 判定链

`RA_CanRepair`（槽 `0x94`）= 引擎"扳手光标显不显示"那句：
`Health>0 && Type->ClickRepairable && !vtable[0x80]() && 0x701140(this)`。
再加 `RA_MissionBusy`（槽 `0x184` 读 `[ecx+0xAC]`，排除 `Construction`/`Selling`）。
扫描与滴发两处都过这两关。

- **不能走"设置 IQ 自动维修"**（`0x450630 → 0x450708`）：本地直接写模拟内存、
  不发事件，正是铁律禁止的；且带房主级条件（`Owner+0x24C` vs `Rules+0x1444`），
  对人类玩家本就不成立。只能抄它的判定数据。
- **不能模拟鼠标**：点击判定走 `DisplayClass` 虚表 `+0x48`，而 `DecideAction`
  （`0x692610`）在有选中单位时转给**当前选中代表**的 `MouseOverObject`——结果依赖
  选中了什么，不能当逐建筑谓词。
- **类型类布局不可信**：`BuildingTypeClass::ClickRepairable` 真值 `+0x157A`
  （`0x452644` 实证），`tools/msvc-layout.ps1` 算出来是 `0xB7A`，正好差 `0xA00`。
  所以判定只问引擎，不自己抄那串关卡。

## 指针真伪与归属

`RA_IsObj` / `RA_VFn` 走 `MOE_InAnyModule`（落在任一模块内即算）——`IsPlausiblePtr`
只判 `[64K,2G)` + 4 对齐，堆/栈里随便一个数都能过；而 Ares 的虚表钩子会把虚表
（乃至钩子函数）复制进 `Ares.dll`，只认 exe 会把整张建筑表判成野指针。

归属只有一条：`TechnoClass::Owner` 指针**等于** `[0xA83D4C]`，在 `RA_StillWorth`
里逐栋比、不合就跳过。指针相等已足以保证"绝不修到别人家"，**不要**再要求"Owner
能在 `HouseClass::Array` 里查到"——那张表的地址/条数/`+0x30C` 在 Ares 下对不上时
会把整张建筑表判成非法。扫描范围是**整张表**，不抽样（地图预置的中立/民房排在
数组前面，玩家建筑可能在很后面）。

## 为什么还会"偶发无效"

前三条会让**一次点击完全没结果**，第四条是多修/少修：

1. **瞬态门**：`s_RaStable < 2`（建筑数组 items/count 连续 3 帧不变）最易撞，
   全图任何一栋楼建成或被打掉都会打回 1，交战时是常态。现在 `RA_Scan` 回"没扫的
   原因"，Poll 保留 `s_RaPending` 每帧重试（`RA_PEND_MAX` = 30 帧，约 0.5~1 秒），
   攒满才放弃并记一行。
2. **引擎自己会把维修旗标关掉（钱不够）**：`BuildingClass::Update` 的维修步每 N 个
   逻辑帧一步（`0x450821` 取 `[0x8871E0]+0x16E0` 乘常量后当除数），每步先算单步
   花费再比可用资金：`0x450896 jl 0x4509B4` → 直接把 `+0x6E8` 清 0。一次点亮几十
   栋、资金不够覆盖后续步骤时，排在后面的会被引擎按顺序自己关掉。这是原版经济
   规则，表现就是"点了全修，只有一部分真在修"。
3. **帧号倒退**：`Mode=2` 判据是 `fr - s_RaLastScan >= Interval`，而 `0xA8ED84`
   每局从 0 重数（新开/读档都倒退）。`s_RaLastScan` 是进程级静态，带着上一局的帧数
   时差值恒为负 → 自动修再也不触发。现在 Poll 里 `fr < 上一帧` 即 `RA_NewGame()`：
   清队列（上一局的指针会被 `RA_Drain` 解引用）、复位稳定门/`s_RaLastScan`/双击状态。
   （`Aggressive.cpp` 的 `fr - s_AgLastScan` 是同一写法、同一毛病，尚未处理。）
4. **同楼两条事件**：见上"翻转"，已由 `RA_Push` 去重解决。

| 字段 | 偏移 | 证据 |

## 铁律

- 钩子里只读键态/置标志，全图扫描一律挪到 `RepairAll_Poll` 的正常帧上下文。
- 每帧路径上不许 `GetPrivateProfileIntA`：配置全部在 `RA_EnsureInit` 读一次；
  `0x4F42F0` 一帧跑 ~142 次（SWSBar 实测），故 Poll 内自门控帧号。
- 联机判据/只读查询随便用，唯一写入是那条 Repair 事件。

## 日志

低频，`repairall: ` 前缀，只有三处：

```
mode=.. interval=.. batch=.. dbl=../..ms vk=..   // 启动一行, vk 便于确认改键被读到
mode=..                                          // 设置页改 Mode 时一行
scan give up: stable|moving|qfull|noplayer       // 手动触发重试用尽才记
```

报"没反应"时：只有启动行 = 触发链路没进来；出现 `scan give up` = 扫描被瞬态门拦住；
都没问题却不见血条，去查钱（上面第 2 条）。
