# 建筑一键维修（RepairAll）

原版修建筑 = 点维修图标（或按维修快捷键）进维修光标，再逐个点带血的建筑。
`[RepairAll] Mode` 三档：

| Mode | 行为 |
|---|---|
| 0 | 保持原样（本模块完全不介入） |
| 1 | 半自动，手动触发 |
| 2 | 自动修，定时扫，掉了血且还没在修的建筑自动进维修流程 |

**手动触发**（Mode=1/2 都行，`DoubleClick=0` 可只留 Ctrl 那两条）：

- Ctrl + 点维修图标
- Ctrl + 维修快捷键
- 双击维修图标
- 连按两下维修快捷键

四种都是"一键全修"。触发点就是原版那两处，不新增键位；维修快捷键的 VK
从 `KeyboardMD.ini` 的 `[Hotkey] ToggleRepair` 读（默认 75 = `K`），玩家改键
自动跟随。

> **Ctrl+维修快捷键必须自己轮询**：引擎 `Game::KeyboardProcess`
> (`0x55DEE0`) 遇到修饰键时只按**精确组合键**查命令表（`0x55DF89` 起），而
> `KeyboardMD.ini` 把 `ToggleRepair` 只绑在裸 `K`(75) 上；且
> `ToggleRepariModeCommandClass::PreventCombinationOverride`（`0x535BD0`）
> 是 `xor al,al; ret 4` 恒 false，不会退回裸 K 命令。于是按住 Ctrl 按 K 时
> `0x536FA0` 的 Execute 根本不会被调用，钩子里那条 Ctrl 判断是死代码。
> 现在由 `RepairAll_Poll` 在每循环轮询 `Ctrl && ToggleRepair` 的边沿补上
> （只读键态，触发后仍只发标准 Repair 事件），并加了"聊天输入中不响应"与
> "游戏在前台"两道门。纯 K / 双击 / Ctrl+图标仍走原钩子。

## 触发点（`dist/MOExperience.dll.inj`）

| 地址 | 是什么 | 偷 | 吞掉时落点 |
|---|---|---|---|
| `0x536FA0` | `ToggleRepariModeCommandClass::Execute`（维修快捷键） | 7 | `0x536FAC`（`ret 4`）|
| `0x6A78D9` | 侧栏维修图标分支（只有 `eax==0x8065` 才走到） | 6 | `0x6A78FF`（`jmp 0x6A7A82` 公共尾）|

按钮音之后才是 `0x6A78F6 push -1 / mov ecx,esi / call 0x4AC8C0`，即
`MapClass::SetRepairMode`（`[0x87F7E8]+0x11B0` = RepairMode）。热键那边同形，
只是 `mov ecx,0x87F7E8` 写死。Phobos 的 PlayerAutoRepair 钩的是同两个点、
同样返回这两个落点。

Ares 共存：`Ares.dll` 的 `.syhks00`（1448 条）与 `AutoLoad_nolog.dll` 都没有
这两个点，前后 32B 内也没有。

## 三条会再踩的坑

### 1. Syringe 钩子不重定位被偷字节里的 rel

**钩子返回 0 时，Syringe 会把被偷的字节搬到跳板里原样重放。里面若有直接相对
跳转（`E8`/`E9`/`0F 8x`/短 jcc），重放时基址变了而 rel32 没跟着变 → 跳野地址。**

所以钩点必须挑**无 rel** 的指令边界，且被偷字节里不能有直接相对分支。
维修图标钩点因此放在 `0x6A78D9`（`mov ecx,[0x8871E0]`，6B）而不是 `0x6A78F6`
（那里偷 9 字节，第三条就是 `call 0x4AC8C0`）。热键钩点偷的
`push -1 ; mov ecx,0x87F7E8` 里那个 `E8` 只是 `imm32` 的一个字节，无 rel。

`BQ_PausePeel` / `BQ_DarkDispatchPeel` 是有意保留 rel 的（它们保证永不返回 0）。
`call DWORD PTR [eax+0x14]` 这类寄存器间接调用与位置无关，不算。

**改任何 `.inj` 钩子后先跑 `tools/hook-rel-audit.py`。**

### 2. x86 C 调用约定下 `bool` 只保证在 AL

引擎实现里出现 `xor al,al` / `mov al,x` 的，函数指针的返回类型**必须**声明成
`unsigned char`。声明成 `int` 会读到 EAX 高 24 位（调用方留下的垃圾），把
`false` 读成 `true`。

`RA_CanRepair` 踩过这个：`0x452630` 与它尾调用的 `0x701140` 失败路径都是一字节的
`32 C0 xor al,al`，我原先声明成 `int`，结果"不可修"被判成"可修"，这道门等于
没装。生成代码对比：

```
错: call eax / test eax,eax / setne al      ; 读 32 位
对: call eax / test al,al  / setne al      ; 只读 AL
```

对照 `WhatAmI`（`0x459EC0` 是 `mov eax,6; ret`，写满 EAX）和
`GetCurrentMission`（`0x5B3040` 是 `mov eax,[ecx+0xAC]`）——那两个声明 `int`
才安全。已核过项目里其余引擎函数指针都是整 EAX。

### 3. `IsPlausiblePtr` 不能当前置解引用或调虚表

它只判 `[64K,2G)` + 4 对齐，堆/栈里随便一个数都能过。要判"这真是个对象"看
虚表指针是否落在 exe 映像内（`RA_IsObj`）；要判"这真是个函数"看目标是否落在
exe 内（`OU_InExe`，OrderUtil.h 的共用判断）。BuildingClass 构造链
`0x43B740→0x6F2B40→0x65A750` 往对象头写 `0x7E180C`（`.rdata`），槽里是
`0x40xxxx` 代码指针。

## 双击为什么只吞第二下

第一下必须放行（走原版，切维修光标），第二下才吞。反过来的话，"其实是单击"
时就没法补一个维修光标状态了——补它得自己直调 `MapClass::SetRepairMode`，
那是改模式状态，撞 AGENTS.md 铁律。

所以**双击/连按的净效果 = 单击的维修光标切换（由第一下完成）+ 一键全修**。
单击行为完全不变。Ctrl+点击则是两下都吞（否则会进维修光标又马上退掉，还白白
`UnselectAll` 一次）。

判定用**墙钟毫秒**（`GetTickCount`），间隔上限 `DblMs`（默认 400）：

- **不能用引擎帧号 `0xA8ED84`**：逻辑帧就是游戏速度，`GameSpeed=0`
  不限速或高帧率时 12 帧只有几十毫秒 —— 实测手动双击的两下间隔是 15~17 个逻辑帧，
  按 12 帧判就全部落空，"双击完全没反应"。换成毫秒后与帧率/游戏速度无关。
- **图标**：再比点位（`GtMouseGameXY`，侧栏区域同样有效），两点位移各 ≤ 12
  游戏像素。顺带挡掉"维修→卖→维修"这种快速三连的误判。
- **快捷键**：靠"两下之间松开过"来排除按住不放的 OS 自动重复——`Poll` 每帧
  采一次维修键的 `GetAsyncKeyState`，松开过才把下一次按下当"新的一下"。

命中后清状态，免得第三下又算一次。

## 联机（AGENTS.md 铁律）

唯一的模拟变更 = 往 OutList 塞标准事件 `EventType::Repair`（0x15），**照抄
引擎自己手点维修的那一段**（`0x4AC0BE`：`WhatAmI()==6` → `TargetClass
0x6E6AB0` → `EventClass(house,0x15,id,rtti) 0x4C65E0` → OutList，连 house 都取
`[0xA83D4C]+0x30`）。真去改血的是引擎自己的 `BuildingClass::Update`，各端拿
同一条事件得到同一结果。钱照扣，与手点维修完全一致。

事件布局：`Type@0 / HouseIndex@2 / Frame@3 / Target@7(ID@7 + RTTI@11)`，共
111 字节。对象 RTTI=52(0x34)，但**不硬编码**，直接取 `TargetClass` 构造器产物。

**发一次就够，不用发"关"事件**：`0x4509B4` 处引擎在满血时自己清
`+0x6E8 IsBeingRepaired`，所以也不必知道 Repair 事件是置位还是翻转。配套
"已在修就不排队"，平时几乎不耗事件。

## 可修性：问引擎，不自己抄

（起因是实测"还在修不该修的建筑"；真凶是上面坑 2 的 ABI 宽度，不是判定逻辑。）

### 事件是个"强制"原语

`IsBeingRepaired = 1` 在全 exe **只有一处**写入：`ObjectClass::SetRepairState`
（`0x446FF0`，`BuildingClass` 虚表槽 `0x19C`，`-1`=翻转 / `0`=关 / `1`=开）。
它只有三个调用点：

| 调用点 | 干什么 |
|---|---|
| `0x449C41` | `SetRepairState(0)`，拆除/卖出时关 |
| `0x450708` | `SetRepairState(1)`，在 `0x450630` 那道门**里面**——**这就是"设置 IQ 自动维修"** |
| `0x4C6F01` | `SetRepairState(-1)`，**Repair 事件处理** |

Repair 事件处理（`0x4C6EFD`）只做两件事：查 `IsAlive`，然后 `SetRepairState(-1)`。
**没有资格判定、没有扣钱。** 资格判定全在 `0x450630`，而那里 `0x4506CE` 一看到
`IsBeingRepaired` 就短路跳去修理——**事件一发，引擎不再复查，直接开修**。
所以原版不让你修不可修的东西，靠的是**光标阶段根本不生成 Repair 事件**。

### 真凶：bool 返回值声明成了 int

见上面**坑 2**。`RA_CanRepair` 原先声明成返回 `int`，而 `0x452630` 的失败路径是
一字节的 `32 C0 xor al,al`，于是"不可修"被判成"可修"，这道门等于没装。

### 现在的判定链

`RA_CanRepair`（槽 `0x94`）= 引擎自己那句"扳手光标显不显示"的判断：
`Health>0 && Type->ClickRepairable && !vtable[0x80]() && 0x701140(this)`。
已验明 `0x7E3EBC` 就是 `BuildingClass` 虚表（槽 `0x2C`=`mov eax,6; ret`，
槽 `0x88`=`mov eax,[ecx+0x520]; ret`）。再加 `RA_MissionBusy`（槽 `0x184`
读 `[ecx+0xAC]`，排除 `Construction(0x12)`/`Selling(0x13)`，与 `0x450663`/
`0x450676` 一致）。扫描与滴发两处都过这两关。

### 为什么不能走另外两条路

- **"设置 IQ 自动维修"**（`0x450630 → 0x450708` 的 `SetRepairState(1)`）是
  **本地直接写模拟内存、不发事件**，正是 AGENTS.md 铁律禁止的；而且带房主级
  条件（`Owner+0x24C` vs `Rules+0x1444`、`Owner+0x245`），对人类玩家本来
  就不成立。只能抄它的判定数据，不能抄它的写操作。
- **模拟鼠标**不可行：点击判定是 `DisplayClass` 虚表 `+0x48`（`0x4AC0B6` 按
  返回值 `0x0A`/`0x0C`/`0x0D` 分派 Repair/Sell/SellCell），而 `DecideAction`
  （`0x692610`）在有选中单位时转给**当前选中代表**的 `MouseOverObject`——
  **结果依赖选中了什么**，不能当逐建筑谓词。逐个假造真鼠标输入更是串行且抢
  光标。顺带证实 `BuildingClass::MouseOverObject`（`0x447210`）里根本不含
  `0x0A`/`0x0B`，扳手动作不是它定的。

### 类型类布局不可信

`BuildingTypeClass::ClickRepairable` 真值是 **`+0x157A`**（`0x452644` 实证），
而 `tools/msvc-layout.ps1` 算出来是 `0xB7A`——**正好差 `0xA00`**。这也是当初
不自己抄那串关卡的原因。

## 指针真伪

见上面**坑 3**。`RA_OwnerOk` 逐个验 `Owner` 落在 `HouseClass::Array` 内且
`Money` 像话，并且本家有建筑命中——任一条不过就整轮放弃（宁可不修，也绝不

## 其它铁律

- 钩子里只读键态/置标志，全图扫描一律挪到 `RepairAll_Poll` 的正常帧上下文。
- 每帧路径上不允许 `GetPrivateProfileIntA`（同 `SWSBar.cpp`），配置全部在
  `RA_EnsureInit` 读一次；`0x4F42F0` 一帧跑 ~142 次，故 Poll 内自门控帧号。
- 日志只有一行启动行（`repairall: mode=.. interval=.. batch=.. dbl=../.. vk=..`），
  其中 `vk` 是解出来的维修快捷键，便于确认改键有没有被读到。
