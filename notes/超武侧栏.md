# 超武侧栏 (SWSBar)

代码 `src/SWSBar.cpp`。相关: `notes/隐藏侧栏.md` (锚点随视口变/收集表)、`notes/BuildQueue建造队列.md` (OutList 范式)、`notes/超武列表.md` (ini 挂载表扫描)、`Hotkey.md` (按键语法)。

## 1. 架构与挂点

**不建 Gadget** (虚表/GameCreate 配重太大), **纯覆盖层 + 轮询**; 只读 + 渲染面绘制, 唯一写引擎数据的是防御页去重 (本地 UI 数据)。

| 环节 | 挂点 | 说明 |
|---|---|---|
| Poll | `0x4F42F0` `MOExperience_PrepareEntry` → `SWS_Poll` | **不是每帧一次**, §9 |
| Draw | `0x5D4A94` `MessageDrawHook` → `SWS_Draw` | 合成面 (Composite) |
| 点击吞没 | `.inj: 0x692419 = SWS_ClickGate, 7` | `ProcessClickCoords` 内, 同 Phobos `SkipOnNewButtons` |
| 合并规则快照 | `.inj: 0x6CEA20 = SWS_SwTypeIni, 6` | `SuperWeaponTypeClass::LoadFromINI` 入口, §1.0d |
| 滚轮 | `0x777998` `MOExperience_WheelHook` → `SWS_WheelIn` | dir 与战役框反向, §5 |
| 去重按钮 | 显隐箭头**左边** | §6 |

吞没门: 前 7B = `movsx ecx,[esi]` + `movsx edx,[esi+2]` (无 rel, 实测); 落栏内跳 `0x6925FC`, 否则跑原版。

```
SWS_Poll   帧门(ADDR_FRAME) → 开关/按键边沿 → 按钮命中 → 栏区命中 → 15帧节流 SwsScan → SwsDedupSync
SwsScan    五元组稳定门控 → 逐项全校验 → 写 s_Items[] (原序) + s_OrderN=-1
SWS_Draw   SwsSig/交互态/age → SwsRebuild(画进缓存) | SwsRebuildCollapsed → 一次锁面 → SwsCacheBlit(alpha)
SWS_ClickGate  s_HoldSkip 或 SwsMouseOnIcon → 0x6925FC
```

`SwsScan` 门控: 先纯安全读, 超武 Items/Count + House Items/Count + `CurrentPlayer` 五元组任一变化 → 只缓存本轮返回; 稳定后才做入局检查 (本家须在 House 数组内) + 逐项全校验。**扫整表的新模块照抄**: 启动期半初始化垃圾曾 fault (`IsPlausiblePtr` 只判下界, 放行 `0x404E0000`)。

显示门 = `Owner==本家 && IsPresent==1` && ID 可打印 && `swIdx∈[0,2048)` && 标志位 0/1 && `!hide && SW_ShowCameo && ManualFire && !drain`。**fail-closed 是硬要求**: 任一不过就跳过, 零命中就不画。

### 1.0 数据源: Super 对象 (★ 两次走错路的教训)

**清单 = `SuperClass::Array` 里 `Owner==本家 && IsPresent==1` 的对象**, 就这一份。防御支援页那一份是**被我们单方面删条目**的镜像, 不参与决定画什么。

**❌ 走错路 1: 从 rules ini 读键。** `INIClass::ReadString(INI_Rules, ...)` 只有**基础规则**。战役/地图可在**地图内嵌 ini** 里新增或改写 `[XxxSpecial]` 节, 磁盘上那份 rulesmo.ini 里根本没有那些节 (实测 `SP_CryospearSpecial` / `SP_TPSpecial` 出现 **0 次**) ⇒ 新声明的超武读出空 (`nopcx`, 格子空着), 改写过的读出旧值 (**用错图像**)。

**❌ 走错路 2: 把防御支援页当数据源。** 曾想"清单从防御页取就自动一致了", 还设计了个位图假装解决自指。**自指根本不存在** —— "画走 Super 对象, 防御页那份只被 `SwsDedupRemove` 动"本来就是这种结构, 换数据源等于自己改自己。而且防御页也**不是**"玩家拥有哪些超武":

```cpp
// ares(Antares)/src/Ext/SWType/Hooks.Update.cpp:178  HouseClass_UpdateSuperWeaponsUnavailable
if(!pSuper->IsPresent || pSuper->IsOneTime)
    if(status.Available)
        if(pThis->IsCurrentPlayer())
            if(pData->SW_ShowCameo)                  // ← SW_ShowCameo=no 直接不进页
                MouseClass::Instance.AddCameo(Special, index);
```

`SW_ShowCameo=no` 的那批 (实测 `ConfusionGridSpawn` 就是) **压根不会出现在防御页上**, 把防御页当清单 = 把它们全放出来。

**教训: "和某个界面一致"不等于"以那个界面为数据源"**, 后者要先问"那个界面的清单是谁按什么规则挑出来的"。

### 1.0b 三条旗标读**对象字段** (战役内嵌 ini 才算)

`ManualControl` / `UseChargeDrain` / `Action` 读对象字段 (引擎建对象用合并后的 ini, 战役/地图改写天然生效), ini 那份只用来对账, 不一致打 `sws: flags OFFSET? manual <ID>`。

⚠ **对账用的键名必须是 `ManualControl`, 不是 `SW.ManualFire`** —— 后者是 **Ares** 的键 (写进 `SWTypeExt::ExtData::SW_ManualFire`), 与这个字段毫无关系。原先写的是 `SW.ManualFire`, 于是 `flags OFFSET?` **实测一直触发** (`ConfusionGridSpawn`), 而"偏移可疑"这个结论挂了几个月: 真正该读的 `ManualControl=` 没人读, 判据形同虚设。

三个偏移现已逐个对回 gamemd (`0x6CE62E` 起的 CTOR + `0x6CEE60` 的 `add ecx,0x24` + `DrawCameo` 的 `mov edx,[eax+0xB8]` + 侧栏点击处理 `0x6AAF08 cmp dword [ecx+0xBC],edi` 四处互证): `0xBC=Action` / `0xE5=UseChargeDrain` / `0xF5=ManualControl`。**推导出来的偏移必须配自证日志, 不能默默用** —— 这次的自证日志之所以"一直红", 根因不是偏移错, 是**对账键名错**。

⚠ **绝不能用合并快照里的 `SW.ManualFire` 覆盖 `manual`** (2026-10-02 踩过): `ManualControl` (gamemd) 与 `SW.ManualFire` (Ares) 是**两个不同的键**, 前者在对象上、后者只在 ini 里。对象字段本身已经是合并后的值, 快照对 `manual`/`drain` 没有任何增量, 覆盖只会把过滤弄乱。快照只补**对象上没有对应字段**的那几个 Ares 键 (`SW.ShowCameo` / `SW.UseAITargeting` / `SidebarPCX`)。

(对照: rulesmo.ini 里 `SW.ManualFire=no` 的 9 个节 —— `ReproCashFix` `EMPMineSpawn` `GenomineSpawn` `CryomineSpawn` `StasisGridSpawn` `ConfusionGridSpawn` `CrateDropSpecial` `CraneSpecial` `IronGuardSpecial` —— **是 `SW.ShowCameo=false` 那 17 个的子集**, 所以按 ShowCameo 过滤已经全覆盖, 不需要 ManualFire 这道门。)

### 1.0d 合并规则快照 (`SWS_SwTypeIni`, 0x6CEA20) —— 三个症状同一个根因

`CCINIClass::INI_Rules` (0x887048) 在**扫描期**读到的是**基础规则**那一份。战役/地图可在**地图内嵌 ini** 里新增或改写 `[XxxSpecial]` 节, 那一份只在**加载期**存在:

| 症状 | 缺的是哪个键 | 现场 |
|---|---|---|
| 侧栏里冒出 `SW.ShowCameo=false` 的超武 | `SW.ShowCameo` (Ares) | `IronGuardSpecial` (rulesmo.ini 里明明写了 `=false`, 而以前**根本没读这个键**) |
| 图标时有时无, 要点一次"过滤/显示"按钮 | `SidebarPCX=` | 地图新增的超武 (`WarheadSpecial1`/`SP_CryospearSpecial`…) 在 rulesmo.ini 的 `[SuperWeaponTypes]` 里有号但节里的键读不到 ⇒ 空格子 |
| `WarheadSpecial1` 点一次就生效, 侧栏要点两次 | `SW.UseAITargeting` | 只在 emigdal.map 的 `[WarheadSpecial1]` 里有 |

⇒ **挂 `SuperWeaponTypeClass::LoadFromINI` 入口 (0x6CEA20, 6B = `sub esp,0x3F0`), 当场读键存进自有表 `s_Mix[]`。** gamemd 侧证据: `0x6CEA27 mov ebx,[esp+0x3F8]` 取的正是栈上那个 pINI; Ares 也在同一函数里挂 `0x6CEE43 = ExtMap.LoadFromINI`。

三条铁律:
1. **不留 ini 指针**。地图那份是 `ScenarioClass::Load` 栈上的临时对象 (`lea ecx,[esp+0x2C]`, 用完 `call ~INIClass`) —— 跨帧读它就是野指针。**当场读、当场存值**。
2. **合并语义 = "后写的键覆盖先写的, 没写的键不动"**, 与引擎/Ares 的 `Valueable::Read` (`ReadString` 返回 0 就不动) 一致。首次建条目时先用 `INI_Rules` 垫底 ⇒ 万一钩子只看到基础规则, 行为与修复前一致, **不倒退**。
3. ★★ **实测: 引擎喂进来的"合并后那份"就是 `*(void**)ADDR_INI_RULES`** —— gamemd 在读类型之前把 `[0x887048]` 指向合并后的 ini (`0x52D0FA mov [0x887048],eax`), 读完再换回去。**所以钩子里"非 INI_Rules = 地图那份"这个判据永远不成立** (第一版按它写, 日志里一行都没打, 白查半天)。
   推论: **钩子读到的值必须留住**。第一版把 `s_Mix` 放进 `SwsCacheEpoch` 的"换代就清"里 ⇒ 每次进剧本都把刚读到的 `SidebarPCX` / `SW.UseAITargeting` 全扔掉, 回到"扫描期现读基础规则" ⇒ **图标空着 + `instant` 判错, 两个症状同一个原因**。现在 `s_Mix` 只在**类型对象重建**时清, 而且由**钩子自己**在 `SWS_SwTypeIni` 里判 (`SuperWeaponTypeClass::Array.Items` 变了就清 —— 正好赶在这一轮 ini 读之前)。

自证日志 `sws: swtype hook n=<次数> <ID> p=<0|1> @<ini指针>` (前 3 次 + 每 250 次): `p=0` 是正常的 (见铁律 3)。

`SwsCacheEpoch()` 另盯 `INI_Rules` 指针 + 类型数组指针, 变了就清 `s_Ini` / `s_TC` / 重给诊断配额 —— 换关后不带着上一关的图标/名字。判据用指针而不是内容: 换一份 ini 一定换指针, 每帧比对内容不便宜。

### 1.0e 图标兜底: 让引擎自己重画一次防御页 (`SwsNudgePaint`)

抓取钩 (`0x6A9958`) 只在**引擎正在画防御页 cameo** 时才有数据, 而: 钩子要 `frame >= 60` 才装得上 (装上前侧栏早画过一轮)、防御页默认不是激活页签、地图内嵌 ini 新增的超武压根不在 rulesmo.ini 里。⇒ "格子空着"。

**玩家点一次"过滤/显示"按钮之所以能救回来, 就是按钮那条路顺手调了一次 `RepaintSidebar(1)`** (`SwsDedupRestore` / `SwsDefenseRepair` 都会调), 引擎于是重画防御页, 抓取钩抓到像素。`SwsNudgePaint` 把那次重画自己做掉: 只要还有条目没抓到图标, 每轮扫描催一次, 催满 32 次停手; 条目集一变 (换剧本) 配额重给满。**必须排在 `SwsDedupSync` 之前** —— 去重会把"还没图标"的条目留在防御页上等图标 (见 `SwsSidebarHasIcon`), 催画要赶在它被搬走之前。纯 UI 重绘请求, 不碰模拟。

即便如此 `SidebarPCX=` 那条路仍必须修好: 它是**唯一**不依赖"引擎恰好画了那一页"的来源, 而合并快照 (§1.0d) 已经能拿到地图那份。

### 1.0c 图标: 在 Ares 填好 `CameoPCX` 之后把它读出来

`SidebarPCX=` 只能从 `INI_Rules` 读 ⇒ 战役内嵌 ini 的超武读出空 / 用错旧值。引擎把合并后的值存在 Ares 的 `SWTypeExt::ExtData::SidebarPCX`, 而 `ExtMap` 是 Ares 自己实现的映射 (`ContainerMapBase`), 定位成本过高。

**⇒ 在 Ares 填好 `CameoPCX` 之后把它读出来。** gamemd 原码 (离线反汇编确认):

```
6A9950  73 0C              jae 0x6A995E              ; 越界分支
6A9952  8B 90 B8 00 00 00  mov edx,[eax+0xB8]        ; ← Ares 的钩点 (EAX = SWType)
6A9958  89 54 24 48        mov [esp+0x48],edx        ; ← ★ 我们钩这里 (5 字节)
6A995C  EB 08              jmp 0x6A9966
6A995E  C7 44 24 48 000000  mov [esp+0x48],0         ; 越界分支
6A9966  A1 4C 3D A8 00     mov eax,[0xA83D4C]       ; 两条路的汇合点
```

Ares 的钩替换掉 0x6A9952 那 6 字节, **把 `CameoPCX` 填好之后**才落到 0x6A9958。此刻 `CameoPCX` 已填好 (还没被 blit 掉再清零), 且 **EAX 已被 Syringe trampoline 还原成 `SuperWeaponTypeClass*`** —— pSW 和图标都在手上。

**壳 (27 字节)**, 替换 0x6A9958 那 5 字节:

```
60                pushad
A3 <slot>         mov [slot],eax          ; pSW = EAX (Syringe 已还原)
E8 <rel>          call Sws_CaptureCameo  ; 拷走 60x48
61                popad
8B 90 B8 00 00 00 mov edx,[eax+0xB8]      ; ★ 补回被我们盖掉的那条指令
89 54 24 48       mov [esp+0x48],edx      ;   (Ares 的钩跳过了它, 所以要补)
E9 <rel>          jmp 0x006A9966          ; 直接落到原来那个 jmp 的落点
```

**`CameoPCX` 的地址定位**: 扫两个**导出符号** (`GetProcAddress` 直接拿, 都在 Ares 导出表里) 的函数体, 取第一个命中 Ares `.data` 的绝对地址写/读:

| 符号 | opcode | 含义 | 离线实测命中 |
| --- | --- | --- | --- |
| `StripClass_Draw_SuperWeapon_PCX` | `A3 imm32` | `mov [m],eax` | **+0x17** |
| 同上 (备用形态) | `89 0D/15/1D/25 imm32` | `mov [m],ecx/edx/ebx/esp` | — |
| `StripClass_Draw_DrawPCX` | `83 3D imm32 00` | `cmp dword [m],0` | **+0x03** ★ |
| 同上 | `C7 05 imm32 00000000` | `mov dword [m],0` | **+0x7D** |

⚠ **两个符号都必须扫到**, 且扫出来的地址必须**同一个** —— 那是"这地址真的是 CameoPCX"的唯一证据 (踩过: 只扫 `A3`/`C7 05` 漏掉 `DrawPCX`, 它**读**用的是 `83 3D`, 结果 `a=0x61D720CC b=0x00000000` 互证失败 ⇒ 钩子不装 ⇒ 图标永远空)。扫描窗口须 ≥ 0x80 (`DrawPCX` 的清零在 +0x7D)。

⚠ **不要用 `IsPlausiblePtr` 判 Ares 里的地址**: 它只放行 `[0x10000, 0x7FF00000)`, 而 Ares.dll 的 PE ImageBase 就是 **0x10000000** —— 没有 ASLR 时整个模块都在上界之外, 每个地址都会被判成"不可信"。一律按 `SwsAresImage()` 的**映像范围**判。

⚠ **这一条连踩三次, 是同一个教训: 别去猜 Ares 的内部。** ①按"站点首字节必须是 `E9`"判断 ⇒ 钩子一次没装上; ②`GetProcAddress` 拿钩子体再裸 `jmp` ⇒ 崩, Ares 的 `GET(pSW,EAX)` 编译成 `mov eax,[esp+4]`, 那个"寄存器快照"是 **Syringe trampoline 压在栈上的**, 裸 jmp 过去是游戏栈垃圾; ③自己造快照再 `call` ⇒ 还是崩, Ares 体内 `ExtMap.Find()` 返回 0 → `mov eax,[eax+0x4D0]` 读野指针, 且它压栈压的是 `[eax+0x24]` 而不是 eax, 与 `Container<TX,TCont>` 的 `key_type = base_type*` 对不上。**能"在别人做完了之后观察", 就不要"替别人做"** —— 前三次都在复刻 Syringe/Ares 的私有约定。

其它装钩约束 (**本项目所有装钩的地方通用**):
- ⚠ 写 gamemd 的 `.text` **必须** `VirtualProtect(PAGE_EXECUTE_READWRITE)` + `FlushInstructionCache` (`AirWay.cpp:71` / `ChatEdit.cpp:1110` / `FullMap.cpp:421` / `VecText.cpp:2142`)。第一版直接写, 实测 `fault=1(write)` 当场崩。`SwsAresFindTabCameos` 只**读**、`SwsDedupRemove` 写的是**堆**, 那两处不 protect 也没事 —— **别因为"那两处没炸"就以为可以省**。
- ⚠ `mov [slot],eax` 不能省: 抓取函数是**另一个函数**, 没有寄存器快照可读。漏了它 ⇒ 抓到的 type = 0。
- ⚠ `pushad`/`popad` 必须成对: 中间是真实 call, 会破坏 ebx/esi/edi/ebp, 而编译器只当 ecx/edx/memory 被破坏 (§7 同一个坑)。
- ⚠ 必须**拷像素**, 不能留 `BSurface*`: 引擎切页签/重载美术会释放重建 (§7)。

图标优先级: **抓到的那张 > `SidebarPCX=` 那条路**。前者就是引擎此刻画的那张; 后者现在从**合并规则**快照拿 (§1.0d), 地图新增的超武也读得到。

**⚠ 抓到 ≠ 显示: 抓回来的像素必须有人取。** `Sws_CaptureCameo` 把 60x48 拷进 `s_Cap[]`, 但 `SwsTypeEntry` 每轮扫描会把 `tc->capPix` 清成 NULL —— **必须**在 `SwsScan` 里 `if (!tc->capPix) tc->capPix = SwsCaptured(type);` 交给侧栏, 否则 `s_Cap[]` 是死数据, 症状 = 日志里 `sws: cap` 都在、格子还是空的。

**⚠ 抓到这条路本身不可靠 —— 它只在"引擎正在画防御页"时才有数据。** 防御页默认不是激活页签, 于是绝大多数情况下抓不到; 而去重又把 cameo 搬走了, 更抓不到。以前唯一的兜底 (读 ini 拿 `SidebarPCX=`) 只覆盖基础规则那份 ⇒ 地图新增的超武**两条路都空**。症状就是"要点一次去重按钮才出来"(按钮触发 `AddCameo` + `RepaintSidebar`, 引擎终于画了)。**合并规则快照 (§1.0d) 才是可靠那条路**, 抓取降级成"像素最准"的加分项。

**搬出要等图标到位**: 图标还没着落的条目**先留在防御页上** (`SwsSidebarHasIcon`)。搬走之后引擎不再画它 ⇒ 抓取钩永远抓不到 ⇒ 两边都没图标。重复几秒 ≫ 永久空格子。

**离线先验证再进游戏** (本节最值钱的一条): Ares.dll 就在 `G:\motest`, 导出表 + `.data` 范围 + 钩子体机器码 + gamemd 原码都能脚本读出来。我们打算盖掉的那 5 字节原本是什么、两个钩子认出的地址是否同一个 —— 全都可以离线定死。三次失败里有两次离线五分钟就能查出来。

**日志**: `sws: cameo hook ON pcx=<CameoPCX> base=<Ares基址>` / `sws: cameo getproc FAIL ...` / `sws: cameo pcx mismatch a= b=` / `sws: cameo hook FAIL` / `sws: cap <ID> n=<已抓数>` (前 8 条)。

### 1.1 `s_ItemN == 0` 是"侧栏整个消失"的唯一开关

`s_ItemN==0` 同时决定三件事, 所以症状永远是**成组**出现, 不要当成两个 bug:

```
s_ItemN == 0  ─┬─→ SwsRebuild goto nogeo      → 侧栏整块不画 (连两个按钮都没了)
               └─→ SwsDedupSync 的 s_ItemN<=0 闸门 → 防御页去重停手, cameo 原样留着
```

**现场指纹: "屏上没有侧栏" + "原版防御支援页一堆超武一个没被搬走"** ⇒ 不用猜, 就是 `SwsScan` 交了 0 条。

⚠️ **`fail-closed` 遇到"字段读出垃圾"就等于整条功能静默失效** —— 症状和代码逻辑完全对不上。已给 `SwsScan` 的 9 个 `return` 和 `SwsRebuild` 的 3 条 `goto nogeo` 全加了**旁路日志** (同一原因只记一次, 原因变了再记):

| 日志 | 含义 |
| --- | --- |
| `sws: scan0 cur/suparr/supitems/houserr/houseitems/stability/nohouse a= b=` | 前置门 / 稳定门早退 |
| `sws: scan0 n0 tot= owner= present= type= flag= id= cache= idx= hidden= nocameo= hcnt=` | 扫到条目但被显示门吃光, **逐门计数** (`nocameo` = 被 `SW.ShowCameo=no` 挡掉的) |
| `sws: vec <基址> items= cap= ini= cnt= inc= a=` | 容器头原样 (值变了才记) |
| `sws: draw0 nitems/norows/cache` | 绘制期三条 `goto nogeo` |
| `sws: scan ok n=` | **条目数每次变化都记** (原先只记第一次, 看不出是哪一局坏的) |

实测抓到并已修: `sws: scan0 supitems a=4480 b=0` + `sws: vec 0x00A83CB8 cnt=4480 cap=4480` —— 容器**完全自洽**, 4480 就是 MOE 满编剧本里 `SuperClass::Array` 的真实条目数 (≈9 个 House × ~500 个超武类型), 原先的 `count > 4096` 上界把它误杀了。

⚠ **`fail-closed` 的"上界"必须由容器自己给出, 不能拍脑袋**。统一走 `SwsVecItems()`: `Items` 可信 ∧ `1 ≤ Capacity ≤ 65536` ∧ `0 ≤ Count ≤ Capacity`。最后一条是**硬门** —— `Add` 先 `Reserve` 再写 `Items[Count++]`, 所以恒成立, 反过来就一定是野值。真正的安全网是**逐项全校验**, 上界只该卡"大到读不下去"。

4480 条还带出一个性能坑: 实例门原本每条 cameo 走一遍全表 ⇒ 单次去重复查十几万次循环。已改成 `SwsBuildLiveSet()` 一趟建位图 + `SwsLiveHas()` O(1) 查。

**绝不能只在"首次填充"分支写 `s_Items[n]`** (下标随建筑增减重排 → 张冠李戴): 名字/图标/阵营/优先级/`instant` 属**类型**, 存 `SwsTypeCache` (按 type 指针缓存, `prio<0`=未填充), 每轮拷进 `s_Items[n]`。

## 4. 绘制管线: 离屏缓存 + 15 逻辑帧节流

合成面每渲染帧都被重画 → **重建** `SwsRebuild` (布局+排序+像素全画进自有缓存, **不持锁面**) + 每渲染帧一次 **合成** `SwsCacheBlit` (带 alpha 拷贝, 内层只有乘加移位)。缓存 = **16 位色 `s_CchC` + 8 位覆盖率 `s_CchA`**; 只存色就把半透明烙死。`SwsCacheAlloc` 只清覆盖率面, 上限 `SWS_CACHE_MAXPX = 2M` 超过不画。

`SWS_Draw` 每帧只算三样决定是否重建: ①`SwsSig(w,h,pitch)` = 画布尺寸 + `g_MapRight` + 显隐 + 去重开关 + 滚动偏移 + 条目集合 (`swIdx/side/prio/ready/susp/instant/pcxFile`) —— 锚点必须进签名 (F11 切视口时地图右缘在 1752/1920 跳而画布尺寸不变 → "切换后残留一块图标"), 刻意**不含 `remain`** (有在充能的就永不作废); ②交互态 `hover/btnHov/curSel` 与上次值比 → 移上去/点中/松开上膛/滚轮/点箭头/点去重按钮都**当帧重画**; ③兜底 `age >= 15` 逻辑帧, 帧号回拨 (新开局/读档) 强制重建。

顺序固定, 乱序会被盖掉: 底框(一次黑底 op=30) → 图标+充能文字 → 每列边框 → 条目高亮框 → 滚动条 → 显隐箭头 + 去重按钮 → 悬停名提示框。
- 边框在图标**之后** (否则被 60x48 图标盖住); 高亮框在**每列边框之后**且独立一遍 (画 `it->x-1 .. x+ICON_W`, `ColGap=0` 时压住左右邻列外边框; 塞进图标循环会缺一截、像错位)。
- 提示框**不逐像素跟随鼠标** (锚鼠标 x 时移 1px 就要重画整块), 锚图标水平中心、画在图标下方; 悬停那个图标**不透明** (`opaque=1`), 不压"未就绪"暗罩。
- 提示框 = 半透明黑底 + 1px 边框 `A5D3FF`, 框比文字左右各宽 2px (`sw+6` × `adv+4`), 贴边夹取**按框算**; `A5D3FF` 也是箭头/高亮主题色 (`SWS_ACCENT_R/G/B`)。

**提示框必须在分配缓存之前量出来** (`SwsTipPrepare`→`SwsTipRect`, 它可能探出侧栏块), 否则被缓存边界裁掉; 高亮框描边在 `it->x-1` / 下边正好 `yStart+blockH` → 缓存矩形**左/下各再让 1px**。字形走自有覆盖率缓存 `s_Tip` (1024×48×1B), 每帧 `RenderLine` 不行 (每次先 `ClearDib` 一遍)。**GDI 槽 5→6→7** (`GdiText.cpp`): 提示框用槽 6 (`[VecText]` 字号), 充能百分比用槽 5 (`[SWSidebar] FontPx`); **两者不能共用一槽**。画字前必须**显式 `GdiEnsure`**, 直接拿 `g_G` 会借到上一模块的槽。

## 5. 几何 / 布局 / 滚动

- 图标盒固定 **60×48** (Phobos cameo 尺寸), **不要**做成配置项: PCX 是固定尺寸源, 缩放后目标矩形只按屏幕边界裁剪 → 非默认尺寸溢出格子错位。
- 锚点 = **地图区右缘** `g_MapRight` (态0=1752 / 态1,2=1920), `=0` 才退回画布宽; 锚画布右缘会把整块塞到原版侧栏底下。
- `TopMargin` 比例时 `yStart = h*比例 - blockH/2` (视觉居中), 像素时直接当 Y; 纵向要给块顶上方的两个按钮留 `SWS_BTN_H+2`。收起态**不减半个块高**。排序: 阵营 → ini 优先级 → `ArrayIndex`, 只在 `s_OrderN != s_ItemN` 时真排一次。
- **`s_Items`(原序=SuperClass 数组序) 与 `s_Order`(排序后) 是两套下标**: 遍历排序结果一律写 `s_Items[s_Order[i]]`, `SwsHitItem` 返回**排序后**下标。
- **面板级滚动**: 单个 `s_Scroll` 所有列一起滚 (`ColGap=0` 后列间无空隙, 逐列的 4px 滚动条会盖在下一列图标上)。上限 = `最长列条目数 - 可见行数` (**不是** `colCount-1`); 滑块 `scroll/maxSk` **正比**, 第 0 项在**上**面。
- 出界条目 `x = -1`, 既不绘制也**不参与命中** —— 必须 `if (x < 0) continue;`, 否则 `mx >= -1 && mx < 59` 对屏幕左侧整条竖带恒真。
- **按钮** 20×16: 显隐在块右缘、禁入牌在它左边 3px, 两行都在块**上方**。只能挂上方 —— `SWS_Draw` 拿的是合成面 (宽 = 屏幕宽 − 原版侧栏宽 1752), 挂右边会算到面外被丢掉。收起态沿用 `s_BtnXKeep/s_BtnYKeep` (别改成"贴屏幕右缘": 折叠/展开时箭头肉眼可见地跳)。**隐藏态也必须画箭头**, 否则玩家找不到展开处。

### 吞没/命中判定

- 必须按"**真的画了东西的地方**", 不能用整块容器矩形: 某列条目少时下半截是空的, 没图标却把整片点击吞掉 ("侧栏盖住的地图那块点不动"); 现在门只看 `SwsMouseOnIcon()`, 空地还给引擎。
- **UI 元素画在判定框之外 = 永远点不到**: 两个按钮都在栏区判定框之上 → 命中判定必须排在栏区判定**之前**。**右键取消也必须限在栏区内**, 否则玩家在地图上右键取消单位会把超武选中状态也清掉。
- 判定用 `s_BoundsKnown`, **不是** `s_BoundValid`: 后者由 `SwsScan` 开头清零、只在重建末尾置 1, 而点击那帧 Poll 先跑 + 点击必然 `s_ForceScan=1` 触发重扫 → 门撞上被清零的窗口。`s_HoldSkip` 在物理左键按住期间一直吞引擎地图点击, 松开即清。

### 按键边沿

**多个分支必须共用同一份状态变量**: 可见分支点箭头后直接 `return`, 绕过末尾的 `s_PrevLB = lb` → 下一帧进隐藏分支拿到的还是旧值而按键确实按着 = 伪造出一个**新按下沿**, 刚收起的侧栏立刻弹回来。修法: 每条 `return` 前自己写回按键态, 隐藏分支不要另开一份。判据: 任何"提前 return 的路径"都会跳过末尾的状态更新。

## 6. 隐藏防御支援页里的重复超武 (DedupDefensePage)

侧栏有的超武, 引擎自带的**防御支援页** (页签 1) 里不再出现一遍; 侧栏上没有的 (ini 隐藏 / `SW.ShowCameo=no` / `SW.ManualFire=no` / 火风暴类) 照旧。开关在显隐箭头左边。

**⚠ 这个功能只能"少删", 绝不能"多删"** (超武丢失类 bug 的唯一来源): 判据必须是"侧栏此刻真的在画这个超武"的**真子集**, 因为搬出是**单向**的 —— "侧栏不画 + 防御页被删" = 两头都没了且不自愈。四道门 (任一不过就保留 cameo):

| 门 | 判据 | 挡的是什么 |
| --- | --- | --- |
| 类型门 | `SwsSidebarShows()` = `!hide && SW_ShowCameo && ManualFire` | ini 隐藏 / `SW.ShowCameo=no` / `SW.ManualFire=no` / 火风暴类 |
| 实例门 | `SwsLiveHas()` = 本家有 `IsPresent==1` 的 Super | cameo 已进防御页但 Super 还没变 `IsPresent` 的时间差 (Ares `HouseClass_UpdateSuperWeaponsUnavailable` / ICBM / `Grant1ShotSW`) |
| 快照门 | `SwsSidebarShowing()` = 最近一次 `SwsScan` 的 `s_Items` 里真的有 | `SwsScan` 早退 (数组换了=开局/重开/读档 / 本家未入 House 数组 / 半初始化垃圾) 时 `s_ItemN==0` |
| 图标门 | `SwsSidebarHasIcon()` = `capPix \|\| pcxFile` | 图标还没着落 (见 §1.0c), 搬走后永远抓不到 |

`SW_ShowCameo` **必须**在类型门里, 而且是**双向**的: 少了它侧栏会冒出游戏里根本没有的超武 (问题 1); 多了它 `SwsDedupRestore` 会把引擎本来不给的 cameo **主动加进防御页**, 那是改游戏行为。

实例门也是**两个方向对称性**的要求: `SwsDedupRestore()` 一直有实例门而 `SwsDedupRemove()` 曾经没有 → 差出来的就是丢失窗口。

⚠ **紧凑搬移的位移量必须现算**: `tail = cnt - 1 - i;` 然后 `for (j = 0; j < tail; j++)` 前移。`j`/`tail` 若没赋值就用了, 会从任意偏移往 cameo 数组里搬数据 —— 这是"去重之后超武彻底消失"的成因之一。

引擎机制: cameo 入口 `SidebarClass::AddCameo` `0x6A6300`, 调用点 `HouseClass_UpdateSuperWeaponsUnavailable` (Ares `0x50B329`)、`ICBM` 补给箱 `0x482D4C`、脚本 `Grant1ShotSW`/`GrantPermanentSW`; 引擎唯一的移除路径 `StripClass::RecheckCameo` `0x6AA600` **只删 `IsPresent==0` 的** —— 我们的都还在。入口拦截 (`0x6A6316`) **一次都没被调用过** (零日志, 而 76 条确实能搬出) → 改用 15 帧复查。

### `RulesExt::TabCameos[4]`

Ares 3.0 换掉了 cameo 容器 (`ares(Antares)/src/Ext/Rules/Hooks.CameoList.cpp`): `DynamicVectorClass<BuildType> RulesExt::TabCameos[4];` (Ares.dll 的 .data)。增删/绘制/点击/排序/`RecheckCameos` 全走它; `StripClass::Cameos[75]` 内联数组是**死内存** (只留 `Index`/`TopRowIndex`/`CameoCount` 还在用)。Ares 没导出"删某个 cameo"的接口, 只能直接改这个数组。`BuildType` 步长 `0x34`; 首字段 `AbstractType` (+0), 次字段 ArrayIndex (+4)。

### 定位办法 (`SwsAresFindTabCameos`) —— 从 Ares 自己的代码里读地址

Ares 导出的 `SidebarClass_AddCameo_SkipSizeCheck` (钩 `0x6A63B7`) 开头几十字节:
```
8B 04 CD <disp32>     mov  eax, [ecx*8 + TabCameos[0].Items]
6B 0C CD <disp32> 34  imul ecx, [ecx*8 + TabCameos[0].Count], 0x34
```
两个 `disp32` 都是编译期写死的绝对地址 → `TabCameos = (Items的disp32) - 4`, 再用第二条互证 `(Count的disp32) - 0x10 == TabCameos`。不扫 `.data`、不误命中别的容器, ASLR 后依然对; 容器头地址终身不变 (Ares 只在 `ClearCameos` 清内容, 从不搬容器), 只有 `Items` 随扩容变 → **每次用之前现读 `Items`**。扫 `.data` 那版失败的唯一原因: 判据骨干 `TabCameos[i].Count == StripClass::CameoCount` 里 `this` 取错 → 永远 `hits=0` (**判据里放进一个自己都没验证过语义的东西 = 给自己判死刑**)。

定位后逐个校验四个容器 (`SwsDVecOk`: vtable 相同且落在 Ares 映像内、`CapacityIncrement == 100`、`Capacity >= Count >= 0`、`Items` 可读), 任一不过即 fail-closed。`SwsTabCameoOk` **只校验容器自身, 不再拿 `CameoCount` 互证** (该互证坑过两轮: `this` 取错; 本机确实与 `TabCameos[i].Count` 不同步)。**只在确实在跑一局时才找**: `CurrentPlayer` 有效 + 帧号走过 60 (主菜单里容器还没建好), 试一次就够, 失败整条功能关掉并记一行; 这类"可能整条路都不走"的代码必须有一条**无论如何都会打的旁路日志**。

### 两个方向依赖不对称 (关键)

- **搬出 (隐藏)**: 必须直接改 `TabCameos[1]`, 再调 `SwsDefenseRepair()` 收尾。
- **搬回 (显示)**: **完全不碰容器**, 对每个 `IsPresent && 侧栏有` 的超武调引擎自己的 `AddCameo(0x1F, idx)`; 它自带查重, 对已在页里的重复调用是**无害空操作**。搬回也查容器判重的话, 校验一不过就**静默失败** —— 同理 `SwsDefenseRepair()` **只在搬出之后才调**。

`SwsDefenseRepair` 顺序: 同步 `StripClass::CameoCount = TabCameos[1].Count` (**必须**, 页签布局按它算; 写前先读一次确认落在 `[0,4096]`, 宁可跳过也不能写坏别人内存) → 非空则 `UpdateScrollButtons`; 空则 `GadgetClass::Disable(页签按钮)` + 跳第一个非空页签 `SetTab` → 滚动位置**只夹取不重置** → 两个 redraw 标志 → `RepaintSidebar(1)`。

**`SwsSidebarShows()` 是纯谓词 (只有类型门), 里面绝对不能判 `s_Enable` / `s_DedupHide`**: 它被搬出和搬回共用, 而"切回显示"时 `s_DedupHide` 恰好是 0 → 恢复循环把所有超武 `continue` 掉 (症状: 有 `sws: dedup btn show` 却接着 `sws: dd show n=0`)。其余三道门也别塞进去 (会连带把搬回判没)。

`SwsDedupSync` 每 15 帧 (0.25s) 在 `s_DedupHide` 时置 `s_DedupDirty`, 让 `SwsDedupRemove` **在已隐藏态也再跑一遍移除** (幂等)。目标态 `want = s_DedupHide && s_Visible` —— **`s_Visible` 这半个是必须的**: 侧栏收起 (F4) 之后一格都不画, 若目标态还是"隐藏重复", 那些刚被搬走的超武就在收起期间两头都没了, 而搬出单向、展开也不会补回防御页。同理 `want && s_ItemN <= 0` 时**这一轮什么都不做** (日志 `sws: dd wait scan`): 扫描早退那 0.25s 里删 = 整页清空。

> 踩过一次反直觉的坑: 曾把 `s_Visible` 从 `want` 里去掉, 理由写的是"收起时不必把防御页恢复成全都显示, 那是多余动作"—— 但那时防御页里**已经被搬走过**了, "侧栏藏了照样能用"根本不成立。**判据里塞进一个没验证过后果的前提 = 给自己埋丢失**。

## 7. 图标链路 (PCX, 全部引擎现成设施)

MO 的超武图标**不是 SHP**: `rulesmo.ini` 里 96 个超武节用 `SidebarPCX=xxx.pcx`, `SidebarImage` 只出现 1 次且指向引擎 `XXICON.SHP` 占位引用 (画出来全是**同一个紫球**, 11 个条目指针完全相同)。PCX 打包在 `expandmo*.mix`/`thememo.mix`, 磁盘上没有。

```
1. 读键: 合并规则快照 (§1.0d) 里 <ID> 节的 SidebarPCX=
2. 载图: PCX::Instance = 0xAC4848 (this 就是该地址, 不能解引用) -> GetSurface @0x6BA140, 未命中则 ForceLoadFile @0x6B9D00
3. 贴图: 自写逐像素循环 SwsCPcx (色键 0xF81F, 源列映射表预计算)
```
- `GetSurface` 在文件**未加载时不返回 NULL**, 而是给占位 surface → 必须**无条件先 `LoadFile`**, 否则全是紫球 (而日志显示 "pcx ok")。
- 引擎 `BSurface*` **绝不能跨帧缓存**: 切页签/重载美术会释放重建 → 平时脏图、切页签崩溃; 现在**只缓存文件名**, surface 每帧现取。
- 文件名按 Ares 的做法**小写化**后存 (Ares 的 `AresPCXFile::operator=` 里就是 `_strlwr_s`), MIX 里 PCX 一律小写。
- 无 PCX 的超武 = 空条目 (边框/百分比照旧), 记一行 `sws: nopcx <ID>`。悬停名字优先 `SWType::UIName`, 空则退回 ID。

## 8. 即时类超武与 SpecialPlace 事件

### `instant` 判据 (对象字段为主 + 合并 ini 兜底, 每类型算一次)

```
对象上的 Action(+0xBC) == 0        ← gamemd 侧栏点击处理 0x6AAF08 判的就是它
||  SW.UseAITargeting=yes          ← Phobos LaunchSuper 额外认这一条
||  Action=None (ini)              ← 兜底
||  Type ∈ {HunterSeeker, Battery}
||  UseChargeDrain=yes
```
**判据直接抄 Phobos 的 `SWButtonClass::LaunchSuper`** (`src/Ext/Sidebar/SWSidebar/SWButtonClass.cpp:203`) —— MO 原版侧栏就是它, "与原版一致" 的基准是它而不是引擎自带的那条:
```cpp
if (pType->Action == Action::None || pSWExt->SW_UseAITargeting)
    OutList.Add(EventClass(..., SpecialPlace, swIndex, CellStruct::Empty));
else
    CurrentSWTypeIndex = swIndex;      // + EVA_SelectTarget
```

★ **`SW_UseAITargeting` 不是可有可无的补充**: `WarheadSpecial1` 在 rulesmo.ini 里是 `Type=GenericWarhead` + `Action=Custom` ⇒ Ares 把 Custom 改写成 `Actions::SuperWeaponAllowed` (0x7F) ⇒ **光看 `Action==0` 判不出来**。它"点一下就生效"靠的是 emigdal.map 里的 `SW.UseAITargeting=yes` —— **这条键只在地图内嵌 ini 里有**, 于是它同时解释了"为什么以前只在 ini 里找 `Action=None` 永远判不对"和"为什么必须去拿合并规则"。

另一半 `Action == 0` 读对象字段: 引擎/Ares 建对象时已把**合并后**的 Action 写好, 而 gamemd 自带的侧栏点击处理 (`0x6AAF08 cmp dword [ecx+0xBC],edi`, ecx = `pSuper->Type`+0x28, edi=0) 判的也正是它 —— 引擎那条路**不看** UseAITargeting, 所以两个判据都得有。

`Action` 偏移 0xBC (四处互证, §1.0b)。实测值: `BlasticadeSpecial`/`HunterSeeker`/`Nanocharge`/`GearChange` = 0, 其余 127 = Ares 改写后的 `SuperWeaponAllowed`。

⚠ **`Action=Custom` 不是 `Action::None`**: Ares 在 `ExtData::LoadFromRulesFile` 里把 `Custom` 改写成 0x7F —— MO 基础规则里几乎所有超武都写了 `Action=Custom`, 只在 ini 里找 `Action=None` 是找不到的 (138 个类型里一次都命中不了)。

引擎侧两条出口 (gamemd `SidebarClass_ProcessClickCoords` 内, 离线反汇编):
```
6AAEF7..6AAF08  pSuper = HouseClass::Player->Supers[esi];
                cmp dword [pSuper->Type + 0xBC], edi(0)
6AAF0E  jne 0x6AAF46            ; Action != 0 -> 0x6AAF92 mov [0x8809A0],esi = CurrentSWTypeIndex
6AAF10..6AAF3C  EventClass(house, 0x12 SpecialPlace, Type->ArrayIndex, CellStruct{0,0})
```
所以"要不要点第二次地图"完全由 `Type->Action` 决定, 与鼠标位置无关。

### 释放方式 (联机铁律)

走 `EventClass::OutList` 塞标准 `SpecialPlace`, 引擎在 DoList 执行, 联机由 Mega/Connect 同步。**不写 `CurrentSWTypeIndex`** (本地 UI 态, 引擎当帧不会释放 → "点了没反应"; 且直接改模拟状态会破坏联机同步)。
- ctor `0x4C6B60` (`thiscall`, this=111 字节缓冲, houseIdx/Type/id/CellStruct)
- OutList: Count `0xA802C8` / Next `0xA802D0` / Buf `0xA802D4` / Par `0xA83A54`
- 事件 111B, 容量 `0x80`, `Next` 用 `(next+1)&0x7F`; 读回 `Next` 要**夹一次**
- 拷完调一次 `call [0x7E1530]` 无参回调, 返回 EAX 存 `Par[next]`; `houseIndex = [house+0x30]`, `CurrentPlayer = *(0xA83D4C)`; `EventType::SpecialPlace = 0x12`
- **ctor 之前必须清零 111 字节**: `EventClass` 是 pack(1) 且 `operator==` 是 `memcmp(...,111)`, 留栈垃圾会给联机同步埋雷
- **`Location` 传 `CellStruct::Empty` (0,0)** —— 与引擎点**原版侧栏**发出的那条逐字节一致 (已用抓包核对)。布局 `[0] Type / [1] IsExecuted / [2] HouseIndex / [3..6] Frame / [7..] DataBuffer`, 其中 `SPECIAL_PLACE { int ID@7; CellStruct Location@11; }`
- 无参回调必须用**普通函数指针调用**, 不能内联汇编 (§11 坑 7); 满了 (`count >= 0x80`) 返回 0 → 记 `sws: instant queued fail`, 仍吞掉这一击

### 火风暴类 (爆裂屏障/心灵之火): 做不到, 已过滤

`DrainSupers=0` 默认把 `UseChargeDrain=yes` 的整个过滤。Ares 两条**不相交**的入口:
```
SuperClass_Launch    @0x6CC390 -> Activate() -> NewSWType::Activate()
SuperClass_ClickFire @0x6CB920 -> ChargeDrain 开关状态机 (Ready<->Draining)
事件 -> 0x4C78D6 (Ares Networking_RespondToEvent_SpecialPlace) -> HouseClass::Fire_SW @0x4FAE50 -> Launch -> Activate
```
整条链都不经过 `ClickFire`, 而 ChargeDrain 开关逻辑只在 `ClickFire` 里 → 事件能把**效果**打出去 (围墙真的会激活), 但 `ChargeDrainState` 永远停在 `Ready`, 侧栏显示不出"生效中"。要真修得写引擎的 `ChargeDrainState`, 而那要先拿 `HouseClass::Supers` 偏移 —— YRpp 头推导值 `+0x180` 与先前估值 `0x384` 差 `0x204`, 不可信。**收益远小于风险, 别做。** 附: 手册说"可以手动关闭"只在 `SW.Unstoppable=no` 时成立, MO 给的是 `yes`。

## 9. 帧率: `0x4F42F0` 不是"每帧一次"

`SWS_Poll` 与同函数里其它 9 个 `*_Poll` 挂在 `0x4F42F0` (`MOExperience_PrepareEntry`)。当年注释写的"帧准备钩, 每循环必跑" —— **"每循环"被当成了"每帧"**。实测: gamemd 里 `call 0x4F42F0` 有 **113 个静态调用点**, 散在 AI / 对象 / 渲染 / 消息代码里, 多处位于**逐对象循环内**; 两个独立锚点交叉验证 → **每渲染帧 142 次** (区间 47~225)。

142 倍扇出 = 每帧 142× `GetAsyncKeyState` + 142×2 次 `QueryPerformanceCounter`; `SwsFireWatch` 的 78 次条目循环 → 每帧约 11,000 次迭代; `SwsScan` 的"每 15 次"其实是每 0.25 秒一次。**日志本身不是帧率杀手** (≈50~150 µs/帧), 真正的开销是扇出。已做: ①**帧门** —— `SWS_Poll` 开头读 `ADDR_FRAME` 与上次相同就直接返回; ②`SwsFireWatch`/`EvWatch` 挪进扫描节流并连同删掉; ③日志汇总周期 60 → 600 帧; ④布局/排序/像素全移进"重建"路径, §4。**还能砍的 (未做)**: 其余 9 个 `*_Poll` 同样在扇出里且被 `PowerDrawBoth` 无条件调用 = 最大剩余开销。

**教训**: 写钩子注释必须数一遍 `call <addr>` 的静态引用和它所在的循环层级 —— 真帧入口应该只有 1 个调用点。

## 11. 已确认的坑 (改代码前先看)

1. `0x87F7E8` 是对象本身, 不能解引用 (§2.1)。
2. **透明度函数约定相反**: `SwsCFillA` **内部已乘** `s_Alpha`, 调用方只给原始不透明度; `SwsCCov`/`SwsCFillR` **不乘**, 调用方才预乘 (给 `SwsCFillA` 传 `70*s_Alpha/100` 是乘两次)。只有悬停名提示框与悬停图标不吃 `Alpha`。
3. **缓存 blit 里有两套坐标系**: 目标列漏 `s_CchX` → 整块贴到画面最左边; 夹取写成"只有出画时才修正" → 内层多跑 `s_CchX` 次 → **整块侧栏被平铺糊满全屏**。正确: 目标列区间 `[0,surfW)` 平移成缓存内下标再与 `[0,s_CchW)` 取交, **两头都夹**。其它原语 (`SwsCFill`/`SwsCPcx`/`SwsCCov`) 都是先减原点→夹→一律缓存下标, 无此问题。
4. **单像素混合算术测试抓不到循环边界错**, **逐点测试也看不见"包含关系"** (提示框自身矩形对但缓存矩形没包住 → 截断; blit 像素对但循环边界没夹 → 平铺糊屏)。合成/拷贝必须另做**结构性**测试: 预填哨兵的合成面跑真循环, 逐像素断言"该写的写对 / a=0 的没动 / 矩形外一格没动"。
5. **探针扫内存必须跳过虚表指针**: offset 0 是代码地址, 被当结构读会顺着"文件名指针"二次解引用 → 必崩。**缓存槽位必须同时记 id**, 否则查找永远失配、槽位涨满后一律返 NULL。
6. **判新行/新字串的缓冲要清满**: 充能百分比那 8 字节 `wchar_t st[8]` 只清前 4 个, 第 5 个是栈垃圾 → `RenderLine` 把 "100%" 后的垃圾也画出来。
7. **内联汇编 clobber 列表必须完整**: 只声明 `ecx/edx/cc/memory` 而真实 `call` 还破坏 `ebx/esi/edi/ebp` → 崩在 `EAX=ESI=<代码地址>`。**已改成普通函数指针调用, 让编译器自己生成 `call`。**
8. **删代码时判断注释起点用 `lstrip().startswith("/*")`** (注释是缩进的), 否则脚本走错位置, "删掉了"其实没删。**用行切片改文件前先备份** —— 索引算错会一次性丢掉后面全部内容。构建校验看退出码 + DLL 时间戳, 不能只 grep `error C` (gcc 的 `error:` 无 C)。

## 12. 通用方法论

- **别拿"缺失"当证据**: 照抄 Phobos `LaunchSuper` 就以为 SpecialPlace 就够 (它根本没接 ChargeDrain); Firestorm 在 `SWTypes/` 里没有 `Action=None` 赋值就推断它需要选格 (而手册与 `SW_Firewall::Activate` 明说不用格子); 照抄有 bug 的代码。正确做法: **抓包 / 读被调用方源码**。
- **★ 拿上一版 `.o` 当回归基准**: 改完重新编译, `nm -C --defined-only` 逐个函数比**代码大小**; 只该变你动过的那几个。再用 `strings` diff 一遍字面量 —— 少一条日志往往就是删错了一个分支。同参数下 `-O2` 生成的代码是稳定的, 差 16 字节就是真差。这比"能编译"强得多, 也比进游戏试快得多。
- **扫 ini 挂载表** (`SuperWeapon=X` / `SuperWeapon2=X` / `SuperWeapons=a,b,c` 三种写法都要认、单值尾部 `]` 要 `rstrip`、逐行扫记当前节名、重扫要重置节名、CSF 键名统一小写): 属 rules 扫描范畴, 记在 `notes/超武列表.md`。
- **测试** (`test/`, `run-tests.bat`, 纯逻辑不加载 gamemd, 几秒): `sws_blit_test` 哨兵合成面跑真 blit 循环 13 种摆法; `sws_geom_test` 网格扫分辨率×MaxRows×Gap×ColGap×RightMargin×名字宽度×滚动位置, 断言每个画进缓存的元素都在缓存矩形内 + 折叠按钮不跳位; `sws_hover_test` 造"原序 ≠ 排序后"断言 `SwsHitItem` 经 `s_Order` 解析回同一条目; `sws_blend_test` 28 个混合算术数值例 (565/555、快路、alpha 饱和、无串位)。经验: geom 不变量要跟**夹取后**的值比; 加防空转守卫; **每套都做反向验证** (把 bug 版改回去确认它会红)。## 13. ### 正确做法 = 直接读 Ares 已经算好的结果

| 需求 | ExtData 字段 | 本机 3.0 偏移 | 证据 |
| --- | --- | --- | --- |
| 过滤（`ShowCameo=false` 不进侧栏） | `SW_ShowCameo` | **+0x1E5**（bool, 1 字节） | `0x1003347D` + `0x1003962C` |
| 一键生效（`UseAITargeting`） | `SW_UseAITargeting` | **+0x20E** | `0x100335C7` |
| 图标（`SidebarPCX`） | `SidebarPCX` | **+0x4B0**（定长串, 已小写化） | `0x10033B60` |
| 额外收紧 | `SW_ManualFire` | +0x1E2 | `0x10033451` |
| 自证校验 | `AttachedToObject` | +0x20 | ctor `0x10031909` |
| ExtData 大小 | — | **0x500** | `push 0x500` @ `0x10034701` |

字段偏移的求法固定为（`LoadFromINIFile` 里的模式）：

```
push <键名>;  push edi;  lea eax,[esp+18h];  push eax;
lea ecx,[esi+OFF];  call Valueable<T>::Read        ; esi = ExtData 基址
```

但**只认紧邻的那一对**，不要用 FIFO 配对（会漂）。

### 最硬的交叉验证：引擎自己的 AddCameo 判门

`HouseClass_UpdateSuperWeaponsUnavailable`（`0x1003961D`，对应源码
`src/Ext/SWType/Hooks.Update.cpp:186-193`）：

```
mov ecx, <ExtMap>;  push [eax+0x28];  call find
cmp byte ptr [eax+0x1E5], 0          ; ● SW_ShowCameo
jne -> AddCameo(0x1F, index)         ; ● 非零就加
```

⇒ `+0x1E5` 是 **1 字节 bool**，且**就是**引擎自己决定"进不进防御页"的那个值。
我们读它 = 与引擎逐位一致，不可能再出现"游戏里没有、侧栏里却有"。

### 键是**类型指针**，不是 ID 字符串（曾考错过）

- 源码 `ExtMap.Find(pSuper->Type)`（`Hooks.Update.cpp:188`）+ `_Container.hpp:226`
  `using key_type = base_type*`（`base_type = SuperWeaponTypeClass`）。
- 本机二进制同一条路（`0x10039624`）：`push [eax+0x28]`，
  同函数紧接着 `mov edi,[eax+0x98]` = `Type->ArrayIndex` → 反证 +0x28 取到的确实是
  `SuperWeaponTypeClass*`。
- `find` 的散列是对**指针自己的 4 个字节**（`movzx eax,bl` / `shr eax,8` /
  `xor 0x811C9DC5` / `imul 0x1000193`），全程不解引用 ⇒ 键只可能是指针。
- ⇒ 传错键时 `unordered_map` 只会查不到返回 NULL，不会崩，但也永远取不到 ExtData。

### 定位一律从 Ares 自己的指令里读地址（不写死绝对地址）

- `ExtMap` → 导出钩子体 `StripClass_Draw_SuperWeapon_PCX` 开头的 `mov ecx, <imm32>`
- `find()` → 同一段里 `E8 <rel32>` 的落点

⇒ 定位跟着 Ares 的代码走：不扫数据段、ASLR 后仍然对。找不到 / 落点不在映像内 /
签名对不上（见下）一律 fail-closed。

### 跨模块调用的签名必须核对（否则是崩溃而不是返回 NULL）

`find` 实测 `ret 4`（`0x10057CE3` = `C2 04 00`）→ **恰好 1 个栈参、自己清栈**。
我们是按指针跨模块调它：签名猜错 = 栈被清错 = 崩溃。
所以定位器里额外抠落点附近的字节核对 `C2 04 00`，对不上就整条 ExtData 路线停用
（退回 ini 快照，行为不倒退）。

### 其余细节

- 每个类型都有 ExtData：`SuperWeaponTypeClass_CTOR @0x6CE6F6` 里
  `SWTypeExt::ExtMap.FindOrAllocate(pItem)`（`Body.cpp:1160`）→ 取不到只有定位失败一个原因。
- ctor 把 `+0x4B0` 清 0、`+0x4D0` 置空（新建未配置的超武**安全地得到"无图标"**），
  不会回读到堆垃圾。
- 自证日志 `sws: act ...` 末尾加了 `x1`/`x0` = ExtData 取到没有。

### 图标抓取：光调 `RepaintSidebar` 抓不到（实测）

用户在 emigdal 地图上手动点"过滤/显示"按钮能一次救回图标，而按钮那条路除了
`RepaintSidebar` 之外**还走了 `AddCameo`**。只抄 `RepaintSidebar` 的 `SwsNudgePaint`
连催 32 次一个也没抓到。差别就在 `AddCameo`：它会把 super 挂到防御页的 cameo 槽上，
而抓取钩（`0x6A9958`）只在**槽被画**时才有机会拷像素。
⇒ `SwsNudgePaint` 改成复用 `SwsDedupRestore` 那条已被用户操作实证有效的路径
