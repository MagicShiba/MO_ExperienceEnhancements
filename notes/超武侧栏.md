# 超武侧栏 (SWSBar)

## Phobos 原理 (最小参照, 未入库全文)

- 位置: `references/Phobos/src/Ext/Sidebar/SWSidebar/` (`SWSidebarClass`,
  `SWColumnClass`, `SWButtonClass`, `ToggleSWButtonClass`)。
- 本质: 一组 `GadgetClass` 按钮列, 经 `GScreenClass::AddButton` 注册,
  由引擎输入/绘制管线统一驱动。
- 数据: `HouseClass::CurrentPlayer->Supers[superIdx]` (`SuperClass`:
  `IsPresent/IsReady/IsSuspended/RechargeTimer`, `SuperWeaponType`:
  `RechargeTime/Action/SidebarImage`)。
- 过滤: `SuperWeaponSidebar.Allow` (缺省取
  `RulesExt::SuperWeaponSidebar_AllowByDefault`) /
  `RequiredHouses` / `Significance >= RequiredSignificance` /
  `SW_ShowCameo`。
- 排序: `SuperWeaponSidebar.PriorityHouses` (本家优先) +
  `BuildType::SortsBefore(Special, ...)` (rules 顺序)。
- 布局: 左侧停靠, 列高 pyramid 递减 (`Pyramid`), 垂直居中;
  配置在 `[Sidebar]` (`SuperWeaponSidebar.Max/MaxColumns/Interval/
  LeftOffset/CameoHeight`)。
- 绘制: 图标 `SidebarPCX` (Ares, MO 全套 `*icon.pcx`) 或 SHP
  `SidebarImage`; 未就绪盖 `DARKEN_SHP`; 进度盖 `GCLOCK2_SHP`
  (`AnimStage`); 就绪/快捷键字走 `NameReadiness()`。
- 交互: 左键 `LaunchSuper` (需打靶→置 `Display::CurrentSWTypeIndex`
  进 targeting; `Action==None`/AI 靶→直发 `SpecialPlace` 事件);
  右键取消 (`CurrentSWTypeIndex=-1`); 开关掣翻
  `ScenarioExt::SWSidebar_Enable`。
- 点击吞没: `DisplayClass::ProcessClickCoords` 内 `0x692419`
  (7B: `movsx ecx,[esi]` + `movsx edx,[esi+2]`, 无 rel),
  落自家按钮区跳 `0x6925FC`。

## 本移植取舍 (见 `src/SWSBar.cpp`)

- 不建 Gadget (虚表/GameCreate 配重太大): 纯覆盖层, 渲染挂
  `MOExperience_MessageDrawHook` (Composite 面), 输入靠轮询 +
  `0x692419` 吞没门 (同点同去向, 首 7B 实测无 rel, 见构建记录)。
- 只要图标不要 UI 资源: 不加载 Phobos 那套 On/Off/Top/Center/
  Bottom PCX; 图标盒 60x48 自画 (底 + 阵营色边框 + 名/状态字 +
  进度条)。MO 图标本体是 Ares `SidebarPCX`, 读 Ares 扩展内存
  成本过高, 故图标暂用文字盒占位 (后续可经 `0x4AED70`
  `CC_Draw_Shape` 补 SHP/PCX, 接口已留)。
- 超武/支援技能同注册类型 (`SuperWeaponTypes`), 不区分;
  显示门 = `Owner==本家 && IsPresent` (Phobos 摘牌逻辑同义)。
- 4 列右置 (盟/苏/厄/焚风), 空列隐藏; 归属内建表 96 个
  (由 `rulesmo.ini` 离线推导: 授予建筑 `SuperWeapon*=` +
  `Owner`/`Prerequisite` 链, 脚本见构建记录), 查不到落玩家
  阵营列 (`Scenario.PlayerSideIndex`, 读不到回 0)。
- 单节 `[SWSidebar]`: 全局键 + 超武 ID 键共处一节。
  值语义: 负数=隐藏, 0=默认 (优先级 1000), 正数=优先级
  (越小越靠前, 同值按 ArrayIndex)。缺键=默认显示。
- `ToggleKey` (默认 F4) 显隐, 隐藏即不占空间 (不画+门放行)。
- 点击: 左键图标只写 `Display+0x11B8` (`CurrentSWTypeIndex`,
  UI 态, 非模拟, 联机安全); 右键栏内写 -1。
  `Action==None` 的直发类本版也只进打靶 (limitation)。
- 偏移全 fail-closed: 数组/指针/ID 可打印/`swIdx` 范围/
  标志位 0/1 任一不满足即跳过该项; 扫描零命中即不画。

## 启动崩溃根因与修复 (0.2.154a 首版)

- 现象: Syringe 挂钩成功 (1477 hooks), DLL 初始化走完
  (`MOExperience 0.2.154a start`), 约 4 秒后进程 fault。
- 定位: 首个异常 EIP 落在 `SWS_Poll+0x1AC`, 指令
  `mov eax,[edx+0x1C]` (`type = *(sup+0x1C)`), EDX=0x404E0000。
  调用链 (栈回溯): `PrepareEntry → PowerDrawBoth → SWS_Poll`。
  启动期超武数组半初始化 (Items 非空但条目是垃圾),
  `IsPlausiblePtr` 只判下界, 垃圾指针通过后解引用 fault。
  Syringe 吞掉首异常继续执行, 游戏随后在字体光栅循环
  (0x497AE3/0x497AFC, `mov dx,[eax]` 取字形) 连环 fault。
- 修复: 组合门控 (见 `SwsScan`): 先纯安全读
  (超武 Items/Count + House Items/Count + 本家五元组),
  任一与上一轮不同则只缓存、本轮返回 (内容零解引用);
  五元组稳定后再做入局检查 (本家须在 House 数组内) 与逐项全校验。
- 教训: 凡是扫整表 (数组内容) 的新模块, 一律先稳定门控再碰内容;
  固定地址字可随便读, 指针内容不行。

## 2026-09-29 图标链路定案 (PCX, 走引擎现成设施)

结论: MO 的超武图标**不是 SHP**。`rulesmo.ini` 里 96 个超武节用
`SidebarPCX=xxx.pcx`, `SidebarImage` 出现 1 次、`Cameo` 0 次; PCX 打包在
`expandmo*.mix` / `thememo.mix` 里, 磁盘上没有。所以 `SidebarImage` 指向
引擎的 `XXICON.SHP` 占位引用, 画出来必然是**同一个紫球** (11 个条目
指针完全相同)。

最终链路 (全部引擎现成设施, 与 Phobos `SWButtonClass::Draw` / Ares
`Misc/Cameos.cpp` 同款):

1. 读键: `*(CCINIClass**)0x887048` (游戏已加载好的 rules 对象, 走 MIX)
   -> `INIClass::ReadString` @ `0x528A10` 读 `<超武ID>` 节 `SidebarPCX=`
2. 载图: `PCX::Instance` = `0xAC4848` (**`this` 就是该地址本身, 不能解引用**;
   `DEFINE_REFERENCE(PCX, ...)` 类型是 `PCX` 不是 `PCX*`)
   -> `GetSurface` @ `0x6BA140`, 未命中则 `ForceLoadFile` @ `0x6B9D00`
3. 贴图: `PCX::BlitToSurface` @ `0x6BA580`, 矩形 `{x,y,60,48}`,
   目标面**用 SWS_Draw 收到的 surf**, 色键 `COLOR_PURPLE=0xF81F`
4. 无 PCX 时才回退 SHP: 跟随 `SHPReference::Data`(+0x0C) / `GetData()`
   @ `0x69E580`, 再 `CC_Draw_Shape` @ `0x4AED70` (`__fastcall`, ECX=surf,
   EDX=palette, 其余 14 个压栈)

### 三个决定性坑 (都曾表现为"图标不对"或崩溃)

- `PCX::GetSurface` 在文件**未加载时不返回 NULL**, 而是直接给一张占位
  surface。必须**无条件先 `LoadFile`**, 否则 11 个图标 blit 的全是同一张
  占位图 (症状: 全是紫球, 但日志显示 "pcx ok")。
- 引擎的 `BSurface*` **绝不能跨帧缓存**。引擎切页签/重载美术时会释放并
  重建 PCX surface; 缓存的指针变野指针 -> 平时画成脏图, 切页签时崩溃。
  现在只缓存**文件名**, surface 每帧现取。
- 硬编码 `DSurface::Composite` = `0x88731C` 在本机 Ares 构建里**不是**
  surface 对象 (该处虚表为 NULL), `BlitToSurface` 内部一调虚函数就跳 0
  (转储: `EIP=0, ECX=0x88731C`, 返回地址 `0x6BA597`)。用 SWS_Draw 的
  `surf` 参数。

## 本机 (Ares 3.0) 地址可信度表 —— YRpp 地址不能直接信

游戏实际跑的是 **Ares 3.0** (`syringe.log`: "Applying Ares 3.0",
`Ares.dll` 20.333.289), 不是 YRpp 基线 gamemd。以 `Ares.dll` 的
`.syhks00` (1448 条 hook) 为准:

| 地址 | 含义 | 本机可信? |
|---|---|---|
| `0x528A10` | `INIClass::ReadString` | **被 Ares inline hook** (`INIClass_GetString`, sz=5)。drop-in 替换, 语义一致, 可调 |
| `0x88731C` | `DSurface::Composite` | **不可信** (虚表 NULL) |
| `0x6B9D00/0x6BA140/0x6BA580` | PCX 加载/取面/贴图 | 可信 (Ares 自己也在调) |
| `0xAC4848` | `PCX::Instance` (this) | 可信 |
| `0x4A38D0` | `LoadWholeFileEx` | 可信, 但读 rulesmo.ini 实测拿不到文本 |
| `0x4AED70` | `CC_Draw_Shape` | 可信, 但必须 `__fastcall` |
| `0x69E580` | `SHPStruct::GetData` | 可信 |
| `0x887048 / 0x87F6B0 / 0xA8E330 / 0x473C50` 等数据全局 | | 可信 |

Ares 3.0 自己读 `SidebarPCX=` 并在 `0x6A9952 / 0x6A9A43` 画 PCX cameo ——
原版侧栏里那些正常图标就是 Ares 加载的这一批 PCX。

## 其它已确认的坑

- 探针扫内存时**必须跳过虚表指针**: offset 0 是 0x004xxxxx 的代码地址,
  被当成 SHP 结构读会顺着"文件名指针"二次解引用 -> 必崩。同理不要顺着
  野指针打字符串。
- `SwsPcxFileOf` 建槽位时**必须 `SwsCopyId` 记 id**, 否则查找永远失配、
  槽位涨满后一律返回 NULL (曾导致 PCX 分支静默失效, 全体回落紫球)。
- 删代码时判断注释起点要用 `lstrip().startswith("/*")` —— 注释是缩进的,
  否则脚本会一路走错位置, "删掉了"其实没删 (那个图标探针因此赖了很多轮)。
- **构建校验必须看退出码 + DLL 时间戳**, 不能只 grep "error C": gcc 的
  `error:`(无 C) 不匹配, 曾连续多轮报告"构建成功"而 DLL 根本没更新。

## 上下滚动 + 滚动条 (2026-09-29 22:05)

参照项目里已有的**战役框/主要信息框**滚动 (`MOExperience.cpp` 的
`DrawBox` 战役分支 + `MOExperience_WheelHook`), 没另造一套:

- 滚轮钩子 `0x777998` (`MOExperience_WheelHook`, 6B) 本来就在, 读
  `wparam = *(unsigned*)(regs + OFF_REG_ECX)`, 高位 `0x80000000` = 上滚。
  现在先问 `SWS_WheelIn(mx,my,dir)`: 命中超武栏就滚超武栏并 `return 0`
  (不再滚战役框); 没命中才走原来的战役框逻辑。
  **SWS 判定必须在 `g_CampValid` 之前**, 否则战役框无效时超武栏滚不动。
- 侧栏滚动 `0x533F50` (`MOExperience_SidebarHook`, 5B) 也加了同样的
  `SWS_OverBar` 判定, 免得同一滚既滚超武栏又滚原版侧栏。
- 新导出: `SWS_WheelIn(int mx,int my,int dir)` / `SWS_OverBar(int mx,int my)`
  (`SWSBar.cpp`, 声明在 `SWSBar.h`)。都是只读几何 + 改我们自己的偏移。

### 面板级偏移 (不是逐列)

`[SWSidebar] ColGap=0` (默认也改成 0) 之后列之间没有空隙, 4px 的滚动条
塞不进列间 —— 逐列各画一根会直接盖在下一列上。所以:

- 偏移从 `s_Scroll[4]` 变成单个 `s_Scroll`, **所有列一起上下滚**
  (和战役框整框一个偏移同思路)。
- 滚动条整块右侧一根: `barX = 最右列 x + IconW + 1`, 4px 宽。
  轨道 `RGB(30,30,30) alpha 55` / 滑块 `RGB(170,170,170) alpha 90`,
  与战役框完全同参 (半透明、压暗、不抢眼)。
- 滑块: `thumbH = barH * vis / 最长列条目数` (下限 8px),
  `thumbY = barY + (barH-thumbH) * (maxSk - scroll) / maxSk`。
- **有列装不下时整块左边让出 5px** (`xStart = w - RightMargin - totW - 5`),
  否则滚动条会顶出屏幕右缘。

### 三个踩过的坑

1. **滚动上限**: 原来写 `clamp(s_Scroll[f], 0, colCount[f]-1)`, 能一路滚到
   只剩最后一行、中间全空。正确是 `colCount[f] - 可见行数`。
2. **列底框高度**原来用 `colCount` (全部条目数) 而不是可见行数, 框会一直
   拉到二十几行 —— 画面里那几根长条就是这么来的。
3. **命中判定要跳过 `x < 0`**: 滚出可见范围的条目 `x` 被置 -1, 但
   `mx >= -1 && mx < -1+60` 对屏幕左侧整条竖带恒真, 会把不可见条目当命中。
   `SWS_Poll` 的点击循环里必须 `if (s_Items[k].x < 0) continue;`。

### 新增 ini

```
[SWSidebar]
ColGap=0      ; 列与列之间的水平间距 (像素)
ScrollStep=1  ; 滚轮每次滚动的行数 (超武面板)
```

`ScrollStep` 每次滚轮都调 `GetPrivateProfileIntA` 读, 便于改完 ini
直接生效, 不用重启。

## 三个问题 (2026-09-29 22:27)

### 1) 滚轮方向反

战役框 `wparam & 0x80000000` 时是 `g_Skip -= step` (看更新的), 超武栏却是
`dir<0 -> s_Scroll -= step` (看更靠前的)。同一个高位在两处含义不同, 实际
手感是反的。改在调用点 (`MOExperience_WheelHook`) 传反 dir:

```c
if (SWS_WheelIn(mx, my, (wparam & 0x80000000u) ? 1 : -1)) return 0;
```

> 注意: 0x80000000 到底是"上滚"还是"看更新", 只有实测为准。以后再动这里
> 先按"战役框是基准"对齐, 别按字面理解。

### 2) 百分比

- `1%` 显示成 `001%`: 原来固定写三个数字 (`pct/100`, `(pct/10)%10`,
  `pct%10`)。改成按位数输出: `>=10` 两位, 否则一位。
- `100%` 不显示: `it->ready` 分支整个去掉。就绪与否图标本身能看出来
  (未就绪有压暗), 再叠一层 100% 只是多一次 GDI 文本渲染, 还压住图标。
  顺带 `pct` 上限从 100 收到 99 —— 满格就是就绪, 归上面那个分支管。
- 文本颜色统一 255 白 (原来 ready 时给 160 灰, 现在 ready 根本不画)。

### 3) "点击即生效"的超武点了没反应 (最重要)

**根因不是延迟, 是释放方式错了。** 原来对 `Action==None` 的条目是
"当帧写 `CurrentSW` + 不吞这一击, 让引擎自己释放" —— 错在:

1. `CurrentSW` 只是**本地 UI 状态**。引擎不会因为它被写了就去释放超武,
   所以当帧写、当帧期待引擎动作 = 什么都不会发生。
2. 就算引擎会看 `CurrentSW`, 我们是"自己写模拟状态" —— 违反联机铁律
   (见 AGENTS.md), 联机必然不同步。
3. 还有一层: `0x692419` 那个门的兜底分支 (`mx/my` 落在栏内就返回
   `ADDR_CLICKGATE_SKIP`) 会**无条件吞掉**栏内点击, 就算没设
   `s_EatPress`/`s_HoldSkip` 也照吞。所以"放行这一击"根本没发生过。

**正确做法 = Phobos 的做法** (`SWButtonClass::LaunchSuper`):

```cpp
if (pType->Action == Action::None || pSWExt->SW_UseAITargeting)
    EventClass::OutList.Add(EventClass(pCurrent->ArrayIndex,
        EventType::SpecialPlace, swIndex, CellStruct::Empty));
```

即"往 `EventClass::OutList` 塞一个 SpecialPlace 事件", 由引擎在 DoList
里统一执行 —— 这就是 AGENTS.md 说的"标准事件广播", 联机由
Mega/Connect 同步。

`SwsPushSpecialPlace()` 照 `BuildQueue.cpp` 的 `BQ_FireProduce()` 写
(那套 OutList 追加已经在本项目里验证过):

- ctor `0x4C6B60` (`thiscall`: this=111 字节缓冲, houseIdx/EventType/
  id/CellStruct)
- OutList: Count `0xA802C8`, Next `0xA802D0`, Buf `0xA802D4`, Par `0xA83A54`
- 事件 111 字节, 容量 0x80, Next 用 `(next+1)&0x7F`
- 拷完调一次 `call [0x7E1530]` 无参回调, 返回 EAX 存并行数组
- `houseIndex = [house+0x30]`, `CurrentPlayer = *(0xA83D4C)`
- `EventType::SpecialPlace = 0x12` (**不是**猜的 0x1D; YRpp
  `GeneralDefinitions.h` 有权威值)

要点:
- 队列满 (0x80) 时返回 0, **这一击照旧吞掉**, 别漏到地图上变成误下单。
- 入队成功后**仍然吞掉这一击** (`s_EatPress/s_HoldSkip=1`): 点击落在
  侧栏上, 不能漏给引擎的 `ProcessClickCoords`。
- 于是 `s_InstantPass` 那个标志彻底删掉了 —— 事件方案不需要放行。

### 顺带记: 两个"静默失效"陷阱

1. **命中判定要 `if (x < 0) continue;`**: 滚出可见范围的条目 `x=-1`,
   而 `mx >= -1 && mx < -1+60` 对屏幕左侧整条竖带恒真。
2. **门的兜底分支会吞掉一切栏内点击**: 想"让某次点击通过引擎"不能靠
   不设标志, 那个 `else if` 兜底分支还在。要放行必须像上面那样从
   `if` 链最前面开口子, 或者干脆改用事件 (本例选了后者)。

## 崩了: 内联汇编 call 的寄存器破坏 (2026-09-29 22:29 -> 22:33)

### 现场

`syringe.log`:

```
Exception (Code: 0xC0000005 at 0x737080C4)!
The process tried to write to 0x00DFB0E8.
EAX = 0x400DDDA5  ECX = 0x00002710  EDX = 0
EBX = 0x00000073  ESP = 0x001AD0E0  EBP = 0
ESI = 0x400DDDA5  EDI = 0x00000001  EIP = 0x737080C4
```

判读:

- `EIP=0x737080C4` 在**我们自己的 DLL** 里 (gamemd 只到 `0x497110`),
  所以崩的是我上一轮加的 `SwsPushSpecialPlace()`, 不是引擎、更不是别的模块。
- `EAX = ESI = 0x400DDDA5` 是 **gamemd 的代码地址**。一个"数据指针"位置
  上放着代码地址, 是典型的寄存器被当成指针用了。
- 写目标是近 NULL (`0x00DFB0E8`)。
- 崩溃发生在 `22:29:11`, 也就是点完"点击即生效"超武的瞬间。

### 根因: `__asm__` 里的 `call *%1` 少报了被破坏的寄存器

BuildQueue 的 `BQ_FireProduce()` 里那段 (我照抄过来的):

```c
__asm__ volatile (
    "call *%1\n\t"
    "movl %%eax, %0"
    : "=r" (eaxAfter)
    : "r" (snd)
    : "ecx", "edx", "cc", "memory");
```

问题在 clobber 列表: 真实的 `call` 会破坏 **`ebx`/`esi`/`edi`/`ebp`**,
这里一个都没写。于是编译器认为"这个汇编前后 `esi` 还是我自己的值",
可以放心留着; 实际 `call` 回来 `esi` 已经被 callee 改成别的东西了。
后面代码再拿这个寄存器当指针写内存 —— 写到了近 NULL, `0xC0000005`。

BuildQueue 里同一段代码是**潜伏的**, 之前没炸是因为那条路径
(`ADDR_OUT_PAR` 写的是绝对地址) 恰好没用到被破坏的寄存器做指针。
**照抄危险代码 = 把危险一起抄过来。**

### 修法: 不用内联汇编, 直接函数指针调用

```c
cb = *(void**)0x7E1530u;
if (cb && IsPlausiblePtr(cb))
    eaxAfter = (unsigned)(size_t)((int (__cdecl *)(void))cb)();
else
    eaxAfter = 0;
```

让编译器自己生成 `call`, 它会按 ABI 保存/恢复该保存的寄存器, 不会有
"以为寄存器还是自己的"这种问题。顺带加了三道保险:

- `next = *(unsigned*)SWS_ADDR_OUT_NEXT & 0x7Fu;` —— 读回来就夹一次。
  它是环形计数器的 Tail, 引擎自己会掩码推进; 万一读到脏值, 也不能拿它
  当 `0xA802D4 + next*111` 的下标去写。
- `swIdx` 范围检查 (`0..0xFFFF`), 以及 `cb` 本身的 `IsPlausiblePtr`。
- 事件缓冲 `ev[111]` 照旧, 与 BuildQueue 同尺寸。

### 保险丝: `InstantEvent` (默认 0)

这条路要动引擎事件队列, 地址/布局一旦在某平台不对就是**崩游戏**, 而
"这个超武点了没反应"只是功能缺失 —— 两者不对等。所以加了开关:

```
[SWSidebar]
InstantEvent=0   ; 1=走引擎 SpecialPlace 事件, 0=关 (默认, 安全)
```

关着的时候点"点击即生效"的超武退回报原来的延一帧上膛, 不碰引擎事件
队列, 至少不会崩。确认地址没问题再在 ini 里开 1 试。

> **教训**: 引擎事件队列这类"手写 OutList 追加"的活, 宁可慢也不能崩。
> 另外, 复用别人代码前要问一句"这段为什么这么写" —— BuildQueue 那段
> 汇编能跑通只是因为运气, 不是因为它对。

### EventClass 真实布局 (解出来了)

YRpp `EventClass.h`, `#pragma pack(1)`:

```
[0]      EventType Type        (1B)
[1]      bool     IsExecuted   (1B)
[2]      char     HouseIndex   (1B, '-1'=无效)
[3..6]   unsigned Frame         (4B, 事件应在哪一帧执行)
[7..110] union DataBuffer[104]
           SPECIAL_PLACE { int ID @7; CellStruct Location @11; }   // Location = 2×short = 4B
```

逐字节对照 (`id=47` 那两条):

| 偏移 | 引擎 | 我们 | 含义 |
| --- | --- | --- | --- |
| `[0]` | `12` | `12` | SpecialPlace ✓ |
| `[1]` | `00` | `00` | IsExecuted=false ✓ |
| `[2]` | `00` | `00` | HouseIndex=0 ✓ |
| `[3..6]` | `35 6B 1B 00` | `36 6C 1B 00` | Frame=0x001B6B35 / 0x001B6C36 (≈179万帧, 相隔 257 帧) ✓ ctor 自己填了当前帧 |
| `[7..10]` | `2F 00 00 00` | `2F 00 00 00` | SpecialPlace.ID=47 ✓ 完全一致 |
| `[11..14]` | `00 00 00 00` | `00 00 00 00` | Location=(0,0) Empty ✓ |
| `[15..19]` | `00 90 50 59 08` | `00 73 11 00 00` | **ctor 不碰的残留垃圾** |

**结论: SpecialPlace 事件路线是对的。** 引擎自己点即时超武走的就是
`EventType::SpecialPlace(0x12)`, 和 Phobos `LaunchSuper` 一致。我们构造的
事件在所有语义字段上与引擎逐字节相同。

### 顺带修掉一个真 bug: 事件缓冲没清零

上面 `[15..19]` 引擎那边也是垃圾, 但**我们这边本来更糟**: 我在改成"单独一块
CellStruct"时, 把 `for (i...) ev[i] = 0;` 的清零循环顺手删掉了, 于是
`char ev[111]` 是**未初始化栈垃圾**。

`EventClass::operator==` 是 `memcmp(this, &q, sizeof(q))` 即**整 111 字节
比较**, 留垃圾等于给联机同步埋雷。已加回清零 (ctor 之前), 清零是确定值,
比学引擎留垃圾安全。

### 为什么之前"还是需要点两次"

上一轮用户报"需要点两次"时, `InstantEvent` 保险丝还是**关**的, 走的是
`s_PendSel` 延一帧上膛 —— 那本来就是手动打靶流程 (点图标→点地图), 两下是
预期。删掉保险丝后才是真正的事件路径。所以那个反馈**不能**用来判断事件
路线对不对, 这次抓包才是。

### 新增: IsExecuted 追踪 (证明引擎真的执行了)

之前只能证明"事件进了队列", 证明不了"引擎执行了" —— 这正是查不下去的

## 释放侦测出结果 + 即时类其实分两类 (2026-09-29 22:55)

### 用户补充: 即时类分两类, 行为不同

## 帧率掉了: 每帧读 ini, 而且藏在 perf 盲区里 (2026-09-29 23:14)

### 现象

`d` (绘制耗时) 走势其实是**在变好**的 (日志跨了多次运行, 直写 blit 那版生效):

```
seg1 d_avg=2142us   seg3 d_avg=7756us   seg5 d_avg=2063us
seg2 d_avg=3296us   seg4 d_avg=4314us   seg6 d_avg=1416us
```

但玩家报帧率很低。矛盾点就在这里 —— **日志看着正常, 实际很卡**。

### 根因: `SwsFireWatch` 每帧 `GetPrivateProfileIntA`

```c
static void SwsFireWatch(void)
{
    if (!GetPrivateProfileIntA(SWS_SECTION, "FireWatch", 1, g_IniPath)) return;
    ...
}
```

`GetPrivateProfileIntA` 每次调用都会**打开并解析 ini 文件**。这函数在
`SWS_Poll` 里每帧跑一次 = **每帧一次文件 I/O**。这是上一轮加"释放侦测"
时顺手写的, 完全没意识到成本。

同类的还有两处 (量级小些):

- `SWS_WheelIn()` 每次滚轮读 `ScrollStep` (滚轮事件不算高频, 但仍是 I/O)
- `SwsEventWatch()` 读 `EvWatch` —— 这个当时用了 `static s_WatchOn` 缓存,
  所以侥幸没中招, 但写法上同样危险

### 为什么 perf 日志看不见

`SWS_Draw` 的计时 (`d`) 和 `SwsScan` 的计时 (`s`) 是两段独立区间,
**`SWS_Poll` 里发生的一切完全在盲区**。所以:

- 每帧一次 ini 文件 I/O 的开销不会计入 `d`, 也不会计入 `s`
- 日志显示 `d=1416us s=4us`, 看起来"很健康"
- 而这一帧真实的额外成本在别处

**这类"测不到的开销"比慢本身更难查。**

### 修法

1. **所有 ini 读取收敛到 `SwsEnsureInit`** (只跑一次):
   - `EvWatch` / `FireWatch` / `ScrollStep` 三个新键改读缓存全局量
   - `SWS_WheelIn` 改用 `s_ScrollStep`
   - 复查确认: 现在 `SWSBar.cpp` 里 `GetPrivateProfileIntA` **只出现在
     `SwsEnsureInit` 内** (418~456 行) 和注释里
2. **补上盲区**: `SWS_Poll` 首尾加 QPC, 每游戏帧汇总记一行 `sws: poll <us>`。
   以后 Poll 侧再出这种东西, 日志里立刻看得见。

> **教训**: 诊断代码的性能成本和功能代码一样要付钱。新加"每帧跑"的
> 辅助函数时, 先问一句它有没有文件 I/O / 分配 / 锁; 并且**计时范围要覆盖
> 所有每帧路径**, 否则加诊断本身就会制造看不见的卡顿。

每次都 FIRED; drain 类 (47 爆裂屏障 / 102 心灵之火) 推了 7 次一次没中。**
队列正常 (queued fail=0, Count 恒 1), 所以不是没塞进去。

### 为什么 drain 类事件无效

Ares `SuperClass_ClickFire` (0x6CB920) 的 ChargeDrain 状态机:

```cpp
if(pType->UseChargeDrain) {
    if(ChargeDrainState == Draining) { ...关闭... }
    else if(ChargeDrainState == Ready) { ...激活... }
    return ret(false);          // 两个分支都不命中就直接返回
}
```

超武还在 `Charging` 时点它, **两个分支都不进, 什么都不发生**。
`SwsDrainWatch` 的跳变日志印证: 47/102 一直停在 `Charging`, 从没到过
`Ready`/`Draining` —— 而 tbl 快照里出现过 `Ready`, 说明它确实在推进,
只是推完之前点击无效。

### 回归: 点完 drain 类之后别的武器第一次点击也失效

时间点吻合 —— 上一轮给事件加上"真实鼠标格"之后立刻出现。之前事件传
`CellStruct::Empty(0,0)` 时引擎根本不执行 (`[1]` 恒 `0x00`), 也就没有
副作用; 改成真实格之后引擎开始部分消费, 干扰了输入。

**处置: drain 类先退回打靶路径** (`s_PendSel` + 吞掉整段按住), 也就是
"点图标 -> 点地图" 两步 —— 至少是**可用**的, 而且不再有"下一次点击失效"。
一次点击的问题等逐字节对比数据到手再定。

> 教训: 一次只改一个变量。我这轮同时改了 (a) 事件传真实格 (b) drain 类
> 改成 instant, 两个都作用在同一条点击路径上, 结果 (a) 的副作用被误记到
> (b) 头上, 而 (b) 本身又依赖 (a) 成功。混在一起就分不清是谁的锅。

### 仍待解决: drain 类如何做到一次点击

已就位的取证 (下一轮日志里能直接看):

- `sws: push h=<house> id=<n> <32字节hex>` —— **我们自己构造的事件**前 32 字节
- `swsev: t=18 h=0 SP id=... cell=... <32字节hex>` —— 引擎自己发的事件
- 两者同格式, 可以直接 diff, 找 drain 类差在哪个字节
- `sws: clk notready` —— 点击落在未就绪图标上 (用来定位"点击失效")
- `sws: instant` / `sws: instant drain` —— 事件派发结果

## 链路彻底查清: 事件走 Launch, 开关状态机在 ClickFire (2026-09-29 23:59)

### 逐字节对比 (第二轮: 用户点**原版侧栏**, 地面真值)

```
引擎(原版侧栏) id=47 : 12 00 00 17511B00 2F000000 00000000 00 | 90506D08 F0D21A00 AD020000
引擎(原版侧栏) id=102: 12 00 00 29501B00 66000000 00000000 00 | 90506D08 F0D21A00 BB010000
引擎(原版侧栏) id=53 : 12 00 00 C2541B00 35000000 00000000 00 | 90506D08 F0D21A00 60060000
我                   id=47 : 12 00 00 CB631B00 2F000000 00000000 00 | 00000000 00000000 000000000
我                   id=102: 12 00 00 80671B00 66000000 00000000 00 | 00000000 00000000 000000000
```

**`[0..15]` 结构完全一致, `cell` 都是 `0,0`, `[1]` 都是 `0x00`。**

=> 我上一轮那两个结论**都是错的**:
1. "必须传真实鼠标格" —— 错。引擎点自己侧栏就是传 `CellStruct::Empty`。
   那些 `cell=242,125` 的事件是**别的路径**(AI/触发)产生的, 我拿它当基准了。
2. "`[1]=0x5A` 是已执行标志" —— 错。原版侧栏的事件 `[1]` 也是 `0x00`。
   `0x5A` 只出现在另一类事件里, 与本问题无关。

唯一差异是尾部 `[16..27]`: 引擎恒为 `90506D08 F0D21A00` + 4 字节变化值,
我因清零缓冲是全 0。其中 `[20..23]=0x001AD2F0` 是**栈地址**(事件对象自身
地址), 属构造残留, 非语义字段。**结论: 我的事件结构是对的。**

### 真正的根因: 事件走 Launch, 开关状态机在 ClickFire

Ares 两条不同的入口:

```
SuperClass_Launch   @0x6CC390  ->  SWTypeExt::Activate()  -> NewSWType::Activate()
SuperClass_ClickFire @0x6CB920  ->  ChargeDrain 开关状态机 (Ready<->Draining)
```

`SWTypeExt::Activate` 内部:
```cpp
if(auto const pNewType = pExt->GetNewSWType()) {
    if(!SWTypeExt::Launch(pSuper, pNewType, cell, isPlayer)) return false;
    ...
    SpringHouseTags(pThis->Owner, AresTriggerEvent::SuperActivated, pSuper);
    return true;
}
```

**SpecialPlace 事件 -> Networking_RespondToEvent_SpecialPlace @0x4C78D6
-> SuperClass::Launch -> Activate。整条链都不经过 ClickFire。**

而 ChargeDrain 的开关逻辑**只**在 ClickFire 里:
```cpp
if(pType->UseChargeDrain) {
    if(ChargeDrainState == Draining) { ...关闭... }
    else if(ChargeDrainState == Ready) { ...激活... }
    return ret(false);
}
```

所以对爆裂屏障/心灵之火发 SpecialPlace 事件:
- `Launch` -> `Activate` -> `SW_Firewall::Activate` 会被调用
  (它 `SetFirestormState(true)`, 看起来"应该有效")
- 但 **`ChargeDrainState` 永远不会变成 `Draining`** —— 没人写它
- 于是侧栏读到的状态还是 `Ready`, 自然没有 ON 文本
- 而且下次点击仍然被当成"激活", 状态机依然不前进

这也解释了 47/102 推了 7 次 `FIRED` 一次没有: 计时器重置没发生,
`ready` 边沿检测当然抓不到。**不是事件没被执行, 是执行了但没走该走的路。**

对照: 非 drain 类 (53/73/100) 走 `Launch` 就够了, 所以全部成功。

### 我的日志有个差一错误

```c
static const char* kName[4] = { "None", "Charging", "Ready", "Draining" };
```

但枚举是 `-1=None 0=Charging 1=Ready 2=Draining`。`kName[0]` 应该是
`"Charging"`。所以日志打出的 "Charging" 实际是**状态 1 = Ready** ——
这两个超武**本来就是就绪的**, 不是"没充好所以点不动"。差一错误让我
差点得出错误结论。

### 修法方向 (未实施, 待定)

要让 drain 类一次点击生效, 必须让引擎走 **ClickFire** 而不是 Launch。
可选:

1. **不自己塞事件**, 改为写 `CurrentSWTypeIndex` 让引擎自己进打靶流程
   —— 但那是两步点击, 不满足需求。
2. **hook `SuperClass_ClickFire` (0x6CB920)**, 在我们自己点击即时超武时
   主动走一遍 ClickFire 的状态机。但这是"本地直接调用会改模拟状态的
   引擎函数", **违反联机铁律**(AGENTS.md), 除非同时保证事件已广播。
3. **hook `Networking_RespondToEvent_SpecialPlace` (0x4C78D6)**, 在事件
   执行时对 UseChargeDrain 类型补跑状态机 —— 相当于修正 Ares 的这条链,
   事件仍然照常广播, 联机安全。**这是最合规的方向。**

需要用户确认走哪条。
