# 超武侧栏 (SWSBar)

## Phobos 原理 (最小参照, 未入库全文)

- 位置: `references/Phobos/src/Ext/Sidebar/SWSidebar/` (`SWSidebarClass`,
  `SWColumnClass`, `SWButtonClass`, `ToggleSWButtonClass`)。
- 本质: 一组 `GadgetClass` 按钮列, 经 `GScreenClass::AddButton` 注册,
  由引擎输入/绘制管线统一驱动。
- 数据: `HouseClass::CurrentPlayer->Supers[superIdx]` (`SuperClass`:
  `IsPresent/IsReady/IsSuspended/RechargeTimer`, `SuperWeaponType`:
  `RechargeTime/Action/SidebarImage`)。
- 过滤: `SuperWeaponSidebar.Allow` (缺省取
  `RulesExt::SuperWeaponSidebar_AllowByDefault`) /
  `RequiredHouses` / `Significance >= RequiredSignificance` /
  `SW_ShowCameo`。
- 排序: `SuperWeaponSidebar.PriorityHouses` (本家优先) +
  `BuildType::SortsBefore(Special, ...)` (rules 顺序)。
- 布局: 左侧停靠, 列高 pyramid 递减 (`Pyramid`), 垂直居中;
  配置在 `[Sidebar]` (`SuperWeaponSidebar.Max/MaxColumns/Interval/
  LeftOffset/CameoHeight`)。
- 绘制: 图标 `SidebarPCX` (Ares, MO 全套 `*icon.pcx`) 或 SHP
  `SidebarImage`; 未就绪盖 `DARKEN_SHP`; 进度盖 `GCLOCK2_SHP`
  (`AnimStage`); 就绪/快捷键字走 `NameReadiness()`。
- 交互: 左键 `LaunchSuper` (需打靶→置 `Display::CurrentSWTypeIndex`
  进 targeting; `Action==None`/AI 靶→直发 `SpecialPlace` 事件);
  右键取消 (`CurrentSWTypeIndex=-1`); 开关掣翻
  `ScenarioExt::SWSidebar_Enable`。
- 点击吞没: `DisplayClass::ProcessClickCoords` 内 `0x692419`
  (7B: `movsx ecx,[esi]` + `movsx edx,[esi+2]`, 无 rel),
  落自家按钮区跳 `0x6925FC`。

## 本移植取舍 (见 `src/SWSBar.cpp`)

- 不建 Gadget (虚表/GameCreate 配重太大): 纯覆盖层, 渲染挂
  `MOExperience_MessageDrawHook` (Composite 面), 输入靠轮询 +
  `0x692419` 吞没门 (同点同去向, 首 7B 实测无 rel, 见构建记录)。
- 只要图标不要 UI 资源: 不加载 Phobos 那套 On/Off/Top/Center/Bottom PCX;
  图标盒 60x48 自画 (底 + 阵营色边框 + 充能百分比 + 悬停名)。
  **图标本体走引擎 PCX 管线** (见下方"图标链路定案"), 已定案可用。
  整块画进**自有离屏缓存**, 15 个游戏逻辑帧才重建一次 (交互时立即),
  每渲染帧只做一次带 alpha 的合成 —— 见"绘制: 离屏缓存"。
- 鼠标悬停的那一个图标**不透明**绘制 (不吃 `[SWSidebar] Alpha`), 跟
  悬停名提示框一个规矩: 此刻正在读的东西不许被整体透明度淡掉。
- 超武/支援技能同注册类型 (`SuperWeaponTypes`), 不区分;
  显示门 = `Owner==本家 && IsPresent` (Phobos 摘牌逻辑同义)。
- 4 列右置 (盟/苏/厄/焚风), 空列隐藏; 归属内建表 96 个
  (由 `rulesmo.ini` 离线推导: 授予建筑 `SuperWeapon*=` +
  `Owner`/`Prerequisite` 链, 脚本见构建记录), 查不到落玩家
  阵营列 (`Scenario.PlayerSideIndex`, 读不到回 0)。
- 单节 `[SWSidebar]`: 全局键 + 超武 ID 键共处一节。
  值语义: 负数=隐藏, 0=默认 (优先级 1000), 正数=优先级
  (越小越靠前, 同值按 ArrayIndex)。缺键=默认显示。
- `ToggleKey` (默认 F4) 显隐, 隐藏即不占空间 (不画+门放行)。
- 点击分两类:
  - **点击即发射类** (`instant`, 判据见"附: 即时类超武") -> 往
    `EventClass::OutList` 塞 `SpecialPlace` **标准事件**, 引擎在 DoList
    执行, 联机由 Mega/Connect 同步 (符合 AGENTS.md 铁律)
  - **需选格类** -> **等左键松开**才写 `CurrentSWTypeIndex` 进打靶,
    整段按住由 `0x692419` 那道门吞掉。为什么不能"按下就写"见
    "附: 选中要按很多次 —— 根因"
  - 右键栏内写 -1 取消。
- 偏移全 fail-closed: 数组/指针/ID 可打印/`swIdx` 范围/
  标志位 0/1 任一不满足即跳过该项; 扫描零命中即不画。

## 配置 (`dist/MOExperience.ini` → 游戏内同名文件已同步)

`[SWSidebar]` 全部 18 个键**已改为中文**。ini 与 DLL 都是 UTF-8, 读取走
`GetPrivateProfileIntA` (逐字节比较, 不做代码页转换), 两边编码一致即可匹配
—— 已在编译产物里核实中文键确实是 UTF-8 字节。

**键名保持英文** (与代码里 `SWS_SECTION` 查找一致), 注释为中文。共 12 项:

- 开关: `Enable` / `ToggleKey`(默认 F4)
- 整体: `Alpha` —— 侧栏**唯一**的透明度旋钮 0~100, 作用于画出的每一个像素
  (底框/图标/边框/滚动条/箭头/文字一起变淡)。注意 PCX 图标原本是**直接
  覆盖写**像素, 要实现整体透明必须改成与底色混合, 否则图标永远 100% 不透明。
  曾另有一个只管底框的 `Opacity`, 与 `Alpha` 表达同一件事 (侧栏有多透明),
  两个旋钮能配出"半透明图标浮在不透明黑底上"这种自相矛盾的组合, 已合并;
  底框自己的浓度改成常量 `SWS_BACKDROP_OP`(30)。
  同理底框从"每列画一块"改成"整块画一次": 图标不吃逐元素不透明度, 两种画法
  视觉等价, 少 3 次填充、少 3 份重叠边缘。
- 外观: `Gap` / `ColGap` / `RightMargin` / `MaxRows` / `FontPx`
- 纵向: `TopMargin` —— **一个键两用**:
  - `0 ~ 1` = **比例**, 按屏幕高算。`0.5` = 垂直居中, `0.25` = 偏上。
    分辨率无关, 换分辨率不用改。
  - `> 1` = **像素**, `80` = 距屏幕顶端 80px, 适合精确微调。
  - 旧的 `CenterY`(0/1) + `TopMargin`(px) 已合并成这一个键。
  - 纯整数运算: 先算 `原值 × 10000` 定点来**判定语义**, 再按语义换算
    (比例再放大成 ×100000)。**判定和缩放必须分开** —— 曾经无条件先乘
    100000 再判, 结果 `80` 变成 1000000 像素, 侧栏直接被顶出屏幕。
- 行为: `ScrollStep`
- 防御页: `DedupDefensePage` (默认 1 = 去重; 侧栏有的超武不再在原版防御支援页
  重复出现, 侧栏上没有的照旧。按钮在显隐箭头左边, 点一下运行时切换; 这个键
  只决定开局初始状态。细节见"隐藏防御支援页里的重复超武")
- 过滤: `DrainSupers`(默认 0 = 过滤掉火风暴类) / `<超武ID>=<int>`
  (负数=隐藏, 0 或缺省=默认优先级 1000, 正数=优先级, 越小越靠前, 同值按
  ArrayIndex。**完整清单与写法示例见 `超武列表.md`**)

> 键名**不要**改中文。`GetPrivateProfileIntA` 是逐字节比较, 曾经把键名
> 改成中文试过 —— 因为 ini 与 DLL 都是 UTF-8 恰好能对上, 但这让 ini 变得
> 不可移植 (换台 ANSI 机器就全失效), 而且和 Ares/Phobos 的配置风格不一致。

> **新增键必须同时改两处**: ini 里加一行, **并且**加进 `SWSBar.cpp` 的
> `isGlobal` 排除串。漏了第二步, 该键会被当成"超武 ID"收进 `s_Ini`, 侧栏上
> 多出一个永远不亮的空条目 (不报错、不崩)。已踩过一次。

> **已删除的键** (连同代码里的死变量):
> - `Bold` / `FontFace`: 读进了 `s_Bold` / `s_FontFace` 但绘制时根本没用 ——
>   悬停名走全局 `[VecText]` 的 `VecText_Bold()` / `VecText_FontFace()`。
> - `Pcx`: 原本是"PCX 崩溃隔离开关", 但它只控制一个 `if` 早退, 而 PCX
>   管线早已定案可用, 留着只会让人以为可以关。已删, PCX 路径不再有开关。
> - `ClickFire`: 原本能整体关掉点击交互, 但关掉之后侧栏就成了纯装饰
>   (点了没反应), 没有任何使用价值。已删, 点击恒定生效。
> - `EvWatch` / `FireWatch`: 事件抓包与释放侦测两个诊断, 排查完就没用了,
>   而且 `FireWatch` 每次 Poll 遍历 78 条 (= 帧门修之前每帧 1.1 万次迭代)。
>   连同 `SwsEventWatch` / `SwsFireWatch` / `SwsHexB` / `s_GateLog` 一起删除。
> - `FontPx` **保留**但改注释: 它只影响充能百分比, 与悬停名无关 (后者走
>   `[VecText]`), 之前注释写"name/status font size"是误导。

## 隐藏"防御支援页"里的重复超武 (DedupDefensePage)

需求: 侧栏已经有的超武, 游戏自带的**防御支援页**(侧栏页签 1)里不要再出现
一遍; 侧栏上没有的(内部辅助类型 / `SW.ManualFire=no` / 火风暴类)继续由原版
页显示。运行时用一个开关在"去重"与"原样"之间切换, 按钮在显隐箭头**左边**。

### 引擎侧机制 (gamemd 反汇编实证)

- 超武 cameo 进侧栏的入口是 `SidebarClass::AddCameo` `0x6A6300`
  (`__thiscall`, `ret 8`; `ECX=this=0x87F7E8`, arg1=`AbstractType`,
  arg2=idx)。典型调用点: `HouseClass_UpdateSuperWeaponsUnavailable`
  (Ares 替换版 `0x50B329`, 原版在 `HouseClass::AISupers` 里同一个位置)、
  `ICBM` 补给箱 `0x482D4C`、脚本 `Grant1ShotSW` / `GrantPermanentSW`。
  引擎实际传的 `AbstractType` 一律是 `Special` = `0x1F`。
- 页签归属在两处写死: `SidebarClass::AddCameo` `0x6A636A/0x6A636F` 与
  `SidebarClass::GetObjectTabIdx` `0x6ABC8D/0x6ABC92` → 恒为 **1**
  (`0 建筑 / 1 防御 / 2 步兵 / 3 载具`)。Ares 没有改, Phobos 是靠钩
  `0x6ABC9D` + `TabIndex=` 才可配。我们不改 ini, 所以超武就在页签 1。
- 引擎唯一的移除路径 `StripClass::RecheckCameo` `0x6AA600` **只删
  `IsPresent` 已经为 0 的条目** —— 我们的超武都还在, 它不会动它们。
- **结论: 必须在入口处拦截的做法行不通。** 曾经在 `0x6A6316` (AddCameo 入口
  第一个可挂钩点, `lea ecx,[ebx+0x1598]`, 6B 无 rel; Ares 自己没占, Phobos
  用的也是这个点) 钩了个拦截门, 跳 `0x6A65FF` = AddCameo 的
  `xor al,al; ret 8` 出口 = 返回 false。**装上之后一次都没被调用过** ——
  诊断日志一行都没有, 而 76 条确实能搬出来。说明超武 cameo 是从别的路进
  页签的, 根本没走 `SidebarClass::AddCameo`。钩子已删除, 改用"每 5 帧复查
  一遍页签, 见到就搬走"。机制少一个, 也少占 6 字节。

### 一个坑: 条目根本不在 `StripClass::Cameos[]` 里

Ares 3.0 把侧栏 cameo 容器整个换掉了 (见
`ares(Antares)/src/Ext/Rules/Hooks.CameoList.cpp`):

```cpp
DynamicVectorClass<BuildType> RulesExt::TabCameos[4];   // Ares.dll 的 .data
```

增删 / 绘制 / 点击 / 排序 / `RecheckCameos` 全走它, `StripClass::Cameos[75]`
那个内联数组是**死内存** (只留 `Index` / `TopRowIndex` / `CameoCount`
三个还在用)。Ares 没有导出任何"删某个 cameo"的接口, 所以要把一个**还在**
的超武从防御页拿掉, 只能直接改这个数组。

`DynamicVectorClass<BuildType>` 布局 (YRpp `ArrayClasses.h`, 带虚表):

| 偏移 | 字段 |
|---|---|
| +0x00 | `void* vtable` |
| +0x04 | `BuildType* Items` |
| +0x08 | `int Capacity` |
| +0x0C | `BYTE IsInitialized` / `BYTE IsAllocated` (+2 pad) |
| +0x10 | `int Count` |
| +0x14 | `int CapacityIncrement` |
| | `sizeof = 0x18`, 4 个 = `0x60` |

`BuildType` 步长 `0x34` (52 字节; YRpp 头文件写 0x30, **少 4 字节**)。

### 从 Ares.dll 里挖出各个偏移 (比头文件可靠)

> 💥 **先看这条, 它是本功能 crash 的直接原因, 也是前面三轮"日志里全是垃圾
> 数字"的**总**根因**:
>
> **`0x87F7E8` 本身就是侧栏对象 (`MouseClass`/`SidebarClass`/`DisplayClass`
> 三者同一个静态对象), 不是"侧栏对象指针的存放地址"。**
> 证据三条:
>   1. 原版代码直接 `mov ecx,0x87f7e8` 当 `this` 用 (如 `0x6A6520` 调
>      `MouseClass::AddButton`);
>   2. 本工程别处也一律 `(void*)ADDR_DISPLAY` **不解引用**
>      (`OrderUtil.cpp:268` 等);
>   3. Ares 那句 `add eax,0x880d2c` = `0x87f7e8 + 0x1544`, 一步到位。
>
> 写成 `sb = *(void**)ADDR_SIDEBAR` 读到的是对象的**虚表指针**(一个 .text
> 代码地址, 本机是 `0x007E1964`)。后果是连锁的:
>   - 所有 `Tabs` 字段偏移全算错, `CameoCount` 读出来是 .text 里的代码字节
>     → 日志里 `strip=3688618971/4261264/...` 这种指针样的大数;
>   - `SwsDefenseRepair` 拿它当 `this` 调 `UpdateScrollButtons`/`SetTab`
>     → **当场崩** (写 `CameoCount` 那步被"先读后写"的守卫拦下了, 所以没
>     真的写进 .text, 但调用已经炸了)。
>
> 教训: 拿一个**没验证过语义的地址** (`MouseClass::Instance` 这种名字很容易
> 让人以为是指针的指针) 去算偏移/当 this, 一次错就是连环错, 而且症状
> (日志里是乱码数字) 会被误当成"别的字段偏移不对", 白查好几轮。
> **每个定址都要有一条独立证据, 别靠命名猜。**

**所有 `StripClass` / `BuildType` 偏移都以 Ares.dll 自己的反汇编为准, 不以
YRpp 头文件为准** —— 头文件这几个字段都比实际值小 4。挖法: Ares 把每个钩子
都导出了符号 (`GetProcAddress` 就能拿到), 直接反汇编。

| 字段 | 实际偏移 | 出处 (Ares 导出函数里的指令) |
|---|---|---|
| `SidebarClass::Tabs` | `pThis + 0x1544`, 步长 `0xF94` | `SidebarClass_AddCameo_SkipSizeCheck`: `imul eax,ebx,0xf94` / `add eax,0x880d2c`, 而 `0x880d2c = 0x87f7e8 + 0x1544` |
| `StripClass::Index` | `+0x38` | `StripClass_RecheckCameos`: `mov eax,[edi+0x38]` |
| `StripClass::TopRowIndex` | `+0x44` | 同上 `imul eax,[edi+0x44],0x68` |
| `StripClass::CameoCount` | `+0x54` | 同上 `cmp dword [edi+0x54],0` |
| `sizeof(BuildType)` | `0x34` | `SidebarClass_AddCameo_SkipSizeCheck` 的 `add eax,0x34` / `imul ..,0x34` |
| `DynamicVectorClass<BuildType>` | `0x18` | 见上面的布局表 |

`0x68` 那条看着别扭, 其实对: 锚点取的是 `Items[2 * TopRowIndex]`
(一行两个 cameo), `2 * 0x34 = 0x68`。

有了上面那条"0x87F7E8 就是对象本身", `StripClass::CameoCount` 这条互证就能
用了 (之前读出垃圾全是因为 `this` 取错): 日志里 `tc=` 后面四个数和 `strip=`
后面四个数应该**完全相同**。`SwsDefenseRepair` 把计数同步回 `CameoCount` 时,
仍然先读一次确认落在 `[0,4096]` 才写 —— 写别人维护的字段, 永远多一层保险。

### 定位 `RulesExt::TabCameos` 的办法 (SwsAresFindTabCameos)

**从 Ares 自己的代码里读地址, 不扫数据段。**

Ares 导出的 `SidebarClass_AddCameo_SkipSizeCheck` (钩 `0x6A63B7`) 开头几十
字节里有这两条 (实测反汇编):

```
8B 04 CD <disp32>            mov  eax, [ecx*8 + TabCameos[0].Items]
6B 0C CD <disp32> 34         imul ecx, [ecx*8 + TabCameos[0].Count], 0x34
```

两个 `disp32` 都是**编译期写死的绝对地址** (Ares 自己就这么索引它的), 所以
`TabCameos = (Items 的 disp32) - 4`, 并用第二条互证
`(Count 的 disp32) - 0x10 == TabCameos`。这样:

- 不用扫 `.data` 段, 不会误命中 Ares 里别的 `DynamicVectorClass` 数组;
- ASLR 重定位后依然对 (指令里的绝对地址会跟着一起重定位);
- 容器头地址终身不变 (Ares 只在 `ClearCameos` 里清内容, 从不搬容器), 只有
  `Items` 指针会在扩容时变 —— 所以每次用之前都现读 `Items`。

**扫数据段那版为什么不行**: 判据的骨干是
`TabCameos[i].Count == StripClass::Tabs[i].CameoCount` 互证, 而当时 `this`
取错 (见上面那条), 两边读的都是不相干的东西, 于是永远 `hits=0`。教训: 判据
里放进一个**自己都没验证过语义的东西**, 等于给自己判死刑。

定位成功后还要逐个校验四个容器: vtable 相同且落在 Ares 映像内、
`CapacityIncrement == 100` (Ares 的 `ClearCameos` 统一写死, `AddItem` 只涨
`Capacity` 不动它, 所以终身是 100)、`Capacity >= Count >= 0`、`Items` 可读。
任何一条不过就 fail-closed, 绝不猜地址写内存。

**每次用之前的复核 (`SwsTabCameoOk`) 只校验容器自身, 不再拿
`StripClass::CameoCount` 互证。** 这条互证已经坑过两轮: 第一轮是 `this` 取错
(读出 .text 的代码字节), 第二轮是它在本机确实会和 `TabCameos[i].Count`
不同步 (而定位器在成功那一刻两者还是一致的, 说明是运行中分叉的)。容器地址
来自 Ares 自己的代码, 本身就可信, 犯不着为一个不可靠的互证把整条路堵死。
互证只留在定位成功时打的那行日志里供对照。

只在**确实在跑一局**时才找: `HouseClass::CurrentPlayer` 有效, 且帧号走过 60
(主菜单/加载界面里容器还没建好)。试一次就够, 失败整条功能关掉并记一行 ——
因为上面两个前置条件已经保证时机, 而 Ares 的导出符号和那条指令永远在那儿,
再试也只是重复我们自己的校验。

> ⚠ **不要用 `Unsorted::ScenarioInit` (0xA8E7AC) 做这个判断**。名字像是
> "场景初始化中", 实际既不是 0/1 标志也不是可靠的非零标志: gamemd 里有
> `inc dword [0xA8E7AC]` (`0x442FF7` / `0x44E6ED`) 说明它是计数器, 而实战中
> 它又长期是 **0**。先后试过 `!= 1` 和 `!= 0`, 两次都让定位器**一次都没跑过**
> —— 而失败路径本来不记日志, 于是表现就是"按钮点了没反应, 日志里一行 dedup
> 都没有"。教训: 定位器这类"可能整条路都不走"的代码, 必须有一条
> **无论如何都会打一行**的旁路日志 (现在是失败时那一行 `sws: dd off got=I/C`)。

定位失败那行 `sws: dd off got=I/C` 一眼能看出是"没抓到指令" (`got=0/0`)
还是"抓到了但校验没过"。

### 两个方向

两个方向的**依赖是不对称的**, 这点很关键:

- **搬出 (隐藏)**: 必须直接改 Ares 的 `TabCameos[1]` (引擎的移除路径只删
  `IsPresent==0` 的, 而我们的超武都还在), 所以要先定位到容器, 并且要调
  `SwsDefenseRepair()` 收尾 (同步 `CameoCount`、`UpdateScrollButtons`、
  页签空了则 `GadgetClass::Disable` + `SetTab`、滚动位置只夹取不重置、
  置两个 redraw 标志再 `RepaintSidebar(1)`)。
- **搬回 (显示)**: **完全不碰 Ares 的容器**。对每个 `IsPresent && 侧栏有`
  的超武直接调引擎自己的 `AddCameo(0x1F, idx)`, 而 `AddCameo` 自带查重
  (Ares 的 `SidebarClass_AddCameo_SkipSizeCheck` 会扫一遍
  `TabCameos[TabIndex]`, 已经有了就返回 false), 所以对"已经在页里"的
  重复调用是**无害的空操作**。补完再 `RepaintSidebar(1)` 一次。

> 为什么不对称: 之前"搬回"也去查 `TabCameos` 判重, 于是容器校验一旦不过就
> **静默失败** —— 按钮点了没反应、日志里一行都没有。现在搬回只依赖引擎自己的
> 接口, 不会再被反查出来的地址拖死。同理 `SwsDefenseRepair()` (会写
> `CameoCount`、拿 `this` 调引擎函数) **只在搬出之后才调**, 搬回由
> `AddCameo` 自己把页签状态弄好。

> ⚠ **`SwsSidebarShows()` 是个纯谓词, 里面绝对不能判 `s_Enable` /
> `s_DedupHide`**。它被搬出和搬回共用, 而"切回显示"时 `s_DedupHide` 恰好是
> 0 —— 一旦在这里判掉, 恢复循环会把所有超武 `continue` 掉, 症状是**按钮点了
> 有 `sws: dd btn show` 但接着是 `sws: dd show n=0`**, 看上去像"引擎不肯加",
> 实际是自己把自己判没了。要判"侧栏开没开 / 要不要去重"由**调用方**自己判。
> 教训: 谓词函数里混进"当前模式"这种上下文状态, 就会在某个模式下静默失效。

### 复查代替拦截

`sws: dd hide` 之后并不会一劳永逸: 那个拦截门证明新增拦不住, 所以
`Sws_Poll` 每 15 帧 (约 0.25s) 顺手把 `s_DedupDirty` 置 1, 让 `SwsDedupSync`
**在已经处于隐藏态时也再跑一遍移除**。移除是幂等的, 没新东西就只扫一遍
`Count` 直接返回 0, 不动页签、不重绘; 真搬到了才调 `SwsDefenseRepair()`。
代价是新冒出来的超武 cameo 最多存在 0.25 秒。

**侧栏收起 (F4) 时保持防御页当前的显隐状态** —— 目标态只看去重开关, 与侧栏
显隐无关。原先是 `want = s_DedupHide && s_Visible`, 收起时会把防御页恢复成
"全都显示"; 那是多余的动作: 防御页是引擎自己的页签, 侧栏藏了它照样能用,
所以玩家按 F4 收起侧栏的瞬间, 刚去重掉的图标会莫名其妙全回来。

### 按钮

两个按钮都挂在超武块**正上方** 2px 的一行里 (20x16, 间隙 3px), 右对齐到块

## 绘制: 离屏缓存 + 15 逻辑帧节流 (2026-09-30 重写, 帧率问题的定案)

### 为什么必须重写

上一版的瓶颈不在哪一行, 在**频率**: 侧栏整块贴在一个每渲染帧都被重画的
合成面上, 于是每帧要把整块从零画一遍。按"每像素"算账 (78 条 × 60×48):

| 项 | 像素/帧 | 每像素代价 |
|---|---|---|
| 底框 `SwsFillCore` → `Blend16` | ≈12 万 | **≈20 次整数除法** |
| PCX 逐像素缩放混合 | ≈22 万 | 2 次整数除法 (算源坐标) + 混合 |
| 边框/滚动条/按钮/高亮 | 数千 | `Blend16` |
| 充能百分比 `RenderLine` | 0~2 条 | 每次先 `ClearDib` 256KB |

底框那一项单独就是 **240 万次除法/帧**, 十几毫秒; PCX 那一项是 **44 万次
除法/帧**。而侧栏内容一秒才变几次 —— 全是冗余。

### 结构: 重建 vs 合成

- **重建** (`SwsRebuild`) 画进自有缓存, 不碰合成面, **不持锁面**。
- **合成** (`SwsCacheBlit`) 每渲染帧只做一次带 alpha 的拷贝, 内层循环只有
  乘加和移位, 没有除法。

缓存 = **16 位色平面 + 8 位覆盖率平面**两张 (`s_CchC` / `s_CchA`)。
不能只存 16 位色: 侧栏自己各层要互相压 (底框 → 图标 → 边框 → 提示框),
最后才与面下的地图合成; 只存色就把"半透明"烙死在缓存里了, 换个背景就错。
存覆盖率才能既做层间混合, 又在合成时与地图正确混合。

只清覆盖率平面 (`SwsCacheAlloc`): 覆盖率 0 的像素在合成时整条跳过, 颜色
平面留着旧值永远读不到, 省一半 memset。

### 重建触发: 指纹 + 交互

`SWS_Draw` 每帧只算两样东西, 都是 O(条目数) 的整数运算:

1. **结构指纹** `SwsSig(w,h,pitch)`: 画布尺寸 + 显隐 + 去重开关 + 滚动偏移 +
   条目集合 (`swIdx/side/prio/ready/susp/instant/pcxFile` 逐条混入哈希)。
   变了立刻重建。
2. **交互态** 单独跟"上次重建用的值"比: 悬停项 / 按钮悬停 / 当前选中
   (`curSel`)。所以**鼠标移上去、点中、松开上膛、滚轮滚动、点显隐箭头、
   点去重按钮, 都是当帧重画**, 不用等节流。

再兜一条: `age = 当前逻辑帧 - 上次重建帧 >= 15` 就重建。充能倒计时
(`remain`) **刻意不进指纹** —— 只要有一个超武在充能它每次扫描都在变, 放进来
等于永不作废, 缓存就白做了; 倒计时跟着节流走 (每秒 4 次), 视觉上够用。
帧号回拨 (新开局/读档) 也强制重建, 否则会把上一局的缓存一直贴下去。

节流值 `SWS_REBUILD_FRAMES = 15` 与扫描节流同频, 两个计数器独立漂移无妨:
最坏情况一条新超武 ~30 帧 (0.5s) 才出现在侧栏上。

### 悬停不透明

`SwsCPcx(..., opaque = isHover)`: 悬停的那一个图标按 `a8=255` 画, 不吃
`[SWSidebar] Alpha`; 同时不压"未就绪"的暗罩, 让悬停名提示框和白框说话。
理由与提示框一致 —— 图标也是"此刻正在读"的东西, 淡到 30% 就看不清了。

### 顺带删掉的东西 (都是死代码 / 死绘制)

- **SHP 兜底整条** (`SwsShpOk` + `SHPReference::GetData` 懒加载): 结果写进
  `s_Items[n].shp`, 而绘制处那句"什么都不画"就是它唯一的归宿。纯白烧, 还
  每次给无 PCX 的超武多一次引擎调用。
- **`PCX::BlitToSurface` 兜底**: 它只能 blit 进**已锁的合成面**, 而重建期刻意
  不持锁面 (为它中途 unlock/relock 再重入半段布局, 代价远大于它兜的风险);
  而且它 100% 不透明、不认 `Alpha`, 留着只会让半透明在个别条目上失效。
  校验不过现在就是**不画这个图标** + 记一行日志。
- **写而不读的字段**: `SwsItem.id` / `SwsItem.row` / `SwsItem.shp`、
  `s_ColCount[]` / `s_ColX[]` / `s_Cols[]` / `s_NCols` / `s_ColsValid`、
  `s_BoundValid` (只写不读, 它的注释还专门解释"不能复用", 误导了后续两轮)。
- **`s_FontPx` 一直没生效**: 充能百分比那两趟 `BlitCoverage` 之前**没有**
  `GdiEnsure`, 直接用 `g_G` —— 借的是上一个用过 GDI 的模块的槽 (通常是
  底电/超武面板), 所以 ini 里的 `FontPx` 是摆设, 字号还随别的模块变。现在
  显式 `GdiEnsure(s_FontPx, …, 5, …)`。
- **`GtMouseGameXY` 每帧调两次** (开头拿一次算按钮/悬停, 中途又拿一次),
  合成一处。
- `SwsDrawShapeFn` typedef (CC_Draw_Shape 那条路早废了, 留着只提醒坑)。

### 两个配套决定

- **悬停名提示框不再逐像素跟随鼠标**, 改挂在**图标水平中心**。之前它锚在
  鼠标 x 上, 于是鼠标在图标里横移 1px 就要重画整块 —— 和缓存完全相冲,
  而且逐像素跟随本身就是抖的。
- **提示框的矩形要在分配缓存之前量出来** (`SwsTipPrepare` → `SwsTipRect`),
  因为它挂在图标上方 (或第一行下方), 两头都可能探出侧栏块, 不然会被缓存
  边界裁掉。同理条目高亮框的 1px 描边画在 `it->x-1` / 下边正好落在
  `yStart+blockH`, 所以缓存矩形左/下各再让 1px。
- 提示框的**字形**走自有覆盖率缓存 (`s_Tip`, 照 `MOExperience` 的 `PwrCache`
  抄的): `RenderLine` 每次都要先 `ClearDib` 一遍 1024×64×4 (256KB), 悬停时
  每帧一次纯属白烧。为此 GDI 从 6 槽扩到 7 槽 —— 提示框用槽 6, 充能百分比
  用槽 5, 两者字号来源不同 (`[VecText]` vs `[SWSidebar] FontPx`), 共用一槽
  会让 `GdiEnsure` 每次都拆了重建 (`CreateDIBSection`+`CreateFontW`)。

### 踩坑: 缓存 blit 里混了两套坐标系 (整块侧栏平铺糊满全屏)

合成那层有**两套坐标**: 缓存内下标 `x ∈ [0,s_CchW)` 和画面列 `s_CchX + x`。
写的时候只犯了一处就已经是灾难, 而且两处都犯了:

1. **目标列漏了 `s_CchX`** —— 内层循环用缓存下标直接写 `drow[x]`, 整块侧栏
   被贴到画面**最左边**而不是缓存原点。
2. **夹取留下了画面坐标** —— 写成
   ```c
   x0 = (s_CchX < 0) ? -s_CchX : 0;
   x1 = s_CchX + s_CchW;
   if (x1 > surfW) x1 = surfW - s_CchX;      /* 只有出画时才修正 */
   ```
   整块在画面内时那个分支**根本不进**, `x1` 停在 `s_CchX+s_CchW`, 内层多跑
   `s_CchX` 次: 源指针越过本行读进下一行缓存, 目标也越过右缘写进下一行 ——
   表现就是整块侧栏在屏幕上被平铺成一片 (截图实测)。

正确写法 (目标列区间 `[0,surfW)` 平移成缓存内下标, 再与 `[0,s_CchW)` 取交,
两头都夹, 写的时候补上 `s_CchX`):

```c
x0 = 0;
x1 = s_CchW;
if (s_CchX < 0) x0 = -s_CchX;                       /* dest col 0 */
if (s_CchX + s_CchW > surfW) x1 = surfW - s_CchX;   /* dest col surfW-1 */
if (x1 > s_CchW) x1 = s_CchW;                       /* 别忘了这条 */
...
int dx = s_CchX + x;
drow[dx] = c;
```

**教训: 单像素的混合算术测试抓不到循环边界错。** 混合公式我跑了几十个数值
用例全绿, 栽的却是内层循环的上下界。合成/拷贝这类代码必须另外做**结构性**
测试: 拿一张预填哨兵的合成面跑真正的循环, 逐像素断言"该写的写对、a=0 的
没动、矩形外的一格没动 (含行尾余量)", 并且把摆法铺开 (贴左/贴右/居中/
四边出画/整块在画外/缓存比画面大/1x1/555)。回归验证: 把上面两处分别改回
 buggy 版本, 13 个用例里分别挂 4 个和 8 个 —— 抓得住。

同一层里其它几个原语 (`SwsCFill` / `SwsCPcx` / `SwsCCov`) 都是**先减原点、
再夹、之后一律缓存下标**, 没有这个问题; 出事的只有 blit, 因为它必须拿
未平移的 `s_CchX` 去跟画面宽度求交。

### 三个 UI 缺陷 (2026-09-30 修, 都是缓存化之后才暴露的)

**1) 悬停名被拦腰截断。** 提示框挂在图标**上面**, 而侧栏块顶上方只有两个按钮
那一行 (18px): 框顶会探出块外。缓存矩形当初只给提示框留了左/右/下三条边,
**漏了上边**, 于是顶上 6 行被削掉 —— 字被拦腰切。
修法两条一起上: 提示框改挂图标**下面** (块内那一侧, 只有最后一行可能顶到
屏幕底, 那种情况才翻上去), 并且缓存上边界取 `min(按钮行, 提示框顶)`,
翻上去时也兜得住。

**2) 高亮框"位置错位 / 被列边框吃掉"。** 高亮框画在
`it->x-1 .. it->x+ICON_W` (62×50 描边), 而 `ColGap=0` 时相邻列贴在一起:
本列右边框在 `x+59`, 下一列左边框正好在 `x+60`。所以高亮框的左右两边**压在
邻列的外边框上**, 而每列边框是画在图标循环**之后**的, 于是把高亮框盖掉一列
—— 看上去就是"框缺了一截、位置不对"。
修法: 高亮框从图标循环里**拎出来**, 单独一遍排在每列边框**之后**。顺序固定
为 底框 → 图标+文字 → 每列边框 → 高亮框 → 滚动条 → 按钮 → 提示框。

**3) 折叠按钮跳位。** 展开时锚点是"块右缘 − 宽", 收起时另算成"贴屏幕右缘",
两者差一个滚动条让出的 5px (实测 cols>10 时跳 5px)。收起并不改变按钮该在的
位置, 玩家要能对着同一个点按回去。
修法: 展开时把坐标记进 `s_BtnXKeep/s_BtnYKeep`, 收起时原样沿用。

**4) 高亮框落在另一个超武身上 (2026-09-30 修, 且是缓存化时**引入的回归**)。**
现象: 鼠标悬停"心灵支配", 亮起来的是"回澜"。这个 bug 在重构**之前**就有,
但重构时又踩了一次同款。

根因是**下标有两套坐标系**, 而高亮和悬停检测各用了一套:

| 用途 | 下标空间 |
|---|---|
| 图标循环 / 高亮循环 (`it = &s_Items[s_Order[i]]`) | **排序后**的位置 |
| `s_Items` 本身 | **原序** (SuperClass 数组序) |

排序键是 (阵营 → ini 优先级 → ArrayIndex), 和原序**不是一回事**。老代码的
悬停检测走 `s_Items[s_Order[i]]`, 于是和高亮循环一致; 重构时我把它抽成
`SwsHitItem` 却写成扫原序 `s_Items[k]`, 高亮循环拿它跟排序下标 `i` 一比就
对不上了。提示框因为**直接**用 `s_Items[hover]` 取名字, 看着还是对的 ——
更骗人: 提示框说"心灵支配", 亮的是"回澜"。

定案: `SwsHitItem` 返回**排序后**下标, 并且 `SwsOrder` 的所有消费者一律
经 `s_Items[s_Order[hover]]` 取条目 (提示框两处都要走)。判据写进函数注释。

这类"同一份数据两个下标空间"的坑, 一旦有人把某个下标"顺手"改成另一种,
编译器和运行都毫无意见, 只有一个肉眼可见的错误高亮。凡是 `s_Items` /
`s_Order` 这种成对结构, 取值处只认一种写法, 别让两种并存。

### 教训: 逐点测试看不见"包含关系"和"循环边界"

三处都是**单点算术全对、组合起来才错**:

- 提示框自己的矩形算对了, 但**缓存矩形**没把它整个包住 → 截断。
- blit 的像素算对了, 但**内层循环边界**没夹 → 平铺糊屏 (上一节)。
- 按钮坐标两处各算都对, 但**两处规则不一致** → 跳位。

所以补了两类**结构性**测试, 都在 `C:\Users\hxyyg\AppData\Local\Temp\opencode\`
(未入库, 要收进仓库说一声):

| 测试 | 断言 | 抓得住 |
|---|---|---|
| `sws_blend_test` | 28 个混合算术数值例 (565/555、快路、alpha 饱和、无串位) | 公式错 |
| `sws_blit_test` | 预填哨兵的合成面跑真 blit 循环, 逐像素断言该写的写对 / `a=0` 没动 / 矩形外一格没动 (含行尾余量), 13 种摆法 | 循环边界 (挂 4 / 8 例) |
| `sws_geom_test` | 网格扫 640~2560 × 480~1440 × MaxRows 1~20 × Gap × ColGap × RightMargin × 5 种名字宽度 × 滚动位置, 断言**每个画进缓存的元素都在缓存矩形内**, 外加折叠按钮不跳位 | 截断 (挂 47250 例) / 跳位 (挂 6 例) |
| `sws_hover_test` | 造"原序 ≠ 排序后"的条目集, 对每个条目断言 `SwsHitItem` 返回的下标经 `s_Items[s_Order[…]]` 解析回**同一条目**, 且高亮遍 `i==hover` 恰好选中它 | 错位高亮 (挂 7 例, 报 "hovered 1001 lit 1004") |

`sws_hover_test` 里加了一条防空转的守卫: 先断言原序确实 ≠ 排序后, 否则
"ALL PASS" 只是因为排序恰好是恒等 (2/4 条目时就会这样)。

`sws_geom_test` 的不变量写法要注意: 元素探出屏幕时**本来就该被裁**, 所以要跟
**夹取后**的值比, 不能跟原值比, 否则一堆假阳性。

### 还没做的

- `SwsPcxLiveSurf` 仍是每条目每次重建一次 `GetSurface` (按文件名的引擎缓存
  查找)。**不能**跨帧缓存 `BSurface*` —— 引擎切页签/重载美术时会释放重建,
  那是野指针。现在是 15 帧一次, 已经无所谓了。
- 缓存矩形目前是"按钮行 ∪ 超武块 ∪ 滚动条 ∪ 提示框"的**并集矩形**, 提示框
  很宽时会把缓存拉宽。真正省事的做法是提示框不进缓存、每帧单独落面, 代价是
  每帧一次 `RenderLine` (所以选了现在这条)。

## 绘制性能 (上一版, 每帧都在跑, 所以按"每像素"算账 —— 已被上面那节取代,
留着是为了说明"为什么当时那些优化不够")

开销的大头是**像素**, 不是逻辑: 78 个条目 × 60×48 图标 ≈ 22 万像素/帧, 底框
再一整块。所以优化都压在这两个循环上。

- `SwsFillCore` (底框/边框/滚动条/按钮/罩暗):
  - 上下左右边界**各夹一次**到画布内, 内层循环不再逐像素判越界。
  - `op==100` 走直接写, 不调 `Blend16`。注意位深是**运行时探测**的
    (565 或 555, `GdiText` 里 `g_RBits/g_GBits/g_BBits`), 压色必须照
    `Blend16` 的同一套移位来, **不能硬编码 RGB565** (先写错过一次: 把蓝色
    放进了高位)。
- `SwsPcxBlitLocked` (图标): 同样把 x 范围夹到循环外, 并把 Alpha 的
  `kA/kB = 100-kA` 提到循环外 —— 原来每个像素做 3 次除以 100。
- **底框只画一次** (整块), 不是每列一次。
- **排序结果缓存**在 `s_Order[]`: 排序键 (阵营, ini 优先级, ArrayIndex) 全来自
  `s_Items`, 而 `s_Items` 只有 `SwsScan` 会改, 也就是这个顺序**与帧无关**。
  原来每帧重排一次纯属白做。`SwsScan` 末尾把 `s_OrderN` 置 -1 作废。
  (`colCount` 也跟着缓存在 `s_OrderColCount`。)
- 没做的: `SwsPcxLiveSurf` 仍是每条目每帧一次 `GetSurface`(按文件名的缓存
  查找)。**不能**跨帧缓存 `BSurface*` —— 引擎切页签/重载美术时会释放重建,
  那是野指针。想省只能加"每帧一次 GetSurface 后当帧复用"的当帧缓存。

## 2026-09-29 图标链路定案 (PCX, 走引擎现成设施)

结论: MO 的超武图标**不是 SHP**。`rulesmo.ini` 里 96 个超武节用
`SidebarPCX=xxx.pcx`, `SidebarImage` 出现 1 次、`Cameo` 0 次; PCX 打包在
`expandmo*.mix` / `thememo.mix` 里, 磁盘上没有。所以 `SidebarImage` 指向
引擎的 `XXICON.SHP` 占位引用, 画出来必然是**同一个紫球** (11 个条目
指针完全相同)。

最终链路 (全部引擎现成设施, 与 Phobos `SWButtonClass::Draw` / Ares
`Misc/Cameos.cpp` 同款):

1. 读键: `*(CCINIClass**)0x887048` (游戏已加载好的 rules 对象, 走 MIX)
   -> `INIClass::ReadString` @ `0x528A10` 读 `<超武ID>` 节 `SidebarPCX=`
2. 载图: `PCX::Instance` = `0xAC4848` (**`this` 就是该地址本身, 不能解引用**;
   `DEFINE_REFERENCE(PCX, ...)` 类型是 `PCX` 不是 `PCX*`)
   -> `GetSurface` @ `0x6BA140`, 未命中则 `ForceLoadFile` @ `0x6B9D00`
3. 贴图: 自写逐像素循环 (色键 `COLOR_PURPLE=0xF81F`, 源列映射表预计算)。
   引擎的 `PCX::BlitToSurface` @ `0x6BA580` 2026-09-30 起不再使用 ——
   它只能 blit 进**已锁的合成面**, 而现在图标是画进自有缓存的 (见"绘制:
   离屏缓存")。
4. ~~无 PCX 时才回退 SHP~~ **2026-09-30 删除**: 回退结果从未被画出来过
   (见"顺带删掉的东西"), 留着只是每帧给无 PCX 的超武白跑一次
   `SHPReference::GetData` 懒加载。无 PCX 的超武现在就是空条目, 要么在
   `rulesmo.ini` 补 `SidebarPCX=`, 要么在 `[SWSidebar]` 给它负值隐藏。

### 三个决定性坑 (都曾表现为"图标不对"或崩溃)

- `PCX::GetSurface` 在文件**未加载时不返回 NULL**, 而是直接给一张占位
  surface。必须**无条件先 `LoadFile`**, 否则 11 个图标 blit 的全是同一张
  占位图 (症状: 全是紫球, 但日志显示 "pcx ok")。
- 引擎的 `BSurface*` **绝不能跨帧缓存**。引擎切页签/重载美术时会释放并
  重建 PCX surface; 缓存的指针变野指针 -> 平时画成脏图, 切页签时崩溃。
  现在只缓存**文件名**, surface 每帧现取。
- 硬编码 `DSurface::Composite` = `0x88731C` 在本机 Ares 构建里**不是**
  surface 对象 (该处虚表为 NULL), `BlitToSurface` 内部一调虚函数就跳 0
  (转储: `EIP=0, ECX=0x88731C`, 返回地址 `0x6BA597`)。用 SWS_Draw 的
  `surf` 参数。

## 其它已确认的坑

- **凡是"每条目"的数据, 都不能只在首次填充时写进 s_Items[n]**。
  
 是**本次扫描的条目下标**, 建筑一增减, 条目顺序就会重排 —— 挂在
  某个 n 槽上的数据会张冠李戴。悬停名字就踩过这个坑: 它被写在
  if (tc->prio < 0)(类型首次填充) 分支里, 建筑变动后条目重排, 名字
  留在旧槽位, 于是图标刷新了但提示文字是别的超武。正确做法: 名字属于
  **类型**的固有属性, 存进 SwsTypeCache.name, 每轮从 	c 拷到
  s_Items[n], 随条目一起搬。
- **多个分支的按键边沿必须共用同一份状态变量**。
  显隐按钮点一下"只闪一下、第二次才生效"就是这么来的: 可见分支点箭头后
  直接 `return`, 绕过了函数末尾的 `s_PrevLB = lb`, 于是下一帧进入隐藏
  分支时拿到的还是"上一帧没按键"的旧值, 而按键确实按着 —— 伪造出一个
  **新的按下沿**, 刚收起的侧栏立刻又弹回来。修法两处都要动:
  (a) `return` 前自己把按键态写回去;
  (b) 隐藏分支不要再另开一份 `s_HidPrevLB`, 直接用 `s_PrevLB`。
  判断依据: 任何"提前 return 的路径"都会让末尾的状态更新被跳过。
- **吞没/挡鼠标的判定要按"真的画了东西的地方"来, 不能用整块容器矩形**。
  栏区底框是按每列 `maxRows` 画满的, 某列条目少时下半截是空的, 加上栏区
  内部留白, 这些地方根本没有图标却把整片点击吞掉 —— 表现是"侧栏盖住的
  地图那块点不动, 框不了单位也打不了靶"。现在门只看 `SwsMouseOnIcon()`,
  空地还给引擎。顺带: 右键取消也必须限在栏区内, 早先只要 `s_BoundsKnown`
  就生效, 玩家在地图上右键取消选中单位反而把超武选中状态清了。
- **描边/边框只画一层, 底板别用纯黑**。
  箭头早先是"纯黑底往外扩 2px + 亮绿边框", 视觉上就是"一层黑一层绿"两条
  带, 很脏。现在底板也用主题色 `A5D3FF` 压到 45~70 不透明度, 边框单独
  165~225, 就一层。侧栏主题色统一在 `SWS_ACCENT_R/G/B`, 改色只改这三行。
- **半透明填充要分清两个函数谁乘 `s_Alpha`**:
  - `SwsFillLocked` **内部已经乘了** (`op = op * s_Alpha / 100`), 调用方只能给
    原始不透明度。给它 `70 * s_Alpha / 100` 等于乘两次 —— `Alpha=30` 时实际
    只剩 6%, 提示框底色几乎透明。
  - `BlitCoverage` **不乘**, 调用方才要预乘 `s_Alpha / 100`。
  这两个反着来最容易出错, 现象是"调 Alpha 时底框和字的浓淡对不上"。
- **提示框: 半透明黑底 + 一圈 1px 主题色边框** (`A5D3FF`)。
  框比文字左右各宽 2px (`sw + 6` x `adv + 4`), 所以贴边夹取要**按框算**,
  不能按文字算, 否则右边缘跑出屏幕少一截。

- **`BSurface` 偏移: 虚表大小不是字段偏移 (踩过, 导致 Alpha 对图标无效)**。
  `PCX::GetSurface` 返回的是 `BSurface*`, 真实布局 (gamemd.exe `0x6B9D00`
  构造函数据实, 与 `YRpp/Surface.h:144` 一致), `sizeof == 0x20`:

  | 偏移 | 字段 |
  |------|------|
  | +0x00 | `void* vptr` (BSurface 虚表 `0x7E2070`) |
  | +0x04 | `int Width` |
  | +0x08 | `int Height` |
  | +0x0C | `int LockLevel` |
  | +0x10 | `int BytesPerPixel` (=2, 16bpp RGB565) |
  | +0x14 | `void* Buffer` (WORD*, 紧排, 行距 = `Width*2`) |
  | +0x18 | `int Size` (= `Width*Height*2`) |
  | +0x1C | `bool Allocated` |

  早先写的是 `0x88/0x8C/0x94/0x98` —— `0x88` 是**虚表大小** (34*4), 有人把虚表
  整个的大小当成了字段基址偏移, 而虚表指针本身只占 4 字节。于是每次都在校验处
  提前 `return 0`, 图标一直退回引擎 `BlitToSurface` 兜底, 而那条路是整块覆盖、
  100% 不透明, 根本不认 `s_Alpha`。**现象: Alpha 对底框/边框有效, 对图标完全
  无效** —— 因为底框走 `SwsFillLocked` (吃 s_Alpha), 图标走引擎 blit (不吃)。

  另外: `PCX::Instance` 是 `0xAC4848` 上的**全局对象**, `+0x00` 是 cache 的
  桶数组指针, **没有虚表** —— 别去找它的虚表。
  (排查手法是曾在快速路径里留一行一次性日志; 问题定死之后已删, 复现时再加回来。)

- **只有一个元素不吃整体透明度: 悬停名字提示框**。
  它用 `SwsFillRawLocked()` (不乘 `s_Alpha`) + `BlitCoverage` 直接给 100/85。
  提示框是玩家此刻正在读的信息, 跟着 `Alpha=30` 一起淡就看不出是哪个超武了。
  记住两个绘制函数约定相反: `SwsFillLocked` 内部乘 `s_Alpha`, `BlitCoverage` 不乘。

- **UI 元素画在判定框之外 = 永远点不到**。显隐按钮原先画在超武块**上方**
  (`s_BtnY = yStart - 16`), 而点击判定被包在 `my >= s_BoundY(=yStart)` 里,
  按钮在 `yStart` 之上 -> 分支进不去, 表现就是"有个绿块但没反应"。
  现在按钮放在超武块**右侧**, 且命中判定**提到栏区判定之前**。
- **"隐藏"不能把唯一的入口也一起隐藏**。侧栏收起时如果连箭头一起不画,
  玩家就再也找不到展开的地方。所以 `SWS_Draw` 里的 `!s_Visible` 早退
  放在**拿到锁面之后、画超武之前**, 隐藏时只画一个向左的 ◀; `SWS_Poll` 的
  隐藏分支里也保留了箭头的点击处理。
- `isGlobal` 排除串必须和 `SwsEnsureInit` 里**真正读取的键保持一致**。
  曾经两边不一致, 留下一堆早已删除的键 (`点击发射` / `PCX图标` /
  `诊断_*` / `CenterY`), 排查时误以为它们还生效。现在两边逐键核对。
- 探针扫内存时**必须跳过虚表指针**: offset 0 是 0x004xxxxx 的代码地址,
  被当成 SHP 结构读会顺着"文件名指针"二次解引用 -> 必崩。同理不要顺着
  野指针打字符串。
- `SwsPcxFileOf` 建槽位时**必须 `SwsCopyId` 记 id**, 否则查找永远失配、
  槽位涨满后一律返回 NULL (曾导致 PCX 分支静默失效, 全体回落紫球)。
- 删代码时判断注释起点要用 `lstrip().startswith("/*")` —— 注释是缩进的,
  否则脚本会一路走错位置, "删掉了"其实没删 (那个图标探针因此赖了很多轮)。
- **构建校验必须看退出码 + DLL 时间戳**, 不能只 grep "error C": gcc 的
  `error:`(无 C) 不匹配, 曾连续多轮报告"构建成功"而 DLL 根本没更新。

# 附: 即时类超武 (点击即生效) —— 已查实的结论

## 判据 (三条, 从 rules INI 读, 不猜结构偏移)

Ares 侧栏点击钩子 `ares(Antares)/src/Ext/SWType/Hooks.cpp` 的
`SidebarClass_ProcessClickCoords` @ `0x6AAEDF`:

```cpp
// a SW without a cursor and an AI targeted one do not need the player
// to pick a cell. fire them right away.
if(pSuper->Type->Action == Action::None || pData->SW_UseAITargeting) {
    R->EAX(HouseClass::CurrentPlayer);
    return 0x6AAF10;
}
```

同一钩子里更早的**前置条件**, 缺一个都静默拒绝 (症状与"点了没反应"一样):

```cpp
bool manual = !pData->SW_ManualFire;     // SW.ManualFire=no -> 点击作废
if(!pSuper->CanFire() && !manual) { 播 EVA_Impatient; return; }
if(!CanTransactMoney(Money_Amount)) { 播 EVA_InsufficientFunds; return; }
if(pData->SW_UseAITargeting && !MeetsAITargetingConstraints(...)) { return; }
if(manual || unstoppable) return;
```

`Action=Custom` **不是** `Action::None`。Ares `SWType/Body.cpp`:

```cpp
if(exINI.ReadString(section, "Action") && !_strcmpi(exINI.value(), "Custom"))
    pThis->Action = Actions::SuperWeaponAllowed;
```

`Actions.h`: `SuperWeaponAllowed = 0x7F`。MO 相关超武**全是** `Action=Custom`。

逐个查 `ares(Antares)/src/Misc/SWTypes/`, 只有这几个把
`pSW->Action = Action::None` 写进 `SuperWeaponTypeClass`:

| NewSWType | 赋值 | MO 里谁用 |
|---|---|---|
| `HunterSeeker` | `Action::None` | 工厂停产维护 / 纳米回复场 / 猎杀机器人 |
| `Battery` | `Action::None` | 心灵之火 |
| `EMPulse` / `Reveal` / `SonarPulse` | 条件赋值 (看 ini) | — |
| `Firestorm` | **无该赋值** | 爆裂屏障 |

**所以本移植的 `instant` 判据是三条并集** (`SwsBehaviorOf`, 每类型读一次
ini 后缓存):

```
Action=None (ini)  ||  SW.UseAITargeting=yes  ||  Type ∈ {HunterSeeker, Battery}
```

实测 (`sws: tbl`): `inst=1` 的只有精英预备队(100, 靠 `SW.UseAITargeting`)、
工厂停产维护(73)、纳米回复场(56)、猎杀机器人(53)、心灵之火(102)、
PaladinAid(128)。

**全 135 个超武的节名 / 中文名 / Type / 挂载建筑, 见 `超武列表.md`。**
名字对照取自 `AutoLoadDev/ini/stringtable10(单位名称).csf.txt` (UTF-8),
注意 **CSF 表标签全是小写** (`name:hunterseeker`), 而 ini 里是混合大小写
(`NAME:HunterSeeker`) —— 查表必须统一小写, 否则一条都匹配不上。

> `Action=None` 这条判据在 MO 的 135 个超武里**一次都命中不了**
> (125 个是 `Custom`, 其余是 `IronCurtain`/`LightningStorm` 等原版值)。
> 真正起作用的是 `Type ∈ {HunterSeeker, Battery}` 与 `SW.UseAITargeting`。

## 释放方式: SpecialPlace 事件

`instant` 类走 `EventClass::OutList` 塞一条 `SpecialPlace`, 由引擎在 DoList
执行 —— 联机由 Mega/Connect 同步 (AGENTS.md 铁律: 只走标准事件)。

事件构造 (`SwsPushSpecialPlace`, 照 `BuildQueue.cpp` 的 `BQ_FireProduce`
那套已验证的 OutList 追加):

- ctor `0x4C6B60` (`thiscall`: this=111 字节缓冲, houseIdx/Type/id/CellStruct)
- OutList: Count `0xA802C8`, Next `0xA802D0`, Buf `0xA802D4`, Par `0xA83A54`
- 事件 111 字节, 容量 `0x80`, Next 用 `(next+1)&0x7F`
- 拷完调一次 `call [0x7E1530]` 无参回调, 返回 EAX 存并行数组
- `houseIndex = [house+0x30]`, `CurrentPlayer = *(0xA83D4C)`
- `EventType::SpecialPlace = 0x12`
- **ctor 之前必须清零 111 字节**: `EventClass::operator==` 是
  `memcmp(...,111)`, 留栈垃圾会给联机同步埋雷
- **`Location` 传 `CellStruct::Empty` (0,0)** —— 这和引擎点原版侧栏发出的
  事件逐字节一致 (已用抓包核对)

`EventClass` 布局 (YRpp, pack(1), sizeof=111):

```
[0] Type(1B) [1] IsExecuted(1B) [2] HouseIndex(1B) [3..6] Frame(4B)
[7..] DataBuffer, 其中 SPECIAL_PLACE { int ID@7; CellStruct Location@11; }
```

> **[1] 不是"引擎是否已执行"的判据。** 曾据此写过一个 EXECUTED 追踪器,
> 后经原版侧栏抓包证伪: 引擎自己发的事件 `[1]` 也是 `0x00`, 另一类事件
> 才是 `0x5A`。该追踪器已删除。

## 火风暴类 (爆裂屏障/心灵之火): 已放弃, 过滤掉

`[SWSidebar] DrainSupers=0` (默认) 把 `UseChargeDrain=yes` 的类型整个
过滤, 不显示也不处理。

**为什么做不到** —— Ares 有两条不相交的入口:

```
SuperClass_Launch    @0x6CC390 -> Activate() -> NewSWType::Activate()
SuperClass_ClickFire @0x6CB920 -> ChargeDrain 开关状态机 (Ready<->Draining)
```

SpecialPlace 事件的实际路径 (Ares hook `0x4C78D6`
`Networking_RespondToEvent_SpecialPlace` 接管, 末尾 `return 0x4C78F8`):

```
事件 -> 0x4C78D6 -> HouseClass::Fire_SW(idx, cell) @0x4FAE50
     -> SuperClass::Launch -> Activate -> NewSWType::Activate
```

**整条链都不经过 ClickFire**, 而 ChargeDrain 的开关逻辑只在 ClickFire 里:

```cpp
if(pType->UseChargeDrain) {
    if(ChargeDrainState == Draining) { ...关闭... }
    else if(ChargeDrainState == Ready) { ...激活... }
    return ret(false);
}
```

结果: 事件能把**效果**打出去 (火风暴围墙真的会激活), 但
`ChargeDrainState` 永远停在 `Ready`, 侧栏显示不出"生效中"。

**Phobos 没有可抄的实现** —— 它的 `SWButtonClass::LaunchSuper` 与 Ares 的
点击钩子**逐条同构**, 全文只有 `unstoppable` 判定处出现一次 ChargeDrain,
且不参与状态推进。ChargeDrain 是 Ares 的功能 (手册也归在 Ares 3.0), 而
Ares 侧本身就没把它接进事件路径。

**要真修**就得写引擎的 `ChargeDrainState`, 而那要先拿到
`HouseClass::Supers` 的偏移。从 YRpp 头推导时遇到 **40 处尺寸未知**的成员
(各种 `DECLARE_PROPERTY` 计时器 + 末尾 `??` 块), 推导值 `Supers@+0x180`
与先前估值 `0x384` 差 `0x204` —— 不可信。拿猜的偏移写引擎结构迟早崩游戏,
收益 (两个超武的 ON 文本) 远小于风险, 故放弃。

> 附: 手册说"你也可以手动关闭它"只在 `SW.Unstoppable=no` 时成立。MO 给的是
> `yes`, 所以即便做对了, 生效中也是**不允许**手动关的。

`SW_Firewall::Activate` 收下 `CellStruct const cell` 却根本不用, 直接
`SetFirestormState(true)` —— 印证这类超武确实"不需要选格"。

# 附: 选中要按很多次 —— 根因

症状: 点超武图标经常选不中, 要点好几次才进打靶态; 有时干脆直接就地释放。

## Phobos 为什么没这问题

`SWButtonClass` 是**真 Gadget**:

```cpp
GadgetClass(x, y, w, h, (GadgetFlag::LeftPress | GadgetFlag::RightPress), false)
```

引擎的 `GadgetClass::Action` 消费这次点击时, 会顺手清掉 `MouseClass` 的
按键态 —— `DisplayClass::ProcessClickCoords` 根本看不到"左键按住"。
我们不建 Gadget (虚表/GameCreate 配重太大), 只能纯覆盖层+轮询, 引擎照常
看到左键按住。这是架构差异, 不是某处写错。

## 引擎的放置判据

`DisplayClass::ProcessClickCoords` 内 `0x692B06`:

```
692b06: mov 0x8809a0,%eax     ; CurrentSWTypeIndex (Display+0x11B8)
692b0b: cmp $0xffffffff,%eax
692b0e: je  0x692b28          ; -1 = 无选中, 不放
        ... call *0x6c(%eax)  ; SuperClass 虚表 -> 放置
```

**只要 `CurrentSWTypeIndex != -1` 且引擎认为左键按住, 当帧就在鼠标处释放。**
真正的"按下即生成 SpecialPlace"在 `0x4AC20C`
(`DisplayClass_LeftMouseButtonUp`), 用的是**当前鼠标格** —— 所以日志里
能看到 `cell=236,141` 这种真实格子, 而我们自己推的 `instant` 事件是
`CellStruct::Empty (0,0)`, 两者可据此区分来源。

## 三个缺陷叠加

1. **延一帧写躲不掉**。早先的写法是"按下记 `s_PendSel`, 下一帧写
   `CurrentSWTypeIndex`"。但那一帧按键**还按着**, 引擎立即释放。日志实证:

   ```
   sws: armed
   sws: armed                                  <- 我们刚上膛
   bq: ev a=0x00000012 ... c=0x008D00EC       <- 引擎 SpecialPlace
   swsev: t=18 h=0 SP id=22 cell=236,141 raw=125A0042...
   sws: FIRED id=22 inst=0 rem=5399/5400      <- 当场释放
   ```

   `raw` 第 1 字节 `0x5A` 是引擎自己写的 `IsExecuted`; 我们推的
   `instant` 事件该字节是 `0x00`, 且 `Location` 是 `(0,0)`。

2. **吞没门依赖了会被清零的标志**。门判 `s_BoundValid`, 但
   `SwsScan()` 开头就把它清零 (只在重建条目期间有效), 要等 `SWS_Draw`
   跑到布局末尾才置 1。点击那帧 `SWS_Poll` 先跑、门后跑, 而点击必然
   `s_ForceScan=1` 触发重扫 —— 门**恰好**撞上被清零的窗口,
   走 `else if (!s_BoundValid) r = 0;` 放行。症状就是 `sws: gate`
   日志一行都没有 (该日志本来就受 `s_GateLog < 40` 限制, 一次没出
   说明门一次都没生效过, 不是被上限截断)。

   栏区几何 (`s_BoundX/Y/W/H`) 在重扫期间并没有变, 所以改用只由
   `SWS_Draw` 置位、隐藏时才清零的 `s_BoundsKnown`。

3. **`s_EatPress` 是死代码**。它在同一次 `SWS_Poll` 调用里置 1 又清零,
   门永远读不到。真正起作用的只有 `s_HoldSkip` (整段按住)。已删除,
   免得下一个人以为"吞这一帧"是个独立机制。

## 定案

- **需选格类**: 按下只记 `s_ArmIdx` + `s_SelDown`, 整段按住由
  `s_HoldSkip` 吞掉; **松开边沿**才写 `CurrentSWTypeIndex`。
  写的时候按键已松开, 引擎"按住即释放"的条件不可能成立 ——
  等价于真 Gadget 消费掉这次完整点击。
- **即时类**不受影响: 它走 `SpecialPlace` 事件, 从不写
  `CurrentSWTypeIndex`, 所以"按下即发"仍然成立。

## 排查这类问题的通用手法

日志能把"谁生成的这次释放"分清: 看 `Location` 是不是 `(0,0)`
(我们推的) 还是真实格子 (引擎按当前鼠标格放的), 再看 `IsExecuted`
字节 (`0x00` vs 引擎写的 `0x5A`)。别只看"超武没了"就猜时序。


# 附: 帧率 —— 0x4F42F0 不是"每帧一次"

## 最大的性能坑: 挂错钩子位置

`SWS_Poll` (以及同一函数里的其它 9 个 `*_Poll`) 挂在 `0x4F42F0`
(`MOExperience_PrepareEntry`)。当年注释写的是"帧准备钩, 每循环必跑"——
**"每循环"被当成了"每帧"**。

实际: gamemd 里 `call 0x4F42F0` 有 **113 个静态调用点**, 散在 AI / 对象 /
渲染 / 消息代码里, 多处位于**逐对象循环内**。

日志实测 (用两个独立锚点交叉验证):

| 锚点 | 计数 | 换算 |
|---|---|---|
| `sws: perf` (每 60 次 SWS_Draw 一行) | 209 行 | 12,540 渲染帧 |
| `sws: poll` (每 60 次 SWS_Poll 一行) | 29,707 行 | 1,782,420 次调用 |
| 比值 | | **每渲染帧 142 次** (区间 47~225) |

142 倍扇出意味着每帧白烧:

- 142 × `GetAsyncKeyState` (各 Poll 若干)
- 142 × 2 次 `QueryPerformanceCounter`
- `SwsFireWatch` 的 78 次条目循环 → **每帧约 11,000 次迭代** (现已删除)
- `SwsScan` 的"每 15 次"其实是每 0.25 秒一次, 不是注释说的 1 秒
- `sws: poll` 实际是**每渲染帧 2.4 行**, 所以 30,688 行日志里 29,707 行
  (97%) 都是它

**日志本身不是帧率杀手** (2.4 × (SetFilePointer+WriteFile) ≈ 50~150 µs/帧),
真正的开销是这个扇出。`SWS_Draw` 自身 `d=` 中位数 1355 µs 才是第二大项。

## 修法

1. **帧门**: `SWS_Poll` 开头读引擎帧号 `0xA8ED84` (`ADDR_FRAME`), 与上次相同
   就直接返回。同一渲染帧内 142 次调用只真跑 1 次。
   (帧号在输入处理之后才推进, 而 `0x4F42F0` 的第一次调用在帧首, 所以
   "与上次相同则跳过"就够, 不必关心它一帧推进几次。)
2. `SwsFireWatch` 从"每次 Poll"挪进扫描节流 (15 帧) —— 后来干脆连同
   `EvWatch` 一起删掉了 (见配置节)。
3. `sws: poll` 汇总周期 60 → 600 帧 (有了帧门后这已是 10 秒一行的常量开销)。
4. 删掉 `SWS_Poll` 里白读一次的 `ADDR_FRAME` (`int fr` + `(void)fr`)。

## 还能砍的 (未做, 按性价比排序)

1. **其余 9 个 `*_Poll` 同样在 142 倍扇出里** —— `AirWay/BuildQueue/
   PatrolCircle/SmartOrder/TreeChop/FuzzyAttack/SmartArea/DeployPreview/
   MindSelect` 都在 `PowerDrawBoth` 里被无条件调用。这是当前最大的一块
   剩余开销, 但每个模块的轮询频率需求不同, 要逐个加帧门或挪到真正的
   帧钩 (`0x5D49A0`, 单调用点, 已有 `GreenHook`/`MessageDrawHook` 在里面)。
2. `MOExperience.cpp` 的 `MsgPowerDrawSb()` 每次 prepare 都锁面画一次
   闪电+文字 (≈142 次锁/帧), 而上屏钩已经画过一遍。
3. ~~`SWS_Draw` 每帧重算布局 + 插入排序 76 条 (约 2,900 次比较)~~ **已做**:
   布局/排序/像素全部移进"重建"路径, 15 逻辑帧一次 + 交互立即。见"绘制:
   离屏缓存"。剩下每帧只算指纹和悬停 (两次 O(条目数) 整数循环)。

   规划多了会刷屏。
5. `LogLine` 每次调用都 `SetFilePointer(FILE_END)` (一次系统调用)。
   改成维护内存偏移量可以省掉, 但当前调用频率已经不高, 优先级低。

## 教训

**"每循环必跑"不等于"每帧一次"。** 写钩子注释时必须实际数一遍
`call <addr>` 的静态引用和它所在的循环层级。判据: 一个真正的帧入口
应该只有 1 个调用点; 113 个调用点的那个是逐对象调用的。

# 附: 滚动 / 布局

- 面板级偏移 (单个 `s_Scroll`, **所有列一起滚**)。原本设计成逐列, 但
  `ColGap=0` 之后列间没有空隙, 4px 滚动条塞不下, 会盖在下一列图标上。
- 滚动上限 = `colCount - 可见行数` (不是 `colCount-1`, 那会一路滚到只剩
  最后一行、中间全空)。
- 滚动条整块右侧一根, 参照战役框 (`MOExperience.cpp` `DrawBox` 战役分支):
  4px 宽, 轨道 `RGB(30,30,30) alpha 55` / 滑块 `RGB(170,170,170) alpha 90`;
  有列装不下时整块左边让出 5px, 否则会顶出屏幕右缘。
- 出界条目 `x = -1`, 既不绘制也**不参与命中** —— 必须 `if (x < 0) continue;`,
  否则 `mx >= -1 && mx < -1+IconW` 对屏幕左侧整条竖带恒真。
- 滚轮走已有的 `MOExperience_WheelHook` (`0x777998`, 5B/6B), 读
  `wparam = *(unsigned*)(regs+OFF_REG_ECX)`, 高位 `0x80000000` 为上滚。
  传给 `SWS_WheelIn` 的 dir **是反的** (与战役框手感对齐), 见调用处注释。

# 附: 性能

- 绘制是主要开销。引擎 `PCX::BlitToSurface` 每调一次就锁/解锁一次合成面,
  N 个条目 = N 次锁面; 现在在同一次锁面里直接写像素
  (`SwsPcxBlitLocked`), 布局对不上才退回引擎 blit。
- **诊断代码本身也是每帧成本。** 三次踩坑:
  1. 某个诊断函数每帧 `GetPrivateProfileIntA` = 每帧一次 ini 文件 I/O。
     所有 ini 读取必须收敛到 `*_EnsureInit`。(该诊断后来已删除, 但这条
     规矩对现存的所有 `*_Poll` 依然有效)
  2. `sws: perf` / `sws: poll` 每帧 `LogLine` 一行, 日志涨到 4MB / 21 万行。
  3. 上面两条的根因是 `0x4F42F0` 每帧跑 142 次, 所谓"每帧一行"其实是
     每帧 2.4 行。**帧门修掉之后**这些节流数字才终于名副其实。
- 计时范围要覆盖所有每帧路径。原来只测 `SWS_Draw`(`d`) 和 `SwsScan`(`s`),
  `SWS_Poll` 是盲区 —— 里面的开销日志完全看不见。现在有 `sws: poll`。
- 扫描节流: 每 15 **渲染帧** (约 0.25 秒) 重扫一次, 玩家点击时立刻补扫。
  布局 (x/y) 仍每帧在 `SWS_Draw` 重算, 命中判定不受影响。
- 完整分析 (142 倍扇出的推导、剩余可砍项) 见
  "附: 帧率 —— 0x4F42F0 不是每帧一次"。

# 附: 反复踩到的同一类错误 —— 别拿"缺失"当证据

这轮翻了三次车, 都是同一类:

1. **照抄参考实现就下结论。** 照抄 Phobos 的 `LaunchSuper` 以为 SpecialPlace
   就够了; 实际上 Phobos 根本没接 ChargeDrain。
2. **从"代码里找不到某赋值"反推行为。** 因为 Firestorm 在 `SWTypes/` 里没有
   `Action=None` 赋值, 就推断它需要选格 —— 而手册和 `SW_Firewall::Activate`
   都明说不用格子。找不到 ≠ 不存在。
3. **照抄了有 bug 的代码。** `BuildQueue.cpp` 的 `BQ_FireProduce` 里那段
   `__asm__ ("call *%1")` 只声明了 `ecx/edx/cc/memory` 被破坏, 而真实
   `call` 还会破坏 `ebx/esi/edi/ebp` —— 编译器以为那些寄存器还是自己的,
   实际已被 callee 改掉, 崩在 `EAX=ESI=<代码地址>`。
   **现在改成普通函数指针调用, 让编译器自己生成 `call`。**

正确做法: **抓包 / 读被调用方源码**, 让事实说话。`sws: tbl` 这个诊断就是
为此保留的 (它直接给出 `inst` / `rdy` / `rem`, 是判断"点了到底生效没有"
最省事的依据)。

# 附: 其它已确认的坑 (跨模块通用)

- 探针扫内存时**必须跳过虚表指针**: offset 0 是 `0x004xxxxx` 的代码地址,
  被当成结构读会顺着"文件名指针"二次解引用 -> 必崩。
- 建缓存槽位时**必须同时记 id**, 否则查找永远失配、槽位涨满后一律返回
  NULL (曾导致 PCX 分支静默失效, 全体回落紫球)。
- 删代码时判断注释起点要用 `lstrip().startswith("/*")` —— 注释是缩进的,
  否则脚本会走错位置, "删掉了"其实没删。
- **构建校验必须看退出码 + DLL 时间戳**, 不能只 grep `error C`: gcc 的
  `error:`(无 C) 不匹配, 曾连续多轮报告"构建成功"而 DLL 根本没更新。
- **新增 `[SWSidebar]` 配置项要改两处**: ini 里加键, **并且**加进
  `SwsLoadIniList` 的 `isGlobal` 排除串。漏了的话该键会被当成"超武 ID"收进
  `s_Ini`, 侧栏上多出一个永远不亮的空条目 (不报错、不崩, 只是莫名其妙多一行)。
  已踩过一次: `DrainSupers` / `ScrollStep` 两个键都在 ini 里, 却没进排除串。
- **扫 ini 找"谁引用了 X"时, 一个键可能有多种形式**。判断超武挂没挂到建筑上
  要用 `SuperWeapon(?:s|2)?` 同时认三种:
  - `SuperWeapon=X` (单槽)
  - **`SuperWeapon2=X` (第二槽)**
  - `SuperWeapons=a,b,c` (**逗号分隔列表**)
  两个实际踩过的坑:
  - 用 `SuperWeapon2?\s*=\s*(\S+)` 只匹配单值 → 漏掉 18 个真实挂载
    (辐射四联空袭 `PackAttackSpecial` 等全在复数形式里)
  - 用 `SuperWeapons?` 里的 `s?` 去覆盖"复数" → **漏掉整个 `SuperWeapon2=`
    第二槽**, 连带把挂在上面的超武误判成"未挂载", 少算 25 个
  - 单值后面可能带 `]` (如 `[SuperWeapon=Xxx]`), 要 `rstrip(']')`
  - 找"属于哪个节"要**逐行扫**并记住当前节名; 用 `rfind('\n[')` 会跳到
    错误的行 (比如 `[SuperWeapons=3]` 这种非节名的方括号行)
  - 重新扫一遍文件时**别忘了重置"当前节"变量**。踩过: 第二段循环复用了
    第一段留下的 `cur`, 结果整份挂载表都指向同一个节名 (所有超武的
    "挂载建筑"全显示成 `VariableNames`)
  - CSF 查表有三个坑, 见 `超武列表.md` 的"中文名是怎么查出来的"一节:
    **前缀大小写不敏感** (三份表分别用 `name:` / `Name:` / `NAME:`,
    只匹配一种拼写会漏掉整张表)、**键名要统一小写**、**两张表有 33 处
    同名不同值需要定优先级** (按覆盖率: 表10 主力 93/135, 表09 兜底补 2 个)
- **"剔除某类"要先确认判定条件, 别只按单一字段过滤**。`超武列表.md` 的主表
  要求 `ShowCameo != false` **且** (有 `UIName` 或已挂载) —— 只按 cameo 过滤会
  把 `[CeasefireSpawn]` 这种既没名字也没挂载的纯占位节留在表里。
- 手写 OutList 追加这类"照抄别处"的活, 要检查 clobber 列表是否完整。
