# 帧率 / 帧内耗时 (v0.2.473)

起因：不用 MOE 时 OSD 显示 414 帧，用了掉到 207（正好一半），怀疑扩展拖慢。

## 结论：0x4F42F0 (prepare) 每帧被调用 161 次

`0x4F42F0` 是"渲染前 prepare"，但**不是每帧一次**。它有上百个静态调用点，分布在
AI / 对象 / 渲染 / 消息代码里，多处在逐对象循环内。`PowerDrawBoth` 挂在那里，
于是里面每个 `*_Poll` 都跟着跑 161 遍/帧。

实测（1920x1080，1x 缩放，超武侧栏关闭，画中画小窗关闭，存档 SAVE1D75）：

| 版本 | 帧率 | prep(us/帧) | 其中 |
|---|---|---|---|
| 0.2.471 (优化前) | 188~216 | **1600~1900** | pipb 850 / pwr 210 / pv 147 / rp·ms·ra 峰值各 100~170 |
| 0.2.473 (门控后) | **302** | 95~117 | fm 16 / sb 13 / ss 5 / mhk 5 / 其余 ≤1 |

一次 total 约 4.8ms → 3.3ms。旧的 `SWS_Poll` / `Aggressive_Poll` 早就自己用帧号门控
（注释里写明了原因），其余模块没跟上。

## 修法

`PowerDrawBoth` 里加 `PrepDue()`：**帧号变了 或 距上次 >= 16ms** 才算一轮。

- 前半句把同一帧内的重复调用压成一次（帧内输入状态本来就不变）。
- 后半句保证暂停/步进时（引擎帧号 `0xA8ED84` 冻结，迷你循环里 prepare 照跑，
  `PauseView` 的 `PV_MiniLoop` 也靠它）输入照样被采样，F5 恢复不会失灵。

留成"每循环必跑"的只有：`FM_Poll`（撑满视口 + 摘侧栏 gadget，引擎每次切页都会
把按钮重挂回来）、`SS_Poll`（依赖 FM_Poll 结果）、`SB_Poll`、以及鼠标钩重试。

`PowerDisplay_DrawSb` / `PiP_DrawButton` 每帧画一次就够 —— 呈现前 `BlitSbEntryDraw`
里还有一次兜底。

## 怎么再看（探针）

`MOExperience.ini` 的 `[Log] Perf=1`，每 1~2s 往 `MOExperience.log` 写一行：

```
perf: ms=1000 f=302 prepN=161 gate=0 fc=0 gs=0 prep=95 fm=15 sb=13 ss=5 aw=0 ...
       msg=278 msgswp=209 msgdraw=35 msgtail=31 blitsb=50 vecblit=116 vecgdim=13
```

- `f` = 窗口内帧数（照墙钟），`prepN` = 每帧 prepare 被调用几次（正常 1，实际 161）。
- 各项都是 **us/帧**（已除以帧数），可直接和帧周期对比。
- `Perf_Now()` 在开关关闭时直接返回 0，调用点全部短路，常驻无成本；开着时多出
  约 1000 次 QPC/帧（~40us），测最高帧率时先关掉。

## 还没解决的（优化后残留，合计约 0.5ms/帧）

| 项 | us/帧 | 说明 |
|---|---|---|
| `msgswp` | 210 | `SWPanel_Draw` 超武倒计时面板。面板在地图区内，Composite 每帧被地图重绘覆盖，必须每帧重画；5 行 × (RenderLine ×2 + 阴影 blit + 覆盖 blit) + 5 条半透明底 |
| `vecblit` | 116 | VecText 接管后引擎逐字绘制（每帧约 200~300 字）。关掉 `[VecText] Enable` 可省 ~290us（302→331），但字体回点阵 |
| `msgdraw` / `msgtail` / `blitsb` | 35 / 31 / 50 | 各层 UI Draw、聊天框+底电+条带、侧栏呈现入口 |
| 未归集 | ~370 | 关掉所有已知段后仍有残差，怀疑是 43 个 Syringe 钩里高频的那几个（blit 守卫、鼠标虚表钩等），尚未逐项计时 |

已排除：画中画小窗（用户确认测的时候没开；`pip: window ON` 只是某次开过）、
`PlacementPreview_DrawHook`（`pprev` 一次都没触发）、迷雾钩、`VecText` 的字宽度量
（`vecgdim` 只有 13us）。

## 复查 0x4F42F0 调用频率的办法

`prepN` 就是从 `s_PfCnt[PF_PREPARE]/frames` 来的。任何新模块挂 `0x4F42F0` 的 Poll
都要自己门控一次，否则直接按 161 倍计。

# 第二轮 (v0.2.474): 302 -> ~335 fps

目标 350。这一轮把"能靠缓存/门控省掉的"都省了，剩下的都撞在引擎的固有路径上。

## 结果

| 版本 | 帧率 (同存档同场景, 含探针) | 关探针 |
|---|---|---|
| 0.2.471 | 188~216 | — |
| 0.2.473 | 302 | — |
| **0.2.474** | 309~347 (中位 334) | **~335** |
| 0.2.474 关 `[VecText] Enable` | 350~351 | — |

**350 正好是"不开矢量字体"的水平** —— 也就是说 MOE 其余全部功能 (消息帧 UI、prep、钩子、
侧栏 blit) 加起来只值 ~130us，剩下 180us 全是 VecText 逐字重绘的代价。

## 这一轮改了什么

1. **超武面板 SWPanel: 206us -> 65us/帧** —— 合成层缓存。
   原来每帧: 两轮 `RenderLine` 量宽 (10 次 GDI 度量, 79us) + 引擎半透明底板 (20us) +
   阴影/正文逐像素 blit (104us)。现在把"底+阴影+正文"预合成到一张 32 位 alpha 层
   (`0xAARRGGBB`, A=0 透明), 每帧只做一趟整矩形 over 到画面。
   层是否复用由内容指纹 (行文本+颜色+anchor+surfH+全部配置) 决定 —— 超武倒计时按秒变,
   所以每秒重建一次, 其余帧只贴。细分账: `swpm`(量宽) 现在恒 0, 贴层记在 `swpb`。
2. **`OU_KeyDown` 帧内缓存** —— `GetAsyncKeyState` 是系统调用 (~1us), 一帧里 10 个
   `*_Draw` 各查一次 Ctrl/中键就是十几 us。改成帧号相同且墙钟 <16ms 时复用上次结果
   (暂停时帧号冻结, 靠墙钟兜底保证 F5 灵敏)。
3. **`mhk` 门控** —— 鼠标钩重试挪进 `due` 块 (原来 161 次/循环的空检查 + 计时 = 4us/帧)。
4. **`VecRender` 混合热循环** —— 8 位混合改 5 位 alpha 查表 (`g_BlendR/g_BlendG`,
   `TB[inv][dst] = dst*inv/31`, 前景侧按字现建 32 项), 每像素只剩 4 次表查 + 3 次加。
   **实测没有明显收益** (vec 仍 110~130) —— 说明瓶颈不是算术而是字形 cov / 目标面内存访问。
   代码保留 (视觉无差, 边界 a=0/255 精确), 但别再往这个方向优化。
5. **`[Log] Perf=2` 新模式** —— 只记 `perf: ms= f=` 两列, 不做任何分段计时,
   用来判断"掉没掉帧"时几乎零开销。

## 新增的埋点 (Perf=1 时才跑)

- 钩子频率普查: `napp pcol rally sbar skinH tsel bqH repair msgadd chatsp radar esc wheel pipH`
  → **实测全部 ≤14 次/帧**, `pcol/napp/msgadd/chatsp/pipH` 一次都没有。**没有高频钩子陷阱了**。
- VecText 三段: `vprint`(=Print 3 次/帧) `vsimple`(=Simple 14 次/帧) `vprtO/vsmpO`(其中放行给
  引擎原版的部分) `vb1/vb2`(BlitBody 的 Measure 前/后)。
  结论: **vprint/vsimple 的时间几乎 100% 是"放行给引擎原版"** (vprtO≈vprint, vsmpO≈vsimple),
  我们自己拦截/收集的那部分只有 ~0.5us/次。所以别去优化 Print/Simple 里的判断逻辑。
- `clr` = 侧栏面整条抹黑 (`Fm_ClearStripExceptRadar`): **0us**, 不是瓶颈。

## 剩下的账 (Perf=1, f=333)

```
prep=84 (fm15 sb13 ss5 其余~50)   msg=133 (msgswp65 msgdraw31 msgtail33)
blitsb=47   vecblit=109/14字   vecgdim=12   vprint=111 vprtO=111   vsimple=125 vsmpO=118
```

- `msgswp 65us` = 面板层 (346x136 ≈ 47000 px) 一趟 over, 1.4ns/px, 已接近内存带宽。
  想再降只能少贴 (面板内容不变的帧无法跳过 —— 地图每帧把它覆盖)。
- `blitsb 47us` 里 37us 是 `FM_BlitSb` 末尾**引擎的 CopyFromPart** (侧栏面 -> 主面),
  小地图上屏必需; `FM_DrawRadarTo` 在 msgdraw 里还 blit 一次到 Composite。
  (全屏模式下这两个目标面若相同, 理论上能省一次, 但改动会碰视觉残留, 没做。)
- `vecblit 109us/14字` = 7.8us/字。15 个字 = 3 次 Print + 3 次放行 Simple 画的字
  (顶栏数字/提示), 每字约 350 像素。算术已优化到查表仍无改善 -> 固有成本。

## 结论 / 下一步 (若要继续冲 350+)

1. **顶栏数字改回点阵**: `[VecText]` 里给 `CredPx` 那套加"数字走原版 blit"的开关,
   预计省 60~80us (VecText 关掉时 350, 差的 180 里数字占大头)。
2. **合并 BlitSb / DrawRadarTo 的双重 blit** (省 ~30us, 需验证视觉)。
3. 继续抠 msgdraw/msgtail (31+33us, 10 个 Draw + 5 个收尾绘制, 单个 3~6us,
   都在跑"引擎状态查询 + 早退"—— 可以做一次共享帧级上下文)。

# 第三轮 (v0.2.475): ~335 -> fmed 357~370, **350 达成**

上一轮一直在抠 VecText 的逐像素混合, 边际收益为零。这一轮换成问"**每帧到底哪些
调用在重复做同一件事**" —— 一次没用新算法, 全是调用时机/去重, 省下的比前两轮都多。

## 结果 (同存档同场景)

| 版本 | 帧率 | 说明 |
|---|---|---|
| 0.2.474 | 309~347 (中位 334) | 关 `[VecText]` 才 350 |
| **0.2.475** | **f= 341~357 / fmed 357~370** | 开 `[VecText]`, 已超过旧的"关矢量字体"天花板 |

**370 = 上面那个"关掉 VecText 才 350"的天花板被整体顶高了**, 说明省下来的是
VecText 之外的部分, 不是又去动字体。

## 关键: 先把"谁在重复"量出来 (新增埋点)

原来只知道几个大块, 不知道块里是谁。这一轮加了 23 个槽:
- `sbSS/sbPWR/sbPIP/sbFM` —— 侧栏呈现入口四段
- `dSWS/dSO/dPC/dRP/dFA/dSA/dTC/dDP/dWR/dAG/dRAD` —— 消息帧里 10 个 `*_Draw` + 雷达
- `tCE/tPWR/tSB/tPV/tSHOT` —— 收尾五段
- `vhit/vmiss` + `vwhy` —— 字形缓存命中率与未命中原因码
- `lock` —— 全部 `GtLock/GtUnlock` 的 vtable 调用 (实测 16 次/帧共 1us, 不是问题)

**结论式发现**: 10 个 `*_Draw` 全是 0us (早退干净), 雷达 `dRAD=32`,
侧栏末尾 `sbFM=38`, 刻度条 `tSB=32` —— 三个都是"每帧重画一次很小/重复的东西"。

## 这一轮改了什么

1. **刻度条 32us -> 6us (`msgtail` 35 -> 10)** —— 根因是 `RenderLine` **先 `CharsFit`
   再查缓存**: 命中缓存也每帧白跑一次 `GetTextExtentExPointW`。改成**先查行缓存**
   (键用原始 len, 限宽只影响画多宽), 命中就一个字节都不问 GDI。
   这是**全局收益**: 所有用 `RenderLine` 的地方 (超武面板行/提示/标签) 都跟着快。
   实测 `tSB` 里 `sbLbl` 从 ~28us 降到 4us。
2. **雷达重复上屏 32~40us -> 0 (`blitsb` 48 -> 14)** —— 同一块小地图每帧 blit 两次:
   `FM_DrawRadarTo` 进 **Composite**, `FM_BlitSb` 再进 **Primary**。
   日志实测 `composite!=primary`, 而 present 会把 Composite **整幅**送上屏 ——
   也就是说 Primary 那一次的落点**每帧都被覆盖**, 纯白烧 (开个日志确认后,
   把 `FM_BlitSb` 末尾那趟 `CopyFromPart` 去掉, 脏标记/抹黑/光标烙印照做)。
   截图逐项核对: 小地图/侧栏/超武面板/刻度条全正常。
   > 附带确认了一条老结论: 本 MO 的侧栏本来就不是靠 `BlitSidebar` 上屏的
   > (钩子恒返回 `Fm_Ret4` 跳过原版整条 blit), 它走的是 Composite present。
3. **超武面板贴层 66 -> 46us** —— 层里像素只有三种身份, 建层时打 tag:
   `tag0` 全透明 (整段跳过) / `tag1` 纯底板 (纯黑+固定 alpha, 混合**逐通道可分离**,
   用 32/64/32 项通道表直接算, 与 `Blend16(dst,0,0,0,a)` 逐位相同) / `tag2` 才走通用混合。
   贴层按 tag 分段走最省的路径。通道表由 `Blend16` 自己生成, 保证逐位一致。
   (剩 46us ≈ 47000px × 1.0ns, 已接近"读一行+写一行"的带宽, 再往下要 32 位成对写。)
4. **prepare 里两笔重复 10us** —— `PowerDisplay_DrawSb` + `PiP_DrawButton` 在 prepare
   的 `due` 块里画一遍, 侧栏呈现入口 `BlitSbEntryDraw` 每帧又画一遍。
   改成 prepare 只做兜底: 侧栏 100ms 内呈现过就跳过 (`s_BlitSbTick` 记墙钟, 不用帧号
   —— 暂停时帧号冻结, 侧栏照样在呈现)。
5. **`GdiEnsure` 槽位撞车** —— `SWPanel` 和 `PowerDisplay` 都用槽 3, 字号/字面不同,
   一旦内容变化就互相拆 DIB 重建; SWPanel 改到槽 9 (以后新增模块记得各占一槽)。
6. **新指标 `fmed` (中位帧率)** —— 1 秒窗口的 `f=` 会被载入/卡顿拉低 (同一场景两轮能
   差 20), 加了 50us 一档的帧间隔直方图, 报中位数。以后比性能看 `fmed`, 别再看 `f`。

## 新账 (v0.2.475, f=347 / fmed=357)

```

blitsb=14 (sbPIP7 sbPWR3 sbFM2)        vecblit=69/14字  vecgdim=12
```

- `prep=71` 里约 35us 是**探针自身开销** (161 次 `Perf_Now`+`Perf_Add`), 真实 ~40。

- `sbPIP=7` 是画中画按钮每帧重画, 静态内容, 可做层缓存 (约省 5us) —— 没做。

## 下一步 (若要继续)

1. `msgswp` 46 -> ~25: tag 段的 bg 内层改成 32 位成对读写。
2. `sbPIP` 7 -> 2: 按钮层缓存 (照 SWPanel 那套)。

# 第四轮 (v0.2.477~480): 超武侧栏"关闭后不归还" + 三种状态的帧率账

## 1. 修的是什么 bug

用户报: 关掉超武侧栏后, 原版"防御与支援"页仍然是被过滤状态 (没有图标)。

根因有两层, **第二层才是真凶**:

1. `SwsDedupSync()` 开头 `if (!s_Enable) { s_DedupDirty = 0; return 0; }` —— 关掉总开关
   之后永远不搬回; `SWS_Poll()` 的 `if (!s_Enable) return;` 连同步都不跑。去重是**单向**
   搬出 (直接剪切 `TabCameos[1]` + `SwsDefenseRepair` 收尾), 关了以后没人还。
2. **过滤会存进存档**: 在去重态下存档, 读档后防御页本身就是空的。实测那一局
   `sws: dd hide n=0` (我们这一局一条都没搬) 而 `cameo=56` 里一条超武 cameo 都没有
   (`clean snapshot n=0`)。所以"只在 `s_Removed` 为真时才归还"这个判据必然漏掉这种局面。

修法: 关闭总开关时**无条件**补一遍 (一次, 用 `s_RestoreDone` 压住), 搬回只走引擎
`AddCameo(0x6A6300)` (自带查重, 已经在页上的不会加第二次), **不碰容器、不调
`SwsDefenseRepair`** —— 由 AddCameo 自己收尾 `CameoCount`。换图/读档 (`SwsCacheEpoch`)
与重开 (`SWS_SetEnabled(1)`) 都要把 `s_RestoreDone` 清回 0。

## 2. 自动化验证 (不靠截图)

新增 `[Log] TestSws` 时序开关 (默认关, 只在初始化读一次):
`动作@进对局后的毫秒, 逗号分隔, 每项只触发一次`, 动作 = `off/on/hide/show/dd0/dd1`,
全部走与鼠标/按键**同一条状态路径**。

**不能用帧号做触发**: 载入期帧号已经跑过上万, 写死的帧号会在进对局前全部触发完
(实测 5 个动作挤在 5 行日志里)。改成 `Unsorted::ScenarioStarted` 之后按
`GetTickCount()` 毫秒计时。

一次 90s 运行的结果 (v0.2.480):

```
dd hide n=0                 cameo=56 strip=56    <- 存档里就是被过滤的
test off  ms=6000
dd restore on disable n=78  cameo=134 strip=134  <- 78 条全部还回
test on   ms=12000
dd hide n=78                cameo=56  strip=56   <- 再打开又全搬走 (可逆)
test hide ms=18000 / show ms=24000
test off  ms=30000
dd restore on disable n=78  cameo=134 strip=134  <- 可重复
```

`cameo` (容器 `TabCameos[1].Count`) 与 `strip` (`StripClass::CameoCount`) 全程相等 ——
这两个数不等就是"cameo 加回去了但格子里什么都没有"。

## 3. 三种状态的帧率账 (同一次运行, `[Log] Perf=1`, 6~64 个 1s 窗口平均)

| 状态 | fmed | f | `sws` (prep) | `dSWS` (msgdraw) | `msgdraw` |
|---|---|---|---|---|---|
| 启用 + 展开 (78 图标) | 282 | 270 | 7us | **457us** | 491us |
| 启用 + 收起 (只有箭头) | 321 | 309 | 1.7us | 74us* | 107us |
| 关闭 (原版接管) | 284 | 274 | **0.1us** | **13.7us** | 46us |

\* 收起态那 74us 是 6 个窗口里夹了一次箭头缓存重建 (~450us 摊到 6 帧), 不是每帧成本。

回答用户的问题 "**不过滤、也不展开时, 是不是还有额外开销**": **没有**。
关闭态 `SWS_Poll` 只剩一次 `s_RestoreDone` 判断 (0.1us), `SWS_Draw` 首行
`if (!s_Enable) return` (13.7us 是探针噪声)。收起态同理。

## 4. 顺手量出来的新结论 (下一步的靶子)

- **展开态每帧 ~457us 的合成 blit 是当前最大单笔开销**, 比原版整条侧栏还贵:
  收起 (321fps, 3.11ms) vs 展开 (282fps, 3.55ms) 差 430us, 与 `dSWS=457` 对得上。
- **关闭态 (284) 比收起态 (321) 还慢 35fps**, 而关闭态我们这边是 0 —— 这 ~430us
  只能是**原版侧栏自己画回来**的成本 (用户要的"恢复原样"本来就得付这笔)。待确认。
- 目标仍然 350fps 的话, 现在瓶颈已经不是矢量字体, 而是**侧栏整块合成**:
  78 图标 ≈ 240x960 的 16 位 alpha 混合。可行方向: 只重blit变化的那几格 (脏矩形),
  或者把整块 32 位 alpha 层改成"预先乘好 + 成对 32 位写"。

# 第五轮 (v0.2.481): 埋点清理 —— 只计次的 Perf_Hit 全部删掉

## 为什么要清

`Perf_Hit(slot)` 与 `Perf_Add(slot,t0)` 是两回事:

- `Perf_Add` = 一次 QPC 前后差, 给的是**耗时**;
- `Perf_Hit` = 只 `s_PfCnt[slot]++`, 给的是**次数**。它存在的唯一理由是早期那轮
  "钩子频率普查" (结论已在上面第二节: 全部 ≤14 次/帧, `pcol/napp/msgadd/chatsp/pipH`
  一次都没出现, 没有高频钩子陷阱)。普查结束, 这些埋点就只剩噪音 ——
  每 1s 往日志里塞 `tsel=0/11 radar=0/5 pipH=0/1` 这种既不是耗时也无人看的列。

## 删了什么 (15 槽位 / 38 处调用)

| 槽位 | 次数 | 文件 |
|---|---|---|
| `PF_H_BQ` | 8 | BuildQueue.cpp (点击/绘制 8 个钩) |
| `PF_H_CHAT` | 5 | ChatEdit.cpp (4 钩 + HideNative) |
| `PF_H_MSG` `PF_H_WHEEL` `PF_H_SBAR` | 3 | MOExperience.cpp |
| `PF_H_TSEL` | 3 | TypeSelect.cpp (SetCtx/BuildingGate/Clear) |
| `PF_H_PIP` | 3 | PiP.cpp (左键 down/up/band) |
| `PF_TIP` | 3 | ToolTip.cpp (三个钩) |
| `PF_H_RALLY` `PF_H_REPAIR` `PF_H_ESC` `PF_H_RADAR` ×2 | 2 each | RallyPath / RepairAll / EscMenu / MsgText+FullMap+SWSBar |
| `PF_H_NAPP` `PF_H_PCOL` `PF_H_SKIN` | 1 each | NoApproach / PlayerColor / SidebarSkin |

## 保留了什么

- `PF_VHIT` / `PF_VMISS`: 同样是 `Perf_Hit`, 但它给的是**命中率**(比例), 不是频次,
  而且 VecText 优化还没结束 —— 唯一继续留着的一对。
- 所有 `Perf_Add` / `Perf_AddDelta` 分段计时, 包括名字仍叫 `PF_H_PRINT/SIMPLE/
  PRTO/SMPO/VB1/VB2/CLAER` 的那组 (它们是计时的, 只是命名沿用了旧前缀)。

## 防错

`kPfName[]` 改成**不写长度**的数组 + 一句编译期断言
(`sizeof(kPfName)/sizeof(kPfName[0]) == PF_COUNT`)。以前写死 `[PF_COUNT]`, 少写一项
就是补 NULL → `AppendCStr` 崩或**名字整体错位**(不报错, 日志张冠李戴)。

## 老实说: 这不涨帧率

`Perf=0` 时 `Perf_Hit` = 一次 call + 两次读静态 + 比较 ≈ 2ns, 而且这些钩子每秒才几次
(`tsel` 11 次/秒、`radar` 5 次/秒、`pipH` 1 次/秒)。**清理是给日志和代码看的, 不是给
帧率看的。** 真正花钱的是 `Perf=1` 时的 QPC —— 那才是 `Perf_Add` 的成本 (~35us/帧)。

## 顺手量到的新靶子: prepare 入口仍进 72 次/帧

新场景 (用户换的那张图, 240fps 档) 的 `perf` 行: `prepN=72 prep=48/72 fm=9/72
sb=10/72 ss=3/72`, 而 A 段每个 Poll 都是 `/1`。

即: 每帧有 **72 次** 进入 `0x4F42F0` → `PowerDrawBoth`, 其中只有 1 次跑 A 段 (26 个
Poll), 其余 71 次只跑 `FM_Poll` / `SS_Poll` / `SB_Poll` (这三段是**故意**每循环都跑的:
引擎每次切页/改视口都会把侧栏 gadget 重新挂回去)。48us/帧 ≈ 0.67us/次。

要压的话只能改那三段自身的"是否真需要"判据 (例如用 gadget 计数/视口指纹而不是无条件
重挂), 不能简单加帧号门 —— 这是下一个靶子, 本轮没动。

# 第六轮 (v0.2.482~485): 把每帧的像素成本打下来 (fmed 269 -> 325)

## 1. 先把钱数清楚 (新增两个槽位)

`dSWS` 原来是 `SWS_Draw` 整段, 分不清"重建"和"贴层"。加 `PF_SWS_BUILD` / `PF_SWS_BLIT`:

| 项 | 展开态 (125k 像素) |
|---|---|
| `swsL` 每帧带 alpha 贴层 | **420us** (10 cycles/px) |
| `swsB` 重建 (当时 15 帧一次) | 74us/帧均摊 (~1ms/次, 每秒 20 次) |
| `dSWS` 合计 | 496us |

顺带打了像素构成 (`sws: blit 246x510 zero=5466 opq=0 mix=119994`):
**全透明 5%, 全不透明 0%, 半透明 95%** —— 没有"可直拷"的活可省, 每个像素都得算。
(0 个全不透明是因为 `Alpha=75` 把图标也压成半透明了。)

## 2. 贴层改 SSE2 (逐位等价, 不是"近似")

标量内核: `r += ((dr - r) * ia + 128) >> 8`, `ia = 255 - a`, 在 5/6 位空间里算。
SSE2 版 8 像素一批:
- `pmullw` 算 `(dr-r)*ia` —— `|(dr-r)*ia| <= 31*255 = 7905`, 16 位不溢出, **积是精确的**;
- `paddw 128` + `psraw 8` —— `psraw` 就是 C 的算术右移, 负数舍入方向一致;
- `a==0` / `a>=255` 用 `pcmpeqw` 掩码选回 `d` / `c`, 与标量那两条早退等价;
- 位深/gm 走运行时移位 (`psrlw` 向量计数版), 565/555 同一份代码。

**验证不靠截图**: 加一次性自检 `SwsSse2Scan` —— 同一帧、同一批真实像素, 标量与 SSE2
各从同一个目标值出发算一遍逐像素比对。日志 `sws: sse2 selfcheck rows=510 bad=0`。

结果: **420us -> 88us (4.8x)**。`IsProcessorFeaturePresent(10)` 判 SSE2, 老 CPU 退回标量。

## 3. 重建加墙钟门 (帧数门在高帧率下会失控)

原来只有"15 个逻辑帧"一道门。60fps 下 = 250ms 挺好, 但 300fps 下只有 50ms
→ **每秒重建 20 次, 每次 ~1ms, 光为了刷一个每秒才变一次的充能百分比**。
加 `SWS_REBUILD_MS 200`: 两道门都过才重建 (内容/悬停/选中变化仍然当帧重建)。

结果: **swsB 74 -> 18us/帧**。`dSWS` 496 -> 108us。

## 4. 本轮结果 (同一场景, 侧栏展开)

| | 之前 | 之后 |
|---|---|---|
| fmed (`Perf=1`) | 269 | **323** |
| fmed (`Perf=2`, 几乎零探针) | — | **325** |
| dSWS | 496 | 108 |
| msgswp (超武面板) | 96 | 92 |

`fmed` 从 269 到 325 = **+21%**。Perf=1 与 Perf=2 只差 2fps, 说明探针本身已经不是负担。

## 5. 剩下的账 (Perf=1, fmed=317 那行)

```
msg 247 = msgswp 93 (超武面板) + msgdraw 139 (dSWS 107 = swsL 85 + swsB 17; dRAD 29) + msgtail 10
prep 61 (72 次入口; fm 9 sb 7 ss 2, 其余是门与探针)
blitsb 15 (sbPIP 7 + sbPWR 3 + sbFM 3)
VecText: vsimple 24 (其中 12 是放行给引擎) + vecgdim 15 + vprint 5 + vecblit 4
```
我们全部加起来 ≈ **300us / 3077us = 10%**。也就是说**把我们所有绘制全部删掉**
也只有 360fps —— 350 的天花板就在这里, 再往上是引擎自己的账。

## 6. 评估过但没做的 (留证据, 免得下次重走)

- **`msgswp` 93us (47k 像素, 2ns/px)**: tag1 底板走的是"R/G/B 三张 32/64/32 项表",
  已接近该形态的极限。换 64K 单表 (128KB) 每次查表要跨 L2, 大概率不划算。
  它的 `Blend16` 是**8 位空间**混合 (`/255` + 反量化), 与本轮 SSE2 内核的 5 位空间不同式,
  不能直接复用 —— 要 SIMD 就得重写一套并重新证明逐位等价。
- **`prep` 里 72 次入口**: `FM_Poll` / `SS_Poll` / `SB_Poll` 是**故意**每循环跑的
  (引擎切页/改视口会把侧栏 gadget 重新挂回去, 靠 1 帧一次的门会闪一帧原版按钮)。
  只剩 ~3us 真活, 不值得冒画面风险。
- **`sbPIP` 7us**: 每次呈现在条带面上重画按钮。跳过它会依赖"条带面本帧不会被别人清",
  这条件没证据, 省 5us 不值。
